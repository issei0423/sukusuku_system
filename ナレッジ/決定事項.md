## 2026-10-15 ｜ デモのサーバは Azure for Students の VM に SQLite のまま置き、相手の画面への反映は SSE で即時にする

**背景**：下の項（2画面のデモ）を決めたあと、チームはサーバをクラウドに置き、DB を PostgreSQL にしたいと希望した。あわせて、5秒ごとの読み直しではなく、相手の操作をすぐに出したい（即時読み込み）という希望も出た。経緯は `Discordログ/2026-10-15.md` の 12:01・12:13・12:15・12:22 ごろの項にある。

**決定**：

- **サーバは、Azure for Students の小さな VM（B1s・東日本）に、Go のバイナリと SQLite をそのまま置く。PostgreSQL へは移さない。** 2026-09-07 の決定「本演習では SQLite」は変わらない。アカウントは持ち主が作る
- **相手の画面への反映は、SSE（Server-Sent Events）で即時にする。** サーバは、関係する人に「変わった」とだけ知らせ、画面はそれを受けて読み直す。5秒ごとの読み直しは、接続が切れたときの保険として残す

**理由**：

- 持ち主の条件は「無料枠で使えること」だった。Azure for Students の VM は、カード不要で12か月無料、スリープも勝手な再起動もない。セッションをメモリに持つ今の作りのままで、ログインが消えない
- SQLite のまま置けば、PostgreSQL への移行（3〜5人日の見込み）が要らず、11/13 のリハーサルに間に合わせやすい。次の案は採らなかった
  - Render（サーバ）＋ Neon（PostgreSQL）：完全に無料だが、15分使わないと眠り、起きるまで約1分かかる。移行も要る
  - Cloudflare Tunnel：SSE を使うには名前付きの Tunnel と自分のドメインが要り、ドメインの費用で無料の条件から外れる。アカウント不要の Quick Tunnel は SSE に対応していない
  - Render の Postgres は30日で消え、Koyeb は新規登録が有料、Fly.io は無料枠がない
- SSE にしたのは、5秒待たずに相手の画面に出せ、Go の標準の機能だけで作れるため。WebSocket は双方向に送れるが、部品の追加が要り、知らせを受け取るだけの今回には大げさ。間隔を1〜2秒に縮める案は、使う人が多いと重くなる

**影響範囲**：サーバの置き場所と手順書、`server/`（知らせを配る仕組みと受け取り口）、`web/src/hooks.ts` と自動更新の対象の画面、デモプレイの台本

**まだ決まっていないこと**：

- VM での HTTPS の付け方（Caddy を想定）と、外から見られる範囲。デモのパスワードは誰でも使えるので、公開するなら見られる人を絞る方法を決める
- VM を作ることと外部に公開することは、持ち主の承認を得てから行う

**確かめていないこと**：

- この日の時点で、Azure for Students の登録は終わっていない。SSE は作っている途中
- SSE は、サーバを1台で動かす前提である（知らせとセッションをサーバのメモリで持つため）

## 2026-10-15 ｜ 中間発表のデモは、PC 1台に保育士・保護者の2画面を並べて見せ、園長の画面は出さない

**背景**：中間発表（11/13 にリハーサル）の3分のデモについて、チームが台本①〜④を作った（①朝の連絡 → ②午睡チェック → ③日誌の申請・承認・共有 → ④保護者ホームに届く）。台本は保護者・保育士・園長の3つの立場にまたがる。そのため、次のことが決まっていなかった。

- 画面をどう並べて見せるか
- 相手の操作をもう一方の画面にどう出すか
- 台本にあって今の画面に無い機能をどうするか

経緯は `Discordログ/2026-10-15.md` の 11:05・11:18・11:32 の項にある。

**決定**：

- **PC 1台に、保育士と保護者の2つのブラウザの窓を並べる。園長の画面は出さない。** 同じブラウザでは1人しかログインできないので、ブラウザか Chrome のプロフィールを分ける
- **③の日誌の承認は、発表の前に済ませておく。** デモでは、④で保護者に届いたところだけを見せる。承認と共有を分ける仕組みは、発表の中で口頭で説明する
- **台本に合わせて、機能を足す。**
  - 午睡チェックで、スワイプで記録できるようにする
  - 保育士のダッシュボードに、個人チャットの「未対応」を出す
- **自動更新を足す。** 相手の操作が、数秒でもう一方の画面に出るようにする

**理由**：

- 2画面を並べるのは、会場のネットが要らず、「送ったら相手に届く」を同時に見せられるため。次の案は採らなかった
  - 端末を分ける案：会場の Wi-Fi で端末どうしがつながらないおそれがあり、スマホの画面は客席から見えない
  - 1画面で立場を切り替える案：切り替えが多く、3分に収まりにくい
- 園長の画面を外すのは、3分に収めるため。③の承認を画面で見せる案は、次の理由で採らなかった
  - 3つ目の窓を短く映す案：時間がかかる
  - ログインし直す案：さらに時間がかかる
- 機能を足すのは、台本の「スワイプで記録」と「ダッシュボードに未対応として出る」が、今の画面と違っていたため。台本の言い方を今の画面に合わせる案もあったが、チームは機能を足すほうを選んだ。午睡チェックのスワイプは、要件定義書 4-4 の記述にもある
- 自動更新を足すのは、今は画面を読み込み直さないと相手の操作が出ず、デモの手順ごとに F5 が要るため

**影響範囲**：デモプレイの台本、中間発表の台本（スライド High_v3 版）、午睡チェック、職員のダッシュボード、チャット、保護者ホーム、ヘッダの通知、`mockup-go-react`

**あとで決まったこと**：

- サーバの置き場所と即時読み込みは、同じ日に決まった（上の項「デモのサーバは Azure for Students の VM に SQLite のまま置き、相手の画面への反映は SSE で即時にする」）。PostgreSQL へは移さない

**確かめていないこと**：

- 自動更新とダッシュボードの「未対応」は、同じ日にできて、ローカルの `mockup-go-react` にマージした（5951b88。この日の時点で push はしていない）。スワイプは、まだ着手していない
- 午睡チェックは同じ日に、ダイアログをやめて、園児の行で直接記録する形に変わった（`mockup-go-react` の a8a9b98）。スワイプは、この形の上に足す

## 2026-10-09 ｜ 画面詳細図の項目表と実画面の食い違い100件を、3つに分けて決着させた

**背景**：`図/画面詳細図.md` の全画面の項目表を、モックアップの実画面と1行ずつ突き合わせた。文言・部品の形だけの違いは項目表を直したが、**項目表にあって実画面に無い機能と、値・動きの違いが100件**残り、どちらへ寄せるかを決めていなかった（同図 第1.13版「モックアップ実装との差異」(11)）。

**決定**：性質で3つに分け、それぞれの寄せ先を決めた。

- **形・動きが違うが、機能は実画面で成り立っているもの（約45件）は、実画面を正とする。** 項目表を直した。例：停止・再開は編集領域ではなく一覧の行のボタンで行う／共有範囲は切り替えるたびに保存する／絞り込みの初期値は「すべて」／呼吸は「あり・確認できず」、顔色は「通常・蒼白・紅潮・その他」／CSV はエラーが1行でもあれば1件も登録しない／保護者への共有を選べるのは個人日誌だけ
- **モックアップに実装していない機能（30件）は、仕様として残す。** モックアップでは実装しない範囲として、同図 (11-1) に挙げた。例：年度更新の実行／各一覧の絞り込みとページング／追加読み込み／帳票の出力／写真・添付のファイル選択／プライバシーポリシーへの同意／保護者の一時パスワードの再発行
- **検査の抜けと、不具合に近いもの（約25件）は、モックアップを直す。** GitHub Issue #136、PR #137

**理由**：項目表は仕様の正だが、項目表を書いたあとにモックアップを作り込んでおり、画面のほうが後から決めた形である箇所が多い。機能が成り立っているものまで項目表へ戻すと、画面の作り直しが多く出る。一方、実装していない機能を項目表から削ると、要件定義書・基本設計書の記述まで落とすことになる。検査の抜けは、仕様にも実装にも言い分が無く、直すほかない。

**実画面を正としなかったもの**：次の3件は、設計書に理由つきの定めがあったため、実画面ではなく設計書の側を残した。

- 雛形を呼び出したとき、入力済みの本文を置き換えない（書きかけを失うため）。モックアップを直した
- 一時パスワードは「口頭または手渡し」で伝える（要件定義書）。モックアップの文言を直した
- 午睡チェックの体温は入眠時のみ必須（設定マスタの値）。仕様として残し、モックアップでは実装しないものに入れた

**影響範囲**：`図/画面詳細図.md` 第1.14版、`基本設計書.md` 第2.7版（4-4・4-5）、`図/インタフェース一覧.md` 第1.3版、`mockup-go-react`（PR #137）

**確かめていないこと**：ヒヤリハットを保護者への共有の対象外としたことは、実画面に合わせた結果であり、園の運用を聞いて決めたものではない。PR #137 はマージしていない。

## 2026-10-09 ｜ モックアップで仮に置いていた20項目を、いまの動きのまま設計として確定した

**背景**：管理側のペルソナのデモと PR #92 の評価で見つけた指摘（GitHub Issue #95〜#129）を直すとき、設計に定めが無いものは仮の扱いを置き、`web/仮置き値.md` (7-2・7-3) に20項目をまとめていた。モックアップはその扱いで動いており、設計書には書かれていない状態だった。

**決定**：**いまのモックアップの動きを正とし、`基本設計書.md` 第2.6版の該当する節へ書いた。** 主なものは次のとおり。

- 自分が申請した日誌は承認できない／保護者へ共有する承認は確認を挟む／承認済みの日誌に承認者と共有の有無を出す
- 編集ロックはログアウトで外す／読むだけのときは取らない／強制解除は編集画面から行う
- 職員の氏名・ロール・担当クラスは発行後に変えられる（自分のロールは不可）／解除した紐づけを戻せる
- 園児のよみは必須／アレルギーは対象・症状・対応を揃える／平熱は範囲の外で確認を促す／園児ID・職員IDは次の番号を入れておく
- 招待コードの有効日数は 1〜365 日／一括発行は使えるコードを持つ園児を飛ばす
- 午睡チェックは自クラスに限り、当日のぶんだけ開始でき、終了後は記録できない
- チャットのメンバー一覧は参加者と管理者に限る／登録と同じ秒のメッセージは見せない／配布物の取り下げは誤送信対応の対象にしない
- 操作ログに操作の相手を出す／CSV 出力を記録する／完了の表示と確認ダイアログを共通の扱いにする

**理由**：仮置きのまま置くと、動いているものと設計書が食い違い続ける。項目ごとの理由は、指摘を直したときに `web/仮置き値.md` と各 Issue に書いてあり、それを設計書の本文へ移した。**園の運用で変わりうる3件**（自分が申請した日誌の承認、午睡チェックを後から入力する運用、配布物の取り下げを誤送信として記録するか）は、実在の園へのヒアリングを行っていないため、演習上の想定として `要決定事項.md` (1-1) に残した。

**影響範囲**：`基本設計書.md` 第2.6版（4-3・4-4・4-5・4-6・4-7・4-9・5-2・5-8）、`要決定事項.md` 第2.5版（演習上の想定 20件 → 23件）、`web/仮置き値.md`（7-2・7-3 を設計書への案内に置き換える）

**確かめていないこと**：`図/画面詳細図.md`・`図/インタフェース一覧.md` には反映していない。足した経路（職員の情報の変更、紐づけの復元、園児IDの重複の確認、出力の記録）と、変えた画面の項目が、両図に載っていない。


## 2026-10-09 ｜ 管理側のペルソナのデモで残った7件を決めた（ロール・管理者の停止・ログインの記録・規約・基準値・デザイン見本）

**背景**：管理側のペルソナ5名のデモ（`ペルソナ/管理側5名_デモの記録.md`）で見つけた指摘のうち、設計に定めが無いものが残っていた。あわせて、以前から開いたままだった GitHub Issue #68・#69・#72 の扱いを決める必要があった。

**決定**：

1. **園長・主任以外の職種のロール**（#113）。ロールは3つのまま変えない。事務員・看護師などが本システムを使う場合は、**管理者ロールを付与する**。演習上の想定とし、導入時に園へ確認する。**却下した案**：名簿だけを扱える4つ目のロール「事務」を足す（権限表・テーブル・サーバ・画面のすべてに及ぶ。職種ごとの業務の切り分けを園に確かめられない）。事務員・看護師を利用対象外と明記する（名簿の管理を園長・主任が行う前提になり、園の実態を確かめずに決めることになる）。
2. **管理者による、ほかの管理者の停止**（#111）。**許す。** 自分自身は停止できないため、管理者が1人も居なくなる状態は作れない。確認ダイアログに管理者である旨を示し、相手を操作ログに残す。**却下した案**：管理者は管理者を停止できない（退職した管理者を止めるには、先に一般へ下げる手順が要る）。
3. **ログインの記録**（#115）。**失敗と、失敗が続いたことによるロックだけを操作ログに残す。** 成功は残さない。**却下した案**：成功も残す（共用タブレットで担当が替わるたびに行が増える。誰が記録したかは各操作の記録で追える。ログアウトを対象としない既存の判断と同じ考え方）。何も残さない（不正な試行に気づく手段が無くなる）。
4. **職員が同意する利用規約**（#126）。**文書は1本のまま**とし、職員と保護者の双方に適用する。`利用規約・プライバシーポリシー.md` はもとから双方を対象としており、合っていなかったのはモックアップの同意画面に出る本文（デモデータ）だけだった。**却下した案**：職員用の規約を別に作る（同意の判定と同意履歴を文書の種別ごとに持つ実装が要る）。職員には同意を求めない（要件定義書「利用規約への同意」(4-1-1) の対象を変えることになる）。
5. **利用規約の園情報の記入と法務の確認**（#68）。**行わない。** 本システムは演習の成果物であり、実際の園へは導入しないため。Issue は対応しないものとして閉じた。
6. **成長曲線基準値**（#69）。**厚生労働省「平成22年乳幼児身体発育調査」の公表値を投入する。** 演習では仮の値のままとする、という 2026-09-07 の判断を改めた。満月齢0か月には出生時の値、1〜23か月には「N～N+1月未満」の値をそのまま当て、24〜72か月は6か月ごとの公表値を直線で補間する。
7. **デザインアーキテクチャ案の画面見本**（#72）。静的な試作の画像を、**いまのモックアップを撮った画面画像へ差し替える。** 指摘のあと、実際の画面には布目の背景やクレヨン調の見出しが入っており、試作の画像は実物と離れていた。

**理由**：どれも、決めないかぎりモックアップと文書が「未定」のまま残る。実在の園へのヒアリングを行っていないため、園の実態で変わりうるもの（1）は演習上の想定として置き、導入時に確認する事項に残した。成長曲線基準値（6）は、帯の位置が実際と違うと誤った見取りを招くという、もともとの懸念を先に解いた。

**影響範囲**：`要件定義書.md` 第2.14版「アカウントの管理」(4-1-2)・「納品形式」(9)、`基本設計書.md` 第2.5版「ログイン」(4-3)・「アカウントの停止と再開」(4-3)・「成長曲線基準値」(5-7)、`要決定事項.md` 第2.4版、`利用規約・プライバシーポリシー.md` 第1.2版、`図/デザインアーキテクチャ案.md`、モックアップ（PR #131・#132・#133）

**残っていること**：成長曲線基準値は、公表資料の PDF から機械的に読み取った。**人の目による全行の突き合わせは済んでいない。**

## 2026-10-06 ｜ 園だより・献立表は「園からの配布物」として一覧に置く

## 2026-10-06 ｜ ペルソナのデモと実装で見つかった設計の穴8件を決着させた

**背景**：モックアップの実装中に見つけた穴（GitHub Issue #57・#58・#59・#61）と、ペルソナ4人分のデモで見つけた穴（#88〜#91）が、論点の整理に留めたまま残っていた。いずれも「どう直すかはこの Issue では決めない」としていたものである。2026-10-06 に、ユーザーへ案を示して進め方の了承を得た。

**決定と理由**

1. **日誌の差し戻す理由は、`t_diary` に `returned_reason` を1列足して最後の1件だけを持つ**（#57）。理由は作成者がいま何を直すかを知るためのものであり、往復の経緯は操作ログで追える。**却下した案**：差し戻しの履歴を別の表で持つ。テーブルが1つ増えるわりに、画面で経緯を追う場面が想定できなかった。
2. **発達チェックの所見は、`t_development_check` に `note` を1列足し、園内限定とする**（#58）。所見は項目に紐づかないため、項目単位の共有可否の対象にならない。共有できるようにすると、共有しないと決めた内容を所見に書くことで設定を素通りできてしまう。**却下した案**：所見に「共有する／しない」の指定を持たせる。運用の注意に頼ることになる。
3. **クラスに年齢児の列 `age_class` を足し、午睡チェックの間隔をそこから引く**（#59）。タイマーはクラス全体で1つであり、園児の月齢からもクラス名からも決められない。**却下した案**：クラスに間隔そのものを持たせる。混合保育でも表せるが、年齢別の既定値をクラスごとに入れ直す手間が出る。**混合保育は扱わない想定**とした。
4. **クラス日誌・週案月案は、保護者への共有の対象外とする**（#61）。共有先は対象園児の個人チャットであり、対象園児を持たない記録には送り先が無い。**却下した案**：クラスグループへ送る（ほかの園児の様子や写真が全保護者へ届き、写真の利用同意を毎回確かめることになる）。園児それぞれの個人チャットへ送る（同じ本文が人数ぶん流れる）。
5. **園の名称と電話番号は、設定マスタに `facility.name`・`facility.phone_number` として持つ**（#88）。保護者向けの緊急連絡の案内に番号を出し、その場で電話へ切り替えられるようにする。**却下した案**：園の情報の表を新しく作る。項目が少なく、表を1つ増やすほどではない。
6. **現在と同じパスワードへの変更を認めない**（#89）。一時パスワードを同じ値のまま使い続けられると、変更を強制する意味がなくなる。過去に使った値までは遡って調べない（履歴を持つことになり、定期変更を求めない方針とも合わない）。
7. **後から登録した保護者には、登録より前の個人チャットのやりとりを見せない**（#90）。先に登録していた保護者は、自分の書いたものが後から加わる人に読まれることを知らない。経緯を伝える必要があるときは、職員が改めて書く。職員はすべて読める。**却下した案**：すべて見せる。園児についての経緯は伝わるが、書いた本人の知らないところで読み手が増える。
8. **続柄を、職員側のメンバー一覧に保護者の氏名へ添えて出す。保護者の参加は通知しない**（#91）。お迎えに来る人が誰なのかは園児の安全にかかわる。参加は園が発行した招待コードによるものであり、園はすでに知っている。

**影響範囲**：`要件定義書.md` 第2.12版（日誌の共有の表、過去ログの参照範囲、パスワードの要件）、`基本設計書.md` 第2.3版（クラス・日誌・チャット・発達チェックのテーブル、設定マスタ、画面基本構成、パスワードの要件、メッセージ一覧）、`図/ER図.md` 第1.2版、`図/画面詳細図.md` 第1.8版、`要決定事項.md` 第2.2版（演習上の想定が13件から18件に）。モックアップ（`mockup-go-react` ブランチ）も同じ内容へ合わせる。**このうち3・4・2・7・8の5件は、実在の園に確かめていない演習上の想定である。**

## 2026-09-07 ｜ 認証情報はサーバ側セッション＋HttpOnly Cookie で保持する

**背景**：`要決定事項.md` A-2。バックエンドとフロントエンドを分離したため、サーバ側セッションを続けるか、アクセストークンを画面側に持たせる方式へ変えるかが未定だった。**認証の作り直しになるため後戻りが大きい**として優先度Aに置かれていた。

## 2026-09-07 ｜ CSRF対策は SameSite=Strict と Origin 検証の二段構えとする

**背景**：`要決定事項.md` A-3。**未対策のまま実装が進むと、後から全ての更新系の経路に手を入れることになる**として優先度Aに置かれていた。実装は Cookie に `SameSite=Strict` を付けていたが、`session.go` のコメント自身が「緩和策であって、対策の決定ではない」と断っていた。

**決定**：①セッションの Cookie に `SameSite=Strict` を付ける、②**状態を変えるリクエスト（POST・PUT・PATCH・DELETE）で `Origin` を検証する**、の二段構えとする。`Origin` が無い要求は `Referer` で代替し、**どちらも無ければ拒否**する。

**理由**：`SameSite` だけに頼らないのは、ブラウザによって扱いに差があり、将来この既定が緩和されうるため。**「ヘッダが無ければ通す」は対策にならない**ので、送信元を確かめられない要求は拒否する。

**却下した案**：トークンを配って毎回照合する方式（二重送信 Cookie／同期トークン）。Cookie でセッションを持つ構成では、トークンの発行・保持・失効を画面側にも作り込むことになり、**得られる安全性の差に見合わない**。`Origin` の検証は数十行で同等の効果が得られる。

**運用上の帰結**：ブラウザ以外のクライアント（テストや `curl`）は `Origin` を自分で付ける必要がある。結合テストはブラウザと同じヘッダを送るように直した。

**影響範囲**：`要件定義書.md`「セキュリティ要求」(8 No.10)、`基本設計書.md`「CSRF対策の方式」(6-3)。実装は `server/csrf.go`

## 2026-09-01 ｜ ログイン中は、系統・アカウントを問わず新しいログインを成立させない

**背景**：保護者用と職員用で入口（URL・画面）を分ける方式は要件定義書 第1.1版で決まっていたが（「アプリのログイン」(4-1-1)）、**入口をパスで分けると Cookie はドメイン単位で共有される**ため、「職員としてログイン中に保護者用の入口を開いたらどうなるか」が未定義のまま残っていた。実装方式を選ぶ段で表面化した論点であり、要件定義書にも `要決定事項.md` にも項目が無かった。

**決定**：同一ブラウザでは、**ログイン中に別のログインを成立させない**。系統（職員用・保護者用）が同じか異なるか、アカウントが同じか異なるかを問わず、先にログアウトを求める。**上書きログイン（新しいログインで前のセッションを置き換える動作）は設けない。** 制限は職員↔保護者の**両方向に対称**とする。要件定義書 第2.4版「アプリのログイン」(4-1-1) に「同時ログインの扱い」として明記し、機能一覧に「同時ログインの制限」を追加した。

**理由**：①**担当交代の起点をログアウトに統一するため。** 既存の「ログアウト」と「端末の利用形態と本人特定」(4-1-4 (4)) は、共有タブレットでの担当交代がログアウトから始まる前提で書かれている。上書きログインを許すとこの前提が崩れ、共有端末で前の職員のセッションが黙って置き換わり、ログアウト忘れに誰も気づかないまま運用が続く。②**規則を1つにすると例外が無くなる。** 「系統をまたぐときだけ禁止」とすると、同一系統での上書きは許すことになり、①の穴がそのまま残る。③**非対称な制限は説明できない。** 職員→保護者だけを禁じる理由が無く、片方向だけにすると設計書で理由を書けない。

**運用上の帰結**：職員が自身の子どもを同じ園に預けている場合、その職員は職員アカウントと保護者アカウントの2つを持つ（ロールはアカウントに固定されるため。「システムの利用者」(3-1)）。この場合、**一方をログアウトしてからもう一方でログインする**運用になる。同一ブラウザで両方を同時に開くことはできない。

**未定のまま残した点**：**別の端末・別のブラウザでそれぞれログインした場合の可否は定めていない。** 本決定が対象とするのは同一ブラウザのログイン状態のみ。多重セッションを許すかどうかは別論点として、`要決定事項.md` に「別の端末・別のブラウザからの同時ログインを許すか」（優先度B・設計判断）として起票した。既定は「制限しない」。

**影響範囲**：`要件定義書.md` 第2.4版「アプリのログイン」(4-1-1)、`基本設計書.md` 第1.3版「ログイン」(4-3)、`要決定事項.md` 第1.2版「別の端末・別のブラウザからの同時ログインを許すか」、これから作る画面詳細（ログイン画面・ログアウトの導線）

## 2026-09-01 ｜ 保護者用と職員用の入口は、パスプレフィックスで分ける

**背景**：「アプリのログイン」(4-1-1) は「入口（URL・画面）を分ける／バックエンド・DB・認証基盤・園児マスターは共通／別アプリケーション・別コードベースにはしない」と定めているが、**どのレイヤーで分岐させるか**は決まっていなかった。候補はドメイン層（サブドメイン）・URL 層（パス）・アプリ内部（条件レンダリング／コード分割／ビルド分割）の3層。

**決定**：**パスプレフィックス方式**（`/staff/...` と `/parent/...`）を採る。あわせて、①**ログイン後の遷移先はサーバー側でロールを見て決める**（リダイレクト）、②フロントは**コード分割（遅延読み込み）**で、ロール確定後に必要な系統だけ取得する、の2つを組み合わせる。Go 側はルーターの route group、React 側は Router のツリー分割で実現する。現行の Flask モックアップで先に試す場合は Blueprint ＋ テンプレート継承が対応する。

**理由**：①**サブドメイン方式は localhost 検証環境と相性が悪い。** DNS・TLS 証明書・CORS・Cookie ドメインの設計が必要になり、「本演習での動作検証環境（localhost）」(6-2) では hosts ファイルの書き換えまで要る。演習規模に対して過剰。②**単純な条件レンダリングでは入口を分ける目的を満たさない。** `role === 'parent' ? ... : ...` は両系統のコードが全員のブラウザに配信されるため、保護者の端末に職員用画面の項目名やメニュー構成が丸ごと落ちる。「利用者が自分に関係のない導線を目にしないようにする」という目的（「アプリのログイン」(4-1-1)）に反する。コード分割ならこれを避けつつ実装は軽い。③パス方式は認可のミドルウェアをプレフィックス単位でまとめて掛けられる。

**注意**：**画面の出し分けは権限制御ではない。** 入口を分けても、各 API でロールとクラス所属を毎回検証しなければ意味がない。「職員用の入口から保護者アカウントでログインできない」もフロントの分岐では担保されず、認証処理で入口の系統とアカウントのロールを突き合わせて弾く必要がある。未解決事項の「基本設計書の権限マトリクスと要件定義書の権限表の突き合わせ」と同じ問題。

**影響範囲**：`基本設計書.md` 第1.3版「システムの利用方法」(2-2)（反映済み）、これから作る画面詳細、`mockup` ブランチの実装。**マスタ文書（Google ドキュメント）への反映は未了**（`要決定事項.md` D-1 の判断待ち）

**決定**：8 No.3 を「利用者が継続して用いる恒久パスワードを保持しない」に限定し、一時パスワードは①発行画面で1度だけ表示、②システム側はハッシュ化して保存し再表示しない、③有効期限を設け初回ログイン時の変更を必須とする、の3条件で扱う。管理者の復旧は他の管理者による再発行とし、**管理者ロールは常に2名以上**を運用要件とする。管理者が1名になる操作にはシステムが警告を出す。

**理由**：メール送信基盤を持たない演習の制約下では、管理者経由の再発行以外に現実的な手段がない。原則を曖昧にするのではなく、例外の範囲（発行から本人の変更までの間だけ）を明示して限定するほうが、設計としても監査の説明としても筋が通る。

**影響範囲**：全体要件定義書 4-1-1・8 No.3

## 2026-08-03 ｜ 日誌の保護者共有は記録種別ごとの既定値＋管理者の個別指定とする

**背景**：第1.4版は、承認された日誌をチャットツールの個人チャットへ「自動送信」するとしていた。しかしテンプレートには「クラス日誌」があり、クラス日誌には他児の氏名・様子が含まれうる。一律に自動送信すると他児の情報が各保護者へ渡る。発達チェックには項目単位の共有フラグがあるのに、日誌には共有可否の制御が一切なかった。

**理由**：自動送信のままでは、保育士の記述内容次第で個人情報の混入が起きる。かといって毎回すべて手動選択にすると承認の手間が増えるため、既定値で通常運用を回し、例外だけ管理者が判断する形にした。

## 2026-07-28 ｜ 想定運用環境と演習での検証環境を分けて記述する

**背景**：第1.3版で、要件どおりに作ると成立しない矛盾が見つかった。6章の Web サーバは「Flask 開発サーバ（`http://localhost:5000`）」である一方、3-3 は「保護者＝スマートフォン」「ブラウザから URL にアクセス」としていた。localhost では園内の当該 PC からしか開けず、チャットツールに一本化した保護者機能が丸ごと動作不能になる。あわせて、8章が「要配慮個人情報に準じて扱う」としながら通信暗号化の要件がなく、HTTP 前提のままだった。

**決定**：6章を「6-1 想定運用環境（園への導入時）」と「6-2 本演習での動作検証環境」の2段構成にする。6-1 は HTTPS 必須・WSGI サーバ・サーバ用 DBMS・インターネット公開を要件とし、6-2 は localhost／SQLite／Flask 開発サーバとする。8章に「通信の暗号化」を独立要求として追加し、6-1 で必須・6-2 では非適用と明記する。演習範囲の制約（保護者機能は開発用 PC のブラウザで検証する、HTTPS は適用しない）も本文に明示する。

**理由**：保護者スマホ利用という要件を取り下げずに、演習で作れない部分を正直に示せるため。localhost に統一すると、コンセプトの中核である保護者連携が評価されなくなる。園内 LAN 案は、保護者が自宅から連絡帳を見るという価値が失われるため却下した。

**影響範囲**：`HFD_要件定義書02_レビュー編集済み.md` 3-3・6・8章、午睡チェックの通知方式（Web Push は HTTPS 前提のため演習範囲外）、基本設計書の環境記述

## 2026-07-28 ｜ 保護者アカウントは招待コードによる自己登録方式とする

**背景**：職員アカウントは「管理者が発行」と定義されていたが、保護者アカウントの発行方法がどこにも記述されていなかった。一方 `mockup` ブランチには招待コード方式の新規登録タブが既に実装されており、要件に根拠のない機能が存在する状態だった。あわせて、園児と保護者の紐づけ（1園児に複数保護者、1保護者に複数園児）が未定義で、「保護者は自児のみ閲覧」という権限の判定根拠そのものが欠けていた。

**決定**：管理者が園児ごとに有効期限つきの招待コードを発行し、保護者がそのコードで自己登録する方式とする。登録時にコードに紐づく園児と保護者アカウントを自動で紐づける。兄弟姉妹がいる場合は、既存アカウントに追加のコードを入力して紐づける。「自児」とは当該保護者アカウントに紐づく園児を指すと定義する。

**理由**：園が保護者の平文パスワードを持たずに済む。管理者が初期パスワードを発行して配布する方式は、受け渡しの運用負担と漏洩リスクがある。モックアップの既存実装とも一致し、要件と実装の乖離を解消できる。

**影響範囲**：`HFD_要件定義書02_レビュー編集済み.md` 4-1-1・4-1-2・8章、`mockup` ブランチの新規登録実装、基本設計書の ER 図（園児と保護者の多対多）

## 2026-07-28 ｜ 午睡チェックのアラームは「画面を開いたままの運用」を前提とする

**背景**：「0歳児は5分間隔で通知」は SIDS 対策の中核だが、Web アプリでブラウザを閉じた／端末がスリープした状態で通知する方式が未定義だった。実現方式なしにこの要件は満たせない。

**決定**：午睡中はタブレットで午睡チェック画面を開いたまま運用することを前提として明文化する。通知は画面内のタイマー表示と通知音で行い、画面を常時点灯させる。端末の自動スリープ無効化とマナーモード時の通知音は運用手順で担保する。Web Push は演習の対象範囲に含めない。あわせて「本機能は保育士の目視確認の代替ではない」ことを明記する。

**理由**：Web Push は HTTPS 必須で Service Worker の実装を要し、演習の検証環境（localhost／HTTP）では成立しない。画面常時表示なら確実に実装でき、実際の保育現場でもタブレットを手元に置いて午睡チェックを行うため運用実態に合う。判断・安全の責任を保育士に置くという設計原則とも整合する。

**影響範囲**：`HFD_要件定義書02_レビュー編集済み.md` 4-2 (3) 午睡チェック、7-2 性能・可用性、利用手引き（未作成）

## 2026-07-28 ｜ 保護者向け機能をチャットツールに一本化し、保護者ポータルを廃止する

**背景**：要件定義書のなかで、保護者向け機能の担当が矛盾していた。「2-2 対象範囲」は保護者向けの閲覧・お知らせ・連絡受信を**対象外**（保護者ポータルの責務）としていたが、「3-1 システムの利用者」「3-2 利用イメージ」「6 運用環境」は保護者を正規の利用者として扱っていた。原因は、発達チェック単機能の要件定義書（保護者ポータルへ連携するのみ、という前提で書かれたもの）の文言を、システム全体の要件定義書へそのまま持ち込んだこと。

**決定**：独立機能としての「保護者ポータル」を廃止する。保護者向けの記録閲覧・お知らせの受け取り・園への連絡は、すべてチャットツールが担う。日誌・発達チェック・身体測定の記録は、共有可否フラグを付与してチャットツールの個人チャットへ引き渡し、保護者はチャット画面上で閲覧する。

**理由**：文書の実態が既にチャット一本化に寄っていたため。日誌システムの「保管・共有」は個人チャットへの自動送信と書かれ、発達チェックの画面・機能フローも「個人チャットへの連携フロー」となっていた。ポータルを残すと保護者向け画面が2系統に分かれ、保護者側の導線が複雑になる。「4-1 機能全体像」の4機能構成（日誌・チャット・午睡チェック・発達チェック）とも整合する。却下案：保護者ポータルを5つ目の機能として追加する案は、演習の作業量に対して見合わないため見送った。

**影響範囲**：チャットツール、発達チェック、日誌システム、`HFD_要件定義書02_レビュー編集済み.md`（第1.3版で反映済み）、`発達チェック機能_要件定義書.md`（**未改訂・旧記述が残存**）、`CLAUDE.md`

## 2026-07-28 ｜ 権限を役職ロールに一本化し、管理者モード／一般モードの呼称を廃止する

**背景**：「3-1 システムの利用者」では園長・主任＝管理者、保育士＝一般としていたが、「4-2 チャットツール」の注記では「管理者モード…園長・主任・保育士、一般モード…保育士」となっており、保育士が両モードに属していた。モードの切替条件はどこにも定義されていなかった。加えて権限表で個人チャットが管理者モード「―」となっており、園長・主任が保護者と個人チャットできない読み方になっていた。

**決定**：モードという概念を廃止し、「管理者（園長・主任）／一般（保育士）／保護者」の3ロールに統一する。ロールはアカウントに固定して付与し、利用者が状況に応じて切り替えることはない。個人チャットは管理者も送受信可能とする。

**理由**：モードを残すと切替条件・切替UI・切替時の監査ログという要件が芋づる式に必要になり、演習の範囲に見合わない。園長・主任が保護者対応を行うのは通常の運用であり、個人チャットを不可とするのは実態に反する。

**影響範囲**：チャットツール、日誌システム、午睡チェック、発達チェック、`HFD_要件定義書02_レビュー編集済み.md`（第1.3版で反映済み）、基本設計書の権限マトリクス

## 2026-06-16 ｜ システムは発達の判定・診断を行わない

**背景**：発達チェック機能で「遅れ」の自動判定を行うかが論点になった。

**決定**：発達の遅速判定・医療的診断・療育要否の判断は一切行わない。システムは記録・可視化・気づきの支援に徹する。

**理由**：評価と判断の責任は保育士・園側にあり、システムが判断を持つと責任の所在が曖昧になる。医療行為との線引きの問題もある。

**影響範囲**：発達チェック（プロジェクト全体の最重要設計原則）
