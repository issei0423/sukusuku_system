# すくすくシステム（すくすくハイブ）

保育支援システム。保護者という「点」と保育士という「点」を、育児という「線」でつなぐ、園児管理を兼ねたコミュニケーションツール。
チーム開発演習（Hive-Five Developers）の成果物。

> **要件については `要件定義書.md`（第2.7版）が唯一の正**です。本READMEはその要約であり、食い違いがあった場合は要件定義書に従ってください。プロジェクトの進め方は `CLAUDE.md` を参照。
>
> **2026-10-17 から作り直し中。** 作り直しの芯（保護者と保育士を子どもでつなぐ。事務の効率化はおまけ）は `設計方針.md` にある。要件定義書・基本設計書はこれに沿って改訂するまで、`設計方針.md` と食い違う箇所がある。

## 背景・コンセプト

| 項目 | 内容 |
| --- | --- |
| コンセプト | 保護者という点と保育士という点を、育児という線でつなぐ、園児管理を兼ねたコミュニケーションツール |
| ターゲット層 | 保育士と保護者の**双方**（保育士だけの業務効率化ツールではない） |
| テーマカラー | 優しい黄色 |

- 保護者の要望: 子どもの状態・行動がいち早く／どこでもいつでもわかる、シンプルで直感的なUI/UX
- 保育士の要望: 資料管理の負担軽減、日誌などの書き込みの効率化、シンプルで直感的なUI/UX

ねらいは、チャットツールによる情報共有の迅速化と、日誌システムによる事務作業時間の削減を通じて、**保育士が園児と向き合う時間を最大化する**こと。

**チャットツールが「保護者と園をつなぐ唯一の窓口」**であり、日誌・発達チェック・身体測定の記録は共有可否のフラグを付けて個人チャットへ引き渡される。独立した「保護者ポータル」画面は設けない。

### スコープ

対象（要件定義書「対象範囲」(2-2) より）:

- 日誌の作成・編集・承認フロー、過去の日誌の検索・閲覧
- 園児マスターの管理（園児情報の登録・編集、クラス紐づけ、保護者との紐づけ）
- 職員・保護者アカウントの発行と管理
- 職員・保護者間のチャットによる情報共有、保護者への記録・お知らせの共有
- 午睡（昼寝）中の安全管理と記録支援
- 0〜5歳児の発達状況の記録・蓄積・比較（身体測定を含む）

対象外:

- 自治体が実施する法定健診（乳幼児健診）の代替
- 医療的診断・発達障害の判定・療育要否の判断
- 登降園管理、請求・決済、入退園管理（本演習の開発範囲に含めない。今後の検討対象）
- 給食管理機能そのもの（アレルギー情報の記録と参照までを本システムが担う）

## 設計原則

要件定義書「このシステムの設計原則」(0-3) より。全機能に共通し、個別の要件より優先する。

1. **システムは判断をしない** — 発達の遅速判定・医療的診断・療育要否・発育の良否・発熱・ヒヤリハット該当の判定を一切行わない。評価と判断の責任は常に保育士・園にあり、システムは記録・可視化・気づきの支援に徹する
2. **ハードコードを避ける** — チェック頻度・しきい値・通知間隔・共有の既定値は、園が変更できるマスタデータとする
3. **個別の事情に手動で合わせられる** — システムが提示する推奨は上書きでき、園児単位の手動設定を必ず用意する
4. **到達保証のない経路に緊急連絡を載せない** — 通知は画面内表示が基本であり、届かないことがある。緊急連絡は電話、園内は口頭連絡が担保

UI設計方針（基本設計書より）:

- **認知負荷の低減**: 説明書なしで直感的に操作できること。タイマーなど重要情報は常に視認可能な位置に固定する
- **デバイス別レイアウト**: 職員（管理者・一般）はタブレット／PCで12カラムグリッド、保護者はスマートフォンで片手操作前提のシングルカラム
- **配色ルール**: ベースカラーは「優しい黄色」。SIDS関連アラート等の重要通知には補色の「警告赤」を使用し視認性を確保する
- **権限チェックはサーバー側で行う**（画面側の出し分けだけに頼らない。モックアップで確認済み）

## 機能構成

全機能が共有する**共通基盤**と、その上に載る**4つの機能**で構成する。

### 共通基盤

- **アプリのログイン／ログアウト** — 保護者用と職員用で入口（URL・画面）を分ける。未ログインで表示するのは認証の導線のみ
- **アカウントの管理** — 職員アカウントは管理者が発行、保護者アカウントは**招待コードによる自己登録**（1枚＝1アカウント）
- **園児マスターの管理** — 登録・編集はここに一本化し、各機能は参照のみを行う
- **全機能に共通する扱い** — 通知、操作ログの参照、同時編集、端末の利用形態と本人特定
- **参照範囲の全体規定** — 管理者＝全クラス、一般＝自クラス、保護者＝自児

権限は**管理者（園長・主任）／一般（保育士）／保護者**の3ロール。ロールはアカウントに固定して付与し、同一人物が切り替えることはない。

### 4つの機能

1. **日誌システム** — 下書き・作成 → 申請 → 承認／差し戻し → 保管・共有。テンプレート選択、定型文（スタンプ・タグ）、写真添付、ステータス管理、絞り込み検索、PDF出力、ヒヤリハットの記録
2. **チャットツール** — 園チャット／グループチャット（クラス・目的別）／個人チャット／職員チャットのチャンネル別権限のもと、メッセージの送受信・編集・送信取消・削除、既読確認、未対応スレッドの管理、誤送信への対応の記録
3. **午睡チェック** — 年齢別間隔のタイマー・アラーム、体の向き（体位）・体調の記録、異常時の記録、クラス全体の午睡状況の確認、自動帳票出力、検索・履歴閲覧
4. **発達チェック（身体測定を含む）** — 月齢別チェックリスト、推奨スケジュールの提示と手動上書き、身体測定・成長グラフ、保護者への共有（個人チャット経由）

## 技術スタック

本プロジェクトは**現在 Python / Flask のモックアップで動いており、これを Go + TypeScript/React へ移行する予定**です。要件定義書「開発環境」(5) が定めるのは移行先の構成であり、リポジトリの実物とはまだ一致していません。

| 種別 | 現在（`mockup` ブランチで動作中） | 移行先（要件定義書が定める構成） |
| --- | --- | --- |
| バックエンド | Python / Flask | [Go](https://go.dev/) |
| フロントエンド | 素の HTML・CSS・JavaScript（`static/`） | [TypeScript](https://www.typescriptlang.org/) & [React](https://react.dev/) |
| DB | SQLite 3（`hoiku.db` を初回起動時に自動生成） | SQLite 3（演習）。運用時はサーバ用DBMS（PostgreSQL等）へ移行する |
| 認証 | サーバ側セッション、パスワードのハッシュ化 | 同左（ただし分離構成に合わせた方式へ変えるかは要決定） |
| 依存管理 | `requirements.txt` | バックエンド＝`go.mod`、フロントエンド＝`package.json` |
| 配信 | Flask が静的ファイルも配信 | 前段にリバースプロキシ（Nginx等）を置き、Reactのビルド成果物を配信する |
| 通信 | `http://localhost:5000` | HTTPS（TLS）公開必須 |

**移行にあたっての未決事項**（要件定義書「残る要決定事項」(10) より）

- **Go + React への移行の完了時期**。移行が済むまで、テスト仕様書に基づく検証は現行の Flask モックアップ上で行う
- **認証情報の保持方式**。バックエンドとフロントエンドが分離するため、サーバ側セッションを維持するかの判断が要る
- **インタフェースの具体的な設計をどこまで基本設計で定めるか**

### セットアップ

```powershell
git checkout mockup
cd hoiku_app
pip install -r requirements.txt
python app.py
```

起動後、ブラウザで `http://localhost:5000` にアクセス。テストは `hoiku_app/` で `pytest` を実行する。
