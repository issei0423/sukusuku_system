# すくすくシステム（すくすくハイブ）

保育支援システム。保護者という「点」と保育士という「点」を、育児という「線」でつなぐ、園児管理を兼ねたコミュニケーションツール。
チーム開発演習（Hive-Five Developers）の成果物。

> **この README は案内と要約です。** 要件は `要件定義書.md`、設計は `基本設計書.md` が正で、食い違ったらそちらに従ってください（どれが正かは下の「正とする文書」）。版は各文書の冒頭の表にあります。この README には版・画面数・表の数を書き写しません。
>
> **アプリの正は、Oracle Cloud（OCI）の VM に公開している Web アプリです**（下の「いま動いているもの」）。`localhost` で立てて使う・運用する方式はありません。旧 Flask 版（`mockup` ブランチの `hoiku_app/`、Python）は 2026-11-06 に消しました（GitHub PR #396）。理由は `ナレッジ/決定事項.md` 2026-11-06。

### 対象範囲

対象（要件定義書「対象範囲」(2-2)）：連絡帳、チャットによる会話と園からの配布物、保護者向けの成長の記録、午睡中の安全管理と記録、発達・身体測定の記録、保育日誌の作成と承認、園児マスターの管理、職員・保護者アカウントの管理、開いている画面への即時の反映、外部の AI による文の下書き（園が有効にしたときだけ）。

対象外：法定健診の代替、医療的診断・発達の判定、**登降園管理・出欠の記録、請求・決済、シフト管理、写真の販売**、入退園の手続きの管理、給食管理そのもの、センサーなど機器による見守り、メール・SMS・LINE での送信、ネイティブアプリ。

## 設計原則

要件定義書「このシステムの設計原則」(0-3) より。全機能に共通し、個別の要件より優先する。

1. **システムは判断をしない** — 発達の遅速・医療的診断・療育要否・発育の良否・発熱・ヒヤリハット該当の判定を一切行わない。システムは記録・可視化・気づきの支援に徹する
2. **ハードコードを避ける** — チェック頻度・しきい値・通知間隔・共有の既定値は、園が変更できるマスタデータとする
3. **個別の事情に手動で合わせられる** — システムが提示する推奨は上書きでき、園児単位の手動設定を必ず用意する
4. **到達保証のない経路に緊急連絡を載せない** — 通知は届かないことがある。緊急連絡は電話（保護者の画面には常に「緊急のご連絡はお電話でお願いします」と園の電話番号を出す）
5. **保護者に届くことを既定にする** — 子どものようすは、記録した時点で保護者に届くことを既定とする。届けない側に倒すときは理由を書く

## 機能構成

**共通基盤**と、その上に載る**5つの機能**で構成する（要件定義書「機能要件」(4)、基本設計書「システムと業務の関係」(2-1)）。保護者に届くかどうかは「保護者へ届けるときの関所」（4つの段）で決まる（基本設計書「保護者へ届けるときの関所」(2-4)）。

| 機能 | できること | 保護者へ届くか |
| :-- | :-- | :-- |
| **連絡帳**（中心の機能） | 園児1人・1日1ページ。朝の「家庭から」（保護者が書く）、日中の「きょうのようす」（午睡・食事・排せつ・体温・活動のひとこと・写真・クラスのようす）、夕方の「園から」（担任のひとこと）。担任が「家庭から」に「確認しました」を返す。届いていない家庭が職員ダッシュボードに出る | **記録した時点で届く**（管理者の事前の承認は置かない） |
| **日誌システム** | 保育日誌（クラス日誌・個人日誌・週案月案・ヒヤリハット）の作成・申請・承認・差し戻し・承認の取り消し、検索。個人日誌の午睡・食事の欄は、きょうのようすから下書きに入る | **園内の記録で、届けない。** 例外は、保育士が申請するときに「保護者へ共有する」を選び、管理者が承認した**個人日誌だけ**（保護者は「園からの日誌」で読む。2026-10-29） |
| **チャットツール** | 園チャット・クラスグループ・目的別グループ・個人チャット・職員チャット。保護者のメッセージへの「確認しました」、お知らせから「この連絡について園にたずねる」、リアクション、編集・取消、誤送信の記録。園だより・献立表などの**園からの配布物**もここから開く | 送った時点で届く。**会話の窓口であって、記録はチャットに流さない**（記録は連絡帳と成長の記録で読む） |
| **午睡チェック** | 実施の開始・終了、年齢別の間隔のタイマー、体位・呼吸・顔色・体温の記録、「ねた」「おきた」「きょうは対象外」、異常時の記録、検索と帳票（CSV。管理者） | 5分ごとなどの確認の記録（監査の層）は届けない。**「ねた・おきた」の時刻は連絡帳で届く**。異常は電話 |
| **発達チェック**（身体測定・成長の記録を含む） | 月齢別のチェックリスト（確認できた／一部／未確認）、推奨スケジュールと手動の上書き、身長・体重と成長グラフ、共有範囲の設定 | 身長・体重と「確認できた」項目、保護者へのひとことが、保護者の**成長の記録**で届く。所見と「一部」「未確認」は届けない |
| **共通基盤** | ログイン（入口は保護者用と職員用の2つ）、アカウント（職員は管理者が発行、保護者は招待コードで自己登録。1枚＝1アカウント）、園児マスター、年度更新、操作ログ、設定、**リアルタイムの反映（SSE）**、文章の下書き（AI） | 届け方そのものを支える |

### 誰が何を使うか

権限は**管理者（園長・主任）／一般（保育士）／保護者**の3つで、アカウントに固定する（基本設計書「システムの利用方法」(2-2)）。見える範囲は、管理者＝全クラス、一般＝自クラス、保護者＝自分の子ども（例外は要件定義書「参照範囲の全体規定」(4-1-5)）。

| 利用者 | 端末 | 入口 | 画面のメニュー（本線 `web/src/layouts/`） |
| :-- | :-- | :-- | :-- |
| 管理者・一般 | タブレット／PC | 職員用トップ（`/staff-top`） | ダッシュボード・日誌・チャット・午睡チェック・連絡帳・発達・身体・園児。管理者にはさらに、承認待ち・職員アカウント・招待コード・保護者アカウント・年度更新・操作ログ・誤送信対応・設定 |
| 保護者 | スマートフォン（ホーム画面に追加して使える） | 保護者用トップ（`/`） | ホーム（園児ごとの「きょう」。そこから連絡帳へ）・園児ごとの成長の記録・チャット・お知らせ（配布物もここから）・園からの日誌・お子さまの追加・パスワードの変更・利用規約。園が AI を有効にしたときだけ「AI の下書きの利用」 |

- 画面の一覧と数は、基本設計書「画面の一覧」(3-2) が持つ（数は同項と `図/画面ID対応表.md` だけが持つ）。画面ごとの項目は `図/画面詳細図.md`、つながりは `図/画面遷移図.md`
- 設計にあって画面にまだ無いものは、`図/画面詳細図.md`「モックアップでは実装しないもの」(12-1) と本線の `web/仮置き値.md` にある。保護者のメニューの「連絡先の変更」「通知の設定」も、まだ画面に無い（本線の `web/src/layouts/GuardianLayout.tsx`。通知の設定は Web Push を作るかの【要決定】しだい）
- 表の数と列は、基本設計書「データベース設計」(5) と `図/ER図.md` が持つ

### 相手の画面への反映

- 開いている画面へは **SSE（Server-Sent Events）** で知らせ、画面が読み直す。チャット・連絡帳・日誌などは、再読み込みしなくても数秒で相手の画面に届く（本線の `server/events.go`・`web/src/live.ts`。`ナレッジ/決定事項.md` 2026-10-15、基本設計書「リアルタイムの反映と通知」(4-10)）
- アプリを開いていない保護者への通知（Web Push）は、まだ無い（上の表）
- 急ぎの連絡は電話（設計原則4）

## 技術スタック

| 種別 | 中身 |
| --- | --- |
| バックエンド | Go（本線の `server/`）。HTTP サーバを内蔵し、ビルドした画面も配る |
| フロントエンド | TypeScript + React（本線の `web/`） |
| DB | SQLite 3（演習）。運用時はサーバ用の DBMS（PostgreSQL 等）へ移す前提（要件定義書「想定運用環境」(6-1)） |
| 認証 | サーバ側のセッション（HttpOnly の Cookie）、パスワードのハッシュ化、CSRF は SameSite=Strict と送信元の検証 |
| 即時の反映 | SSE（サーバ1台が前提） |
| 外部サービス | 文の下書きに Anthropic の Claude Haiku（バックエンドからだけ呼ぶ。園が有効にしたときだけ。公開先には鍵が無い） |
| 公開 | OCI の VM、前段に Caddy（HTTPS）。本線への push で自動で反映 |

業務の規則は、Go サーバとブラウザ内のモック（`web/src/api/mock.ts`）の2か所にある（本線の `AGENTS.md`）。
