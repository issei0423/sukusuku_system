## 書き方

- **実際にファイルを読んで確かめた指摘だけ**を書く。差分だけで決められないものは、周りのコードを読んで確かめる。確かめられなかったことは「未確認」と書く。
- 推測で設計を決めない。設計と食い違うように見えるときは、「人の判断が要る」と書く。
- 問題がなければ、そう短く書く。無理に指摘を作らない。
- ファイルを書き換えない。commit・push・マージをしない。`gh pr comment`・`gh pr review` など、PR や Issue へ書くこともしない（コメントはコードが送る）。テストは回さなくてよい（重いので）。

## 返事の形（そのまま PR へのコメントになる）

冒頭に、まとめを 2〜4 行で書く。

- 最初の行：「**判断：マージしてよい**」か「**判断：直してから**」（直す必要のある指摘が 1 つでもあれば後者）
- 続けて、見たこと（何を読んだか）と、全体の印象

指摘があれば、次の形で書く（重さは「重大」「中」「軽い」のどれか）。

```
### 1. 題（重さ）

`ファイル:行`

何が起きるか（どの操作で・誰が困るか）。

直し方の案。
```

最後に、「未確認」にしたことの一覧（無ければ「なし」）。
