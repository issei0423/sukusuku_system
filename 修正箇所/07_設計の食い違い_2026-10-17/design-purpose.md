## 0 要約

- **保護者がその日の様子を知る道は、実質「管理者が承認して共有を選んだ個人日誌」の1本しかない。** 早くて夕方〜夜、管理者の承認が翌日に回れば翌日以降になる。承認に期限は無く、3日を過ぎて初めて警告の色が付く。
- **午睡は保護者に一切届かない。** 午睡チェックは5〜15分ごとに記録するのに、保護者が見る経路が設計にも実装にも無く、入眠・起床の時刻そのものも持たない。持ち主が名指しした「午睡」が、いちばん届かない。
- 食事・排せつ・きげんのような「きょうどうだったか」も、記録の項目が無く、日誌の自由記述に頼る（同じく承認待ち）。
- 届いたことを知る手段は「アプリを開いたとき」だけ。SSE の決定（2026-10-15）は設計書に入っておらず、本線は開いている間の5秒ごとの読み直し。SSE は worktree の未コミットの変更にあるだけで、午睡の知らせは職員にしか送らない。
- 根には、**コンセプトが設計原則・ねらい・業務の流れのどこにも入っていない**ことがある。安全・監査・誤共有の側には理由つきの決定が積み上がっているのに、「届ける」側には物差しが無いため、迷うたびに「届けない」側へ倒れている。

## 2 項目（重い順）

### 1. 午睡の様子が保護者に届く道が無い（午睡チェックは職員だけの記録で、入眠・起床の時刻も持たない）

| 欄 | 内容 |
| :-- | :-- |
| 種類 | **抜け** |
| 重さ | **高**（持ち主が名指しした「午睡」について、保護者が知る道が設計・実装の両方でふさがっている） |
| 目的の側の引用 | 持ち主：「リアルタイムで午睡とか日誌とかが欲しい」。インタビュー「午睡管理」(4-3)：「寝た時間・起きた時間を打刻で記録したい」「午睡時間の自動集計があると良い」。`システム概要共有.md`：「保護者にとってのメリット…デジタル記録からリアルタイムで把握できる」（同書は記録項目に午睡チェックを挙げている） |
| 設計の側の引用 | 要件定義書「午睡チェック」(4-4)：「本機能は園児の午睡中の安全管理を強化し、保育士の書類作成負担を軽減する睡眠見守り・記録支援機能である」。機能表の対象権限はすべて「一般・管理者」。同「機能間のデータの引き渡し」(4-6-3)：引き渡しは「記録の共有（発達・身体→チャット）」「日誌の共有」「ヒヤリハットの起票（午睡→日誌）」の3つだけ。基本設計書「権限と利用可能機能」(6-1)：「午睡チェックの実施・記録｜保護者 ×」。保護者が閲覧する行は無い。同「午睡チェック」(5-6)：`t_nap_record` は `checked_at / saved_at / body_position / breathing / complexion / temperature`。入眠・起床の列は無い。設定マスタ `nap.temperature_required`＝「入眠時」はあるが、どの記録が入眠時かをデータで表せない（画面詳細図「モックアップ実装との差異」(11-1)「常に任意。入眠時かどうかを見ていない」） |
| なぜ食い違うか | 午睡チェックは**監査用の記録**（5〜15分ごとの体位・呼吸・顔色）として設計され、保護者に伝える**様子**（何時に寝て、何時に起きて、何分寝たか）は、どの機能の責務にもなっていない。監査用の記録をそのまま保護者に見せない判断はありうるが、その判断も理由も文書に無い。結果として、5分ごとに記録している園でも、保護者には何も届かない |
| 実装の状態 | `server/api_nap.go` の全ハンドラ（`handleNapClassState`・`handleSearchNapRecords` ほか）が `requireStaff`。保護者の画面（`/guardian`・`/guardian/chat`・`/guardian/handouts`・`/guardian/diary/:id`）に午睡は出ない。SSE の下書き（`server/events.go`）も、午睡の知らせは `notifyClassStaff`・`notifyChildStaff` で**職員だけ**へ送る。保護者へ伝えるには、個人日誌の雛形の【午睡】欄に手で書き直し、承認を待つ（項目2・6） |

### 2. 「きょうのようす」は、管理者が1件ずつ承認して共有を選ぶまで届かない（連絡帳と保育日誌が1つの「個人日誌」に重なっている）

## 3 目的をよく支えている設計

- **ホームから記録へ1回で届く。** 共有日誌閲覧画面を設け、保護者ホームからもチャットからも入れる（基本設計書「画面体系図」(3-3)「チャットを遡らずに記録へ届く導線を確保する」）。
- **父母・祖父母が同じものを読める。** 個人チャットを園児単位で作り、保護者が何人でも同じ部屋に入る（基本設計書「チャット」(5-5)）。連絡帳を持たない側の親にも届く。
- **きょうだいを並べて見せ、取り違えを防ぐ**（同 (3-3)）。
- **緊急は電話へ切り替える案内を保護者の全画面に置き、番号を押せる**（同「画面基本構成」(3-5)）。届かないかもしれない道に緊急を載せないという線引きは、保護者を守る。
- **職員側で既読と未対応を管理する**（要件定義書 (4-3)）。インタビューの最優先「重要な連絡が保護者に届いたかどうか確認できない」に応える。
- **園だより・献立表を月ごとに見返せる**（「配布物の掲載と閲覧」(4-3)）。
- **保護者向けは24時間の稼働をめざし、計画停止は保護者の主な利用時間帯（平日 19:00〜23:00）を避ける**（要件定義書「性能・可用性」(7-2 No.3)）。
- **発達の共有範囲は「共有する」を既定にし、外す項目を園が選ぶ**（画面詳細図 (6-5)）。届ける側を既定にした数少ない例であり、日誌（項目9）もこの考え方に揃えられる。
- 実装：開いている保護者ホームとチャットは5秒ごとに読み直し、承認・返信が F5 なしで出る（#150）。
