# モックアップの仮置き値

基本設計書・要件定義書で値が確定していない項目について、モックアップで置いた仮の値の一覧。

**この一覧は設計の決定ではない。** モックを動かすために必要だっただけであり、
ここに書いた値が要件定義書・基本設計書へ逆流しないよう、置いた場所と理由を残す。
確定したら `要決定事項.md` の手順（本文へ反映 → 一覧から落とす → `ナレッジ/決定事項.md` に理由を残す）に従う。

## 1 画面の見た目（基本設計書「画面基本構成」(3-5)）

基本設計書はテーマカラーを「優しい黄色」、警告色を「黄色と対比の付く色」とだけ定めている。
具体値は決まっていないため、次の値を置いた。置き場所は `src/styles/tokens.css` の1か所に集約している。

色・文字・余白・角・影は、**デジタル庁デザインシステム（DADS）** の決まりに沿って置いた。
色の値そのものは DADS の色の段階（`@digital-go-jp/design-tokens` v2.0.1、MIT License。表示は `web/THIRD_PARTY_NOTICES.md`）から選んでおり、
**仮置きなのは「どの段階をどの役割に当てたか」** である。

| :-- | :-- | :-- |
| テーマカラー | `#ffc700`（DADS yellow-400） | 優しい黄色。主ボタン・選んだ選択肢の塗り。黄色は白地の文字に使えない（コントラスト 4.5:1 に届かない）ため、塗り・地・枠にだけ使う |

## 2 入力項目の制約値（基本設計書「画面詳細」(3-6) が【要決定】としている）

| 項目 | 仮置き値 | 置いた場所 |
| :-- | :-- | :-- |
| パスワードの桁数 | **仮置きではなくなった。** 基本設計書「入力項目の制約値」(4-9) のとおり 8〜128 文字、文字種の制約なし。文字数（符号位置の数）で数える（GitHub Issue #159） | `server/password.go`・`api/util.ts` の `validateNewPassword` |
| よく使われるパスワードの一覧 | 基本設計書「パスワードの要件」(6-3) は「password などは拒否する」とだけ定め、一覧を定めていない。漏えいしたパスワードの一覧から、8文字以上で上位に来る 25 個を置いた。大文字・小文字を区別せずに照らす | `server/password.go` の `commonPasswords`・`api/util.ts` の `COMMON_PASSWORDS`（同じ一覧） |
| CSV一括登録の平熱の書き方 | 小数第1位までの数（`36`・`36.5`）に限る。`inf`・`NaN`・`1e2`・`0x24`・符号付き・全角は誤り。整数部は3桁まで。範囲（30.0〜43.0℃）の外は設計どおり誤りにせず確認を促すため、打ち間違い（`365` など）は通して確認を促し、4桁以上は書き方の誤りとして止める（GitHub Issue #160） | `server/api_bulk.go` の `temperatureRe`・`api/mock.ts` の `TEMPERATURE_FORMAT` |
| CSV一括登録の見出し | 1行目に「園児ID」を含むときは見出しとみなし、並びが様式（園児ID,氏名,氏名かな,生年月日,性別,クラス名,平熱）と違えば、行を読まずにファイルごと断る。平熱の列は省いてよい。先頭の BOM は読み飛ばす（GitHub Issue #160） | `server/api_bulk.go` の `checkCsvHeader`・`api/mock.ts` の `isCsvHeader` |
| 招待コードの入力形式 | **仮置きではなくなった。** 基本設計書「招待コード（t_invitation_code）」(5-2) のとおり、大文字・小文字を区別せず、ハイフンは入力しても省略してもよい | `api/util.ts`・`server/api_auth.go` の `normalizeInvitationCode` |
| 新規登録のメールアドレスの重複 | 大文字・小文字だけが違うものも、すでにあるものとして断る（同じ宛先に届くため。基本設計書 5-2「ロールをまたいで園内で一意」）。保存は入力どおりの書き方のままで、ログインの照合も入力どおり（大文字・小文字を区別する）。判定は職員アカウントの発行と同じ `emailTaken` を使う（下の「ログインIDの重複の判定」。GitHub Issue #170・#167） | `server/api_auth.go` の `handleSignUpGuardian`、`api/mock.ts` の `signUpGuardian` |
| 新規登録の保護者の氏名 | 前後の空白を落としてから 50 文字以内（基本設計書 4-9）を数え、落としたものを保存する（GitHub Issue #170） | 同上、`SignUpScreen.tsx` |
| 氏名・本文などの桁数 | 制約なし | 未実装 |

招待コードに紛れ込んだ空白を取り除く扱いだけは、設計に定めが無く、モックで足したものである。

### 日誌の編集ロックの動き（基本設計書「編集ロックの解除」(4-5) が定めていない部分）

基本設計書は「保存時のロック識別子が、現在有効なロックと一致するかを照合する」「解除された編集者の保存は拒否する」
「無操作の経過で自動で解除する」までを定めている。ロックの無い保存も断る（GitHub Issue #166）。
次は、そのうえで動かすために置いた扱いである。

| 項目 | 仮置き | 置いた場所 |
| :-- | :-- | :-- |
| 無操作の時間を過ぎたロック | 行を消さずに残し、**ほかの職員が取りにきた時点で解除する**。それまでは、持っていた本人の識別子を有効とみなし、保存と操作の知らせを通す（ほかの誰も保存できないため、上書きは起きない）。ほかの職員が取ると識別子が替わり、元の編集者の保存は断る | `server/api_diary_write.go` の `holdsDiaryLock`、`api/mock.ts` の `heldDiaryLock` |
| 保存したときのロック | 申請したら外す（申請中の日誌は編集できない）。下書き保存は外さず、最終操作時刻を進める。保存のあとも編集画面に残って書き続けるため | `server/api_diary_write.go` の `updateDiary`、`api/mock.ts` の `saveDiary` |
| 確認画面へ進むとき | ロックを外さずに日誌確認画面へ引き継ぐ。確認画面は、申請する（サーバが外す）か、画面を離れる・タブを閉じるときに外す。「戻る」で編集画面へ返すときは外さず、編集画面が取り直す。確認画面へ移るときに外すと、確認画面にいる間にほかの職員が開いて直せ、申請がその直しを黙って上書きする | `screens/diary/diaryLock.ts`・`DiaryEditScreen.tsx`・`DiaryConfirmScreen.tsx` |
| 本人の解除 | 取得のときに受け取った識別子を添えて送り、一致するときだけ外す。識別子を添えない解除では外さない。同じ職員が取り直したあと（確認画面から戻る、開発時に画面を 2 回描く）に古い識別子の解除が届いても、取り直したロックを外さないため。管理者の強制解除は識別子を問わない | `server/api_diary_write.go` の `handleReleaseLock`、`api/mock.ts` の `releaseLock` |

### 一覧の並び順（設計が定めていない部分。GitHub Issue #177 の 7）

図/画面詳細図.md は、承認待ち一覧（申請の古い順）・配布物（対象の月の新しい順）などのほかは、一覧の並び順を定めていない。
Go サーバとモックで並びが食い違っていたため、次のとおりにそろえた。

| 一覧 | 仮置きの並び | 置いた場所 |
| :-- | :-- | :-- |
| アレルギー一覧 | 園児のよみ順。園児一覧・発達チェック一覧と同じ | `server/api_child.go` の `handleAllAllergies`、`api/mock.ts` の `allAllergies` |
| 異常時の記録 | 発見時刻の新しい順。同じ時刻は、あとで記録したもの（記録の番号の大きいもの）を先にする | `server/api_nap.go` の `handleNapAbnormals`、`api/mock.ts` の `abnormals` |
| スケジュール設定 | 園児のよみ順。発達チェック一覧と同じ | `server/api_dev.go` の `handleDevelopmentSchedules`、`api/mock.ts` の `schedules` |
| 招待コード | 園児のよみ順にまとめ（よみが同じなら園児IDの順）、同じ園児の中は発行の古い順（コードの番号の小さい順）。画面は返した順に園児ごとにまとめる（図/画面詳細図.md「招待コード管理画面」(7-7)「同じ園児の複数枚をまとめて見られる」） | `server/api_admin.go` の `handleInvitationCodes`、`api/mock.ts` の `invitationCodes` |
| 誤送信対応の「対応を記録していない取消メッセージ」 | 送信の新しい順。同じ時刻は、あとで送ったもの（メッセージの番号の大きいもの）を先にする | `server/api_chat.go` の `handleRetractedWithoutRecord`、`api/mock.ts` の `retractedWithoutRecord` |

**よみの比べ方は、まだそろっていない。** Go は SQLite の `ORDER BY child_name_kana`（文字コードの順）、モックは
`localeCompare(…, 'ja')`（日本語の照合の順）で比べる。濁点・半濁点・小さい文字・長音の扱いが違うため、
たとえば「はし」と「ばあ」は、Go では「はし」が、モックでは「ばあ」が先になる。デモデータの園児では同じ並びになる。
上の表の一覧だけでなく、もとからよみ順で並べている一覧（園児一覧・発達チェック一覧・午睡チェックのクラスの園児など）も同じである。
どちらの比べ方にそろえるかは決めていない（GitHub Issue #177 の 7 の PR のレビューで指摘）。

## 5 成長曲線の基準値（`m_growth_standard`）

**仮の値ではなくなった**（GitHub Issue #69）。厚生労働省「平成22年乳幼児身体発育調査」の表1（体重）・
表2（身長）の公表値を入れてある。値は `server/growth_standard_2010.go` と `web/src/api/growthStandard2010.ts` が持つ

残っている仮置きと、注意すること：

| 項目 | 扱い | 理由 |
| :-- | :-- | :-- |
| 数値の確かめ | 公表資料の PDF から機械的に読み取り、各行のパーセンタイルが昇順であること・月齢とともに増えることを確かめた。**人の目による公表資料との突き合わせは済んでいない** | 手で転記すると写し誤りが入るため、機械で読んだ。`web/tests/decisions.test.ts` に、目で見て打った行（出生時・1〜3か月・11か月・12か月・23か月）との照合がある |
| 満月齢0か月 | **出生時の値**を当てる | 公表値は「出生時」「30日」「1～2月未満」…で、0～1か月の階級が無い。30日と、体重の1〜5日の行は使っていない |
| 満月齢1〜23か月 | 「N～N+1月未満」の値を、満月齢 N か月に**そのまま**当てる | 満月齢 N の園児は、この階級に入る |
| 満月齢24〜72か月 | 6か月ごとの階級の中央を代表点とし、前後の代表点から**直線で補間**する | 2歳以上は6か月ごとの値しか公表されていない。公表されている曲線は滑らかにつないだもので、直線の補間とは一致しない |
| 身長の測り方 | 公表値のとおり、2歳未満は仰臥位、2歳以上は立位の値 | 画面の帯は、23か月と24か月のあいだで測り方が変わる |
| すでにあるデータベース | 起動時に、仮の値が残っていれば公表値へ入れ替える（`server/db.go` の `upgradeGrowthStandards`） | 基準値はマスタであり、利用者の記録ではない |

| セッションを切るとき | パスワードの変更（変更した端末以外。基本設計書 6-3 が定めたもの）に加え、アカウントの停止・紐づけの解除・一時パスワードの再発行のときに、そのアカウントのセッションをすべて切る。紐づけの解除は、きょうだいの紐づけが残る保護者も切る（ログインし直せば残る園児の範囲で使える）。管理者が自分の一時パスワードを再発行したときは、操作した端末だけを残す。あわせて、要求のたびにアカウントの状態を読み、停止中なら通さない（GitHub Issue #159） | `server/session.go` の `destroyAccount`・`requireLogin`、`server/api_admin.go`・`server/api_auth.go` |
| ログイン中の新しいログイン・新規登録への応答 | 409 と `kind: already_logged_in`、「すでにログインしています。別のアカウントでログインするには、先にログアウトしてください」。ログイン中の氏名・ロールは出さない。入口（`entrance`）が職員用・保護者用のどちらでもない要求は 400（GitHub Issue #159） | `server/api_auth.go` の `writeAlreadyLoggedIn` |
| セッションが切れたときの画面 | ログインしていた系統のトップへ戻し、「ログインの状態が切れました。もう一度ログインしてください。」と出す。理由（停止・解除など）は出さない | `App.tsx`・`TopScreen.tsx`、`api/procedure.ts` の `onSessionEnded` |
| 72 バイトを超えるパスワード | bcrypt は 72 バイトまでしか扱えないため、72 バイトを超えるものは SHA-256 の要約（base64、接頭辞 `sha256:`）にしてから bcrypt へ渡す。72 バイト以下はそのまま渡すので、保存済みのハッシュはそのまま照合できる（GitHub Issue #159） | `server/password.go` の `bcryptInput` |
| 新規登録で受け取る規約への同意 | 画面は「利用規約に同意します」を入れたときに出していた規約の版を持ち、登録のときに `terms_agreed: true` と `terms_version` を送る。サーバは、同意が無ければ「利用規約に同意いただけない場合、ご利用いただけません。」（メッセージ一覧 4-9）で断り、版がいま有効な版と違えば「利用規約が改定されました。改定後の利用規約をお読みいただき、あらためて同意してください。」で断る（後者の文言が仮置き）。断られた画面は、いまの版を読み直し、版が変わっていれば同意を外して改定後の本文を出す。本文を読み込めるまで同意のチェックは入れられない（GitHub Issue #170） | `server/api_auth.go` の `handleSignUpGuardian`、`api/mock.ts` の `signUpGuardian`、`SignUpScreen.tsx` |
| ログアウトの前に確かめる「保存していない入力」 | 保護者の画面では、チャットの書きかけのメッセージ（空白だけは含めない。書きかけはチャンネルごとに持つので、いま開いていないチャンネルの書きかけも含める。GitHub Issue #172）・保存していないメッセージの編集・パスワード変更画面の入力。あれば「保存していない入力があります」と出し、「破棄してログアウトする」か「やめる」を選ばせる。基本設計書「ログアウト」(4-3) は確認することだけを定め、何を入力とみなすか・文言を定めていない。**職員側のログアウト（`StaffLayout.tsx`）にはまだ付けていない**（GitHub Issue #170） | `src/unsavedInput.tsx`、`GuardianLayout.tsx`・`GuardianChatScreen.tsx`・`PasswordChangeScreen.tsx` |

## 7 実装していないもの

要件・設計にはあるが、本モックアップの範囲外としたもの。

| 項目 | 理由 |
| :-- | :-- |
| 自動ログアウト | 無操作時間の計測を未実装。セッションの有効期限だけを持つ |
| 添付ファイルの実体 | ファイル名だけを持ち、保存も表示もしない。日誌の写真は、名前と形式を日誌と一緒に `t_diary_attachment` へ書く（実体は無い。GitHub Issue #175。上の「日誌作成・編集画面の動き」） |
| 配布物のファイルの実体 | 名前・形式・大きさだけを持ち、保存も表示もしない。開いても中身は出ない（題名・種類・対象の月・ファイルの名前と大きさを示す） |
| PDF出力 | 操作ログへの記録のみ行い、ファイルは生成しない |
| 通知（Web Push） | 演習範囲外（要件定義書） |
| 年度更新の実行 | 進級先の割り当てと卒園の処理を実装していない。現在の年度の内訳の表示までとした。処理の内容は基本設計書「年度更新」(4-4) が定めている |
| ログインの成功の記録 | 操作ログへ残さない。**失敗と、失敗が続いたことによるロックは残す**（GitHub Issue #115 で決めた）。存在しないログインIDへの試行は、残す先のアカウントが無いため残らない。操作者の欄には、試されたアカウントを入れている（本人とは限らない） |
| 引き継ぎ猶予期間の判定 | 未実装 |
| 記録の保持年数にもとづく削除 | 未実装 |
| 定型文の編集 | 定型文を保持するテーブルが基本設計書「日誌」(5-4) に無いため、サーバ側の定数で持っている |

## 8 業務の規則を2か所に持っていること

参照範囲の判定・承認の可否・入力の検証といった規則は、次の2か所にある。

- `server/`（Go サーバ）… 実運用の判定。**権限の担保はこちら**
- `web/src/api/mock.ts`（ブラウザ内のモック）… サーバを立てずに動かすときと、テストの対象

**片方だけを直すと食い違う。** 規則を変えるときは必ず両方を直すこと。
食い違いを検出するために、`web/tests/integration.test.ts` が実サーバに対して
同じ観点（参照範囲・権限の拒否・設定値）を確かめている。
