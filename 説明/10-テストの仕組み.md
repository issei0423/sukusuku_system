## この文書で分かること

- このリポジトリにあるテストの種類と、それぞれの置き場所・相手・時計・回し方。
- 各種類の代表のテストを1〜2個。どう書くか、何を確かめるかをコードで見せる。
- GitHub の CI（`.github/workflows/ci.yml`・`deployed-smoke.yml`）と手元の CI が、どれを回すか。

コードを直す前に、まずここを読む。業務の規則は Go サーバとモックの2か所にあるので、規則を変えたら Go のテスト（`server/*_test.go`）とモックのテスト（`web/tests/`）の両方を足す（AGENTS.md「いちばん大事な決まり」）。テストで気をつけることの全文は [AGENTS.md の「テストで気をつけること」](../AGENTS.md#テストで気をつけること) にある。この文書の最後に要点だけを並べる。

## どこで回るか

```
              手元（npm test / go test）          PR・本線への push             本番へ反映したあと・毎朝
              ─────────────────────────          ─────────────────            ────────────────────
Go のテスト    ○                                  ci.yml server               ―
vitest         ○                                  ci.yml web                  ―
結合テスト     ○（サーバを立てて）                 ci.yml 結合                 ―
a11y           ○                                  ci.yml a11y                 ―
セキュリティ   ○                                  ci.yml security             ―
受け入れ       ○（重い。README の鍵を通す）        ―                           ―
レスポンシブ   ○                                  （型検査だけ）               ―
公開先         ○（公開先へ向く）                   ―                           deployed-smoke.yml
```

- GitHub Actions が課金の都合で止まっているあいだ（2026-10-21〜）は、`ci.yml` が走らない。手元の [local-ci.sh](../agent-harness/api-agent/scripts/local-ci.sh) が、Go のテスト・web の型検査とビルドと lint と vitest・結合・security・a11y を順に回す。結果は `<ログの置き場>/result.txt` に1行ずつ出る（AGENTS.md「GitHub Actions が止まっているあいだ」）。
- 本番へ反映する `deploy-oci.yml`（本番の VM の上で動く）は、`go vet` とビルドは回すが、`go test` は回さない（[.github/workflows/deploy-oci.yml](../.github/workflows/deploy-oci.yml) 45〜51行のコメント。VM が遅く、1回の反映が約25分かかったため）。AGENTS.md の「GitHub Actions が止まっているあいだ」には「go vet・go test は回す」とあり、この版のワークフローと食い違っている。

## コードを読む

**Go のテスト**

### 1. テストの土台：一時フォルダの DB とログイン済みの Cookie（server/api_dashboard_test.go 21〜64行）

```go
// newTestApp は、デモデータ入りのデータベースを一時フォルダに作ってサーバを組み立てる。
// 作業ツリーにある sukusuku.db には触らない
func newTestApp(t *testing.T) (*app, http.Handler) {
	t.Helper()
	db, err := openDB(filepath.Join(t.TempDir(), "test.db"))
	if err != nil {
		t.Fatal(err)
	}
	t.Cleanup(func() { db.Close() })
	a := &app{db: db, sessions: newSessionStore()}
	if err := a.init(); err != nil {
		t.Fatal(err)
	}
	mux := http.NewServeMux()
	a.routes(mux)
	return a, mux
}

// loginAs は、ログインの手順を飛ばしてセッションを作り、その Cookie を返す
func loginAs(a *app, accountID int64, entrance string) *http.Cookie {
	id := randomToken(16)
	a.sessions.mu.Lock()
	// 職員の入口なら、ログインと同じく自動ログアウトを課す（session.go の idleLogout）。ログインした時刻を最後の操作とする
	at := a.sessions.now()
	a.sessions.data[id] = session{accountID: accountID, entrance: entrance,
		expiresAt: at.Add(time.Hour), idleLogout: entrance == "staff", lastActiveAt: at}
	a.sessions.mu.Unlock()
	return &http.Cookie{Name: sessionCookie, Value: id}
}

func call(t *testing.T, h http.Handler, c *http.Cookie, method, path, body string) *httptest.ResponseRecorder {
	t.Helper()
	req := httptest.NewRequest(method, path, strings.NewReader(body))
	if body != "" {
		req.Header.Set("Content-Type", "application/json")
	}
	req.AddCookie(c)
	rec := httptest.NewRecorder()
	h.ServeHTTP(rec, req)
	if rec.Code != http.StatusOK {
		t.Fatalf("%s %s: %d %s", method, path, rec.Code, rec.Body.String())
	}
	return rec
}
```

**解説**
- `newTestApp` は、テストごとに一時フォルダ（`t.TempDir()`）へ DB を作り、デモデータを入れてサーバを組み立てる。作業ツリーの `server/sukusuku.db` には触らない。テストが終われば一時フォルダごと消える。
- 組み立てたサーバは `http.Handler`（要求を受けて応答を返すもの）として返す。ネットワークのポートは開かない。`httptest.NewRequest` で作った要求を `ServeHTTP` に直に渡す。
- `loginAs` は、ログインの手順を飛ばしてセッションを作り、その Cookie を返す。アカウントの番号はデモデータ（`server/seed.sql`）のものである。テストのコメントに「さくら組の担任」のように誰かを書いておく。
- `call` は、要求を投げて、200 でなければその場でテストを止める。200 以外を確かめたいときは `request` と `expectStatus`（[server/api_scope_test.go](../server/api_scope_test.go) 27行・40行）を使う。
- Go のテストは本物の時計で動く。デモデータは起動した日へ日付をずらして入る（`server/seed_shift.go`）ので、「今日の 07:40」の記録は、夜中に回すと未来になる。

### 2. 一覧の末尾でなく本文で探す（server/api_dashboard_test.go 149〜184行）

```go
func TestChatMessagesReadCount(t *testing.T) {
	a, h := newTestApp(t)
	teacher := loginAs(a, 3, "staff")
	guardian := loginAs(a, 6, "guardian")

	const sent = "お大事になさってください。"
	call(t, h, teacher, "POST", "/api/chat/rooms/6/messages", `{"body":"`+sent+`"}`)
	// 一覧の末尾ではなく本文で探す。デモデータには今日の 07:40 のメッセージがあり、
	// それより前の時刻に走らせると、送ったメッセージが末尾に並ばないため
	readCountOfSent := func(c *http.Cookie) int {
		var list []map[string]any
		if err := json.Unmarshal(call(t, h, c, "GET", "/api/chat/rooms/6/messages", "").Body.Bytes(), &list); err != nil {
			t.Fatal(err)
		}
		for _, m := range list {
			if m["body"] == sent {
				n, _ := m["read_count"].(float64)
				return int(n)
			}
		}
		t.Fatalf("送ったメッセージが一覧にない")
		return 0
	}

	if n := readCountOfSent(teacher); n != 0 {
		t.Fatalf("送った直後: read_count = %d, want 0", n)
	}
	call(t, h, guardian, "POST", "/api/chat/rooms/6/read", "")
	if n := readCountOfSent(teacher); n != 1 {
		t.Fatalf("保護者が読んだあと: read_count = %d, want 1", n)
	}
	// 保護者には既読の人数を見せない（0 のまま返る）
	if n := readCountOfSent(guardian); n != 0 {
		t.Fatalf("保護者への応答に既読の人数が入っている: %d", n)
	}
}
```

**解説**
- 職員が送ったメッセージの既読の人数が、保護者が読むと 1 になり、保護者への応答には出ないことを確かめる（147〜148行のコメント）。
- 送ったメッセージを、一覧の末尾ではなく本文（`sent`）で探す（156〜157行のコメント）。デモデータには今日の 07:40 のメッセージがあり、それより前の時刻に回すと、送ったメッセージが末尾に並ばないからである。
- これが AGENTS.md の「一覧の末尾や件数を決め打ちせず、本文や ID で探す」の見本である。決まった時間帯にだけ落ちるテストは、まず時刻を疑う。
- 2人の利用者（職員と保護者）の Cookie を持ち替えて、同じサーバに要求を投げる。役割ごとに応答が違うことを、1つのテストで確かめられる。

### 5. 時計を 18:00 で止める（web/tests/setup-clock.ts 25〜38行）

```ts
import { vi } from 'vitest';

const JST_OFFSET_MS = 9 * 60 * 60 * 1000;
const clock = process.env.SUKUSUKU_TEST_CLOCK || '18:00';
const hm = /^(\d{2}):(\d{2})$/.exec(clock);
if (!hm) throw new Error(`SUKUSUKU_TEST_CLOCK は HH:MM の形で渡す（受け取った値：${clock}）`);

// 日本時間の今日の日付は、本物の時計から取る
const jstToday = new Date(Date.now() + JST_OFFSET_MS);
const start = Date.UTC(
  jstToday.getUTCFullYear(), jstToday.getUTCMonth(), jstToday.getUTCDate(), Number(hm[1]), Number(hm[2]),
) - JST_OFFSET_MS;

vi.useFakeTimers({ toFake: ['Date'], now: start });
```

**解説**
- vitest は、テストのファイルを読む前にこのファイルを読む（[web/vitest.config.ts](../web/vitest.config.ts) 15行の `setupFiles`）。
- 日付は本物の今日（日本時間）のまま、時刻だけを 18:00 にする。デモデータの「今日」の出来事は 17:20 までに置いてあり、18:00 ならすべて済んでいるからである（GitHub Issue #152）。
- 偽物にするのは `Date` だけである（`toFake: ['Date']`）。`setTimeout` などは本物のまま動く。時計は進まないので、時間の経過が要るテストは `vi.advanceTimersByTime(ミリ秒)` で進める。
- 時刻に頼っていないかを確かめるときは、`SUKUSUKU_TEST_CLOCK=03:00 npx vitest run` のように時刻を変えて回す（28行）。
- 自分で時計を扱うテストには、この固定が効かない。`screens.test.tsx` は 13:30 に置き直し、`autoRefresh.test.tsx` は `Date` が本物に戻り、`integration.test.ts` は本物の時計に戻す（16〜20行のコメント）。

## テストを書くときに気をつけること（AGENTS.md の要点）

全文は [AGENTS.md の「テストで気をつけること」](../AGENTS.md#テストで気をつけること) にある。ここでは要点だけを並べる。

- **vitest の時計は日本時間の今日の 18:00 で止まっている。** 時計は進まないので、経過が要るなら `vi.advanceTimersByTime` で進める。時刻に頼っていないかは `SUKUSUKU_TEST_CLOCK=03:00` で確かめる（5.）。
- **Go のテストと結合テストは本物の時計で動く。** 夜中は「今日の 07:40」が未来になる。一覧の末尾や件数を決め打ちせず、本文や ID で探す（2.）。
- **CI は UTC で回る。** 手元で同じ条件を見るには `TZ=UTC` を付ける。
- **画面を描くテストは、1行目に `// @vitest-environment jsdom`。**（6.）
- **`mockDb` は同じファイルのテストどうしで使い回される。** 前のテストの書き込みや件数を当てにしない（4.）。
- **落ちたテストを、期待値の書き換えで通さない。** 規則が変わったのか、不具合なのかを先に確かめる。
- **規則を変えたら、Go とモックの両方にテストを足す。** 同じ観点で書き、頭のコメントにもう片方の場所を書く（3. と 4.）。

## ここで取り上げなかったところ

- レスポンシブレビューの中身（[web/tests/responsive/README.md](../web/tests/responsive/README.md)、`review.spec.ts`・`audit.ts`）。
- セキュリティのハーネスが GLM（OpenCode のモデル）に所見を聞く工程（[web/tests/security/README.md](../web/tests/security/README.md)）。CI では飛ばし、合否に響かせない。
- 受け入れテストのケースの並びを確かめる `npm run test:acceptance:check`（`check-cases.mjs`）と、結果の `results.json` の形。
- 画面に出す文言の見張り（`visibleWording.test.ts`）と、本番のビルドにモックを入れない見張り（`keepMockOutOfBuild.test.ts`）の中身。
