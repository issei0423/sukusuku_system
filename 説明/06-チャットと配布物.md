# 06 チャットと配布物

> この説明は commit 74f09acf のコードで書いた。行番号はその版のもの。

## この機能でできること

- 職員（タブレット・PC）と保護者（スマートフォン）が、チャンネル（話す場）ごとにメッセージをやりとりする。
- チャンネルは5種類ある。園全体・職員・クラス・目的別グループ・個人チャット（園と1家庭のやりとり）。だれが入るかは、ほとんどがアカウント・ロール・担任の割り当てから自動で決まる。
- 職員が保護者の参加するチャンネルへ送るときは、送る前に「ほかの子の名前が入っていないか」をサーバが照合し、当たれば注意を出す。
- 送ったメッセージは取り消せる。管理者は誤送信への対応として、ほかの人のメッセージも削除できる。その後、誤送信対応記録画面で「既読だったか」「とった対応」を残す。
- 園だより・献立表などの配布物は、管理者が配布物管理画面で掲載・取り下げする。掲載すると、チャットに知らせが流れる。保護者は「園からの配布物」で月ごとに見返す。

## チャンネルの種類とだれが入るか

`m_chat_room.room_type` のコード値は [web/src/api/codes.ts](../web/src/api/codes.ts) 32〜36行にある。職員の参加の規則は [server/chat_membership.go](../server/chat_membership.go) の頭（8〜33行）の表にまとまっている。

| `room_type` | 名前 | 入る職員 | 入る保護者 | 投稿できる人 |
| :-- | :-- | :-- | :-- | :-- |
| 1 | 園全体（保護者の画面では「園からのお知らせ」） | 有効な全職員 | 登録した保護者 | 管理者だけ |
| 5 | 職員 | 有効な全職員 | 入らない | 参加している職員 |
| 2 | クラス（クラスグループ） | そのクラスの当年度の担任と管理者 | 子がいま在籍するクラスの保護者 | 参加している職員 |
| 4 | 個人（保護者の画面では「担任の先生とのやりとり」） | その園児のクラスの当年度の担任と管理者 | その園児の保護者 | 参加している職員と、その家庭の保護者 |
| 3 | 目的別グループ | 職員がグループ編成画面で手で入れる | 入らない | 参加している職員 |

- 保護者の参加は、招待コードの登録・お子さまの追加のとき（`joinRoomsOfChildNow`、[server/api_guardian.go](../server/api_guardian.go) 269行〜）に決まる。紐づけを解除すると、個人チャットとクラスグループから外れる（`leaveRoomsOfChild`、[server/api_admin.go](../server/api_admin.go) 1081〜1100行）。
- 外れるときは参加の行（`t_chat_member`）を消さず、`left_at`（外れた日時）を入れる。所属していた期間を、過去ログを読める範囲の判定に使うため（基本設計書「チャット」(5-5)）。
- メッセージの `source_type` は、1 がふつうの投稿、4 が配布物の掲載の知らせ。2・3 は以前の「日誌・発達身体の共有の知らせ」で、いまはすべて取り消し済みにしてある（[server/db_diary.go](../server/db_diary.go) 52〜60行）。

## 流れ

1. 画面を開くと、`GET /api/chat/rooms`（`handleChatRooms`）で、参加しているチャンネルと、未読の件数・投稿できるか（`canPost`）・届く保護者の人数を読む。
2. チャンネルを選ぶと、`GET /api/chat/rooms/{id}/messages` でメッセージを読み、`POST .../read` で既読にする。
3. 送ると `POST /api/chat/rooms/{id}/messages`（`handleSendMessage`）。サーバは参加・権限・本文・他児の名前を確かめてから `t_chat_message` に書く。
4. 他児の名前が当たると 409（いまの状態とぶつかったときなどに返す応答。ここでは注意を表す。`kind: other_child_names`）。画面は注意のダイアログを出し、「このまま送る」で承諾した名前を添えて送り直す。
5. 書けたら操作ログを残し、`notifyRoomPost` で、いまの参加者の開いている画面へ知らせる。画面は知らせを受けて読み直す。
6. 配布物は `POST /api/handouts`（管理者）で掲載する。同じトランザクション（全部書くか、何も書かないかのまとまり）で、園チャットかクラスグループへ「〇〇を掲載しました。」のメッセージ（`source_type` 4）を入れる。

```
StaffChatScreen ──送信──▶ POST /api/chat/rooms/{id}/messages ──▶ handleSendMessage
                                  │ 参加・猶予・投稿権限・本文・他児の名前
                                  ├─ 当たった ──▶ 409 other_child_names ──▶ NameCheckDialog ──承諾して送り直す
                                  └─ 通った ──▶ t_chat_message ──▶ 操作ログ・notifyRoomPost
                                                                     └──▶ 参加者の画面が読み直す
StaffHandoutsScreen ──掲載──▶ POST /api/handouts ──▶ t_handout ＋ 掲載の知らせ（source_type 4）
GuardianChatScreen ──知らせのカード──▶ GuardianHandoutsScreen ◀── GET /api/handouts
```

## コードを読む

### 1. 職員を自動のチャンネルへ入れる（server/chat_membership.go 43〜75行）

```go
// autoRoomsWhere は、アカウント・ロール・担任の割り当てから参加者が決まるチャンネル（m_chat_room を r として引く）
const autoRoomsWhere = `r.is_archived = 0 AND r.room_type IN ('1', '2', '4', '5')`

// syncStaffChatRooms は、職員1人の参加を規則に合わせる。入れたり外したりした数を返す。
// 職員でないアカウントには何もしない。
func syncStaffChatRooms(q dbtx, accountID int64) (int, error) {
	var role, status string
	if err := q.QueryRow(`SELECT role, status FROM m_account WHERE account_id = ?`, accountID).
		Scan(&role, &status); err != nil {
		return 0, err
	}
	if role != roleAdmin && role != roleGeneralStaff {
		return 0, nil
	}

	wanted := map[int64]bool{}
	if status == "1" {
		ids, err := queryIDs(q, `SELECT r.chat_room_id FROM m_chat_room r
			WHERE `+autoRoomsWhere+`
			  AND (r.room_type IN ('1', '5')
			       OR ? = '1'
			       OR r.class_id IN (SELECT cs.class_id FROM t_class_staff cs
			                           JOIN m_class c ON c.class_id = cs.class_id AND c.fiscal_year = ?
			                           JOIN m_staff s ON s.staff_id = cs.staff_id
			                          WHERE s.account_id = ?))`,
			role, fiscalYear, accountID)
		if err != nil {
			return 0, err
		}
		for _, id := range ids {
			wanted[id] = true
		}
	}
```

**解説**

- `syncStaffChatRooms` は、職員1人について「入るべきチャンネル」（`wanted`）を決め、いまの参加と食い違う分だけ入れたり外したりする。
- 入るべきチャンネルは、園全体（1）と職員（5）はだれでも、管理者（`? = '1'`）はクラスと個人のすべて、一般は当年度の担任のクラスとそのクラスの園児の個人チャット。
- 停止中（`status` が 1 でない）の職員は `wanted` が空になり、自動のチャンネルからすべて外れる。外すときは `left_at` を入れる（77〜95行）。戻すときは `left_at` を空にして入れ直す（96〜107行）。
- 目的別グループ（3）とアーカイブ（過年度のクラスグループ）は `autoRoomsWhere` から外れていて、ここでは動かさない。
- 呼ぶのは、職員アカウントの発行・変更・停止と再開（api_admin.go 268・381・537行）、園児の登録で個人チャットを作るとき（child_room.go 42行）、起動のとき（`syncChatMembership`、140〜166行。main.go 137行から）。起動のときは、職員だけのチャンネルに入っている保護者も外す。
- 【仮置き】個人チャットの担任は、ルームの `class_id`（園児のクラス）で決める。名前で引くと、同じ氏名の別の園児の家庭に入ってしまうため（27〜30行。GitHub Issue #140・#163）。
- 目的別グループは手で編成する（`handleUpdateGroupMembers`、[server/api_chat.go](../server/api_chat.go) 1130〜1220行）。入れられるのは有効な職員だけで、保護者は入れない（`groupMemberError`、1100〜1115行）。一般の職員は、いま参加しているグループだけを編成できる（【仮置き】GitHub Issue #161）。
- 気をつけるところ：モックの `syncStaffChatRooms`（[web/src/api/mock.ts](../web/src/api/mock.ts) 1994行〜）に同じ規則がある。片方だけ直すと食い違う。

### 2. 後から入った保護者・外れた職員に見せないメッセージ（server/api_chat.go 166〜172・200〜203行）

```go
const beforeJoinedClause = ` AND NOT EXISTS (
	SELECT 1 FROM t_chat_member gm
	  JOIN m_chat_room gr ON gr.chat_room_id = gm.chat_room_id
	 WHERE gm.chat_room_id = m.chat_room_id AND gm.account_id = ?
	   AND gr.room_type = '4' AND m.sent_at <= gm.joined_at
	   AND m.sent_at >= ` + firstGuardianJoinedAt + `
	   AND (gm.joined_at > ` + firstGuardianJoinedAt + ` OR gm.account_id <> ` + firstGuardianAccountID + `))`
// …（略）…
const afterLeftClause = ` AND NOT EXISTS (
	SELECT 1 FROM t_chat_member lm
	 WHERE lm.chat_room_id = m.chat_room_id AND lm.account_id = ?
	   AND lm.left_at IS NOT NULL AND m.sent_at >= lm.left_at)`
```

**解説**

- どちらも、メッセージを読む SQL（`t_chat_message` を `m` とする）の WHERE に足す条件である。一覧・未読の数え・既読・知らせのどれにも同じ条件を足し、範囲をそろえる。
- `beforeJoinedClause`（保護者だけに足す）：後から登録した保護者には、自分が入る前の個人チャットのやりとりを見せない。先に登録していた保護者は、自分の書いたものが後から加わる人に読まれると知らないため（基本設計書「チャット」(5-6)。148〜165行の説明）。
- ただし、その部屋に保護者がまだ1人もいなかった間の投稿は見せる。個人チャットは園児の登録のときに作るので、保護者の登録より前から園が書けるため（GitHub Issue #140）。境は、その部屋に保護者が初めて入った日時（`firstGuardianJoinedAt`、184〜186行）。
- 時刻は秒の単位なので、登録と同じ秒のメッセージは前か後かを区別できない。見せない側へ倒す（基本設計書「メッセージの送受信」(4-7)。GitHub Issue #102・#301）。
- `afterLeftClause`（だれにでも足す）：外れたあとの投稿は見せない。読めるのは所属していた期間の過去ログだけ（GitHub Issue #161）。保護者は外れた時点でチャンネルごと読めなくなる（ブロック 3）ので、実際に効くのは職員である。同じ秒は、これも見せない側へ倒す（【仮置き】）。

### 3. チャンネルを読めるか・書けるか（server/api_chat.go 231〜267行）

```go
// isMember はそのチャンネルを参照できるかを判定する。
// 職員は外れたあとも、所属していた期間の過去ログを参照できる（読む範囲は afterLeftClause で絞る）。
// 保護者は left_at が入った時点で参照できなくなる（基本設計書 5-5）
func (a *app) isMember(u *SessionUser, roomID int64) bool {
	joined, left := a.memberState(u.AccountID, roomID)
	if !joined {
		return false
	}
	return !(left && u.isGuardian())
}

// canRead は、そのチャンネルのメッセージを読めるか。参加していれば isMember と同じ。
// 管理者は、参加していないグループも読める（書けない。書けるのは isParticipant の人だけ。GitHub Issue #312）
func (a *app) canRead(u *SessionUser, roomID int64) bool {
	if a.isMember(u, roomID) {
		return true
	}
	if !u.isAdmin() {
		return false
	}
	var n int
	a.db.QueryRow(`SELECT COUNT(*) FROM m_chat_room WHERE chat_room_id = ? AND room_type IN `+adminReadOnlyRoomTypes,
		roomID).Scan(&n)
	return n > 0
}

/*
isParticipant は、いまそのチャンネルに参加しているか（外れていないか）を判定する。

投稿・編集・取消・リアクション・未対応の切り替え・メンバー一覧の取得は、いまの参加者に限る。
外れた職員は過去ログを読めるだけで、書くことはできない（基本設計書「メッセージの送受信」(4-6)
「閲覧のみの権限では拒否する」、図/画面詳細図.md 4-3 No.8。GitHub Issue #161）。
*/
func (a *app) isParticipant(u *SessionUser, roomID int64) bool {
	joined, left := a.memberState(u.AccountID, roomID)
	return joined && !left
}
```

**解説**

- 3つの判定を使い分ける。`isMember` は参加の行があるか（保護者は外れたら偽）、`canRead` は読めるか、`isParticipant` はいま参加しているか（外れていないか）。
- 職員は外れたあとも、所属していた期間の過去ログを読める（`isMember` が真のまま）。保護者は `left_at` が入った時点で読めなくなる（基本設計書「チャット」(5-5)）。
- 管理者は、参加していないグループ（園全体・クラス・目的別・職員の全年度）も読める（`adminReadOnlyRoomTypes`、134行。要件定義書「過去ログの参照範囲」(4-4 (c))。GitHub Issue #312）。個人チャットは園児ごとに決めるので、参加の行があるものだけ。
- 書く操作（投稿・編集・取り消し・リアクション・未対応の切り替え）は、いまの参加者（`isParticipant`）に限る。外れたチャンネルは閲覧のみである（GitHub Issue #161）。例外として、管理者の取り消しは参加を問わない（ブロック 7）。
- 投稿できるか（`canPost`）は、チャンネル一覧を返すときに決めて画面へ渡す（`handleChatRooms`、89〜110行）。園全体は管理者だけ、保護者は個人チャットだけ、外れたチャンネルは不可、猶予期間中の保護者（卒園・退園した子の家庭）は不可。
- メンバー一覧（`handleChatMembers`、878〜923行）は職員にだけ返す。保護者が参加していても、ほかの家庭の氏名や続柄は返さない（要件定義書「チャットツール」(4-3)。GitHub Issue #95）。
- 気をつけるところ：画面が `canPost` で投稿欄を隠すのは見た目のためで、担保は送信のハンドラ（ブロック 4）が同じ判定をもう一度することにある。ログインした人の情報（`SessionUser`）の仕組みは [01 全体の仕組み](./01-全体の仕組み.md) を見る。

### 9. 開いている画面へ知らせる相手を決める（server/events.go 303〜325行）

```go
		writeErr(w, http.StatusInternalServerError, "取り下げに失敗しました")
		return
	}
	// 掲載の知らせも取り消す。知らせだけが残ると、開いても見つからない配布物へ案内し続けることになる
	if _, err := tx.Exec(`UPDATE t_chat_message SET is_deleted = 1, body = '', deleted_at = ?, deleted_account_id = ?
		WHERE source_type = '4' AND source_id = ? AND is_deleted = 0`, now(), u.AccountID, id); err != nil {
		writeErr(w, http.StatusInternalServerError, "取り下げに失敗しました")
		return
	}
	if err := tx.Commit(); err != nil {
		writeErr(w, http.StatusInternalServerError, "取り下げに失敗しました")
		return
	}
	a.log(u.AccountID, fnChat, opDelete, "t_handout", i64(id), nil, s(title), s("取り下げ"))
	a.notifyHandout(id, nullInt(classID))
	if noticeID.Valid && noticeRoom.Valid {
		a.notifyMessage(noticeRoom.Int64, noticeID.Int64)
	}
```

**解説**

- 取り下げも管理者だけ。配布物は消さずに `is_deleted` を立てる（論理削除）。一覧（`handleHandouts`）は `is_deleted = 0` だけを返す。
- 掲載の知らせのメッセージも、同じトランザクションで取り消し済みにする。知らせだけが残ると、開いても見つからない配布物へ案内し続けるため。
- この取り消しは誤送信ではない。誤送信対応記録画面の「対応の記録がない取り消し」には出さない（`retractedWithoutRecordClause` が `source_type` 4 を除く。GitHub Issue #98）。取り下げとして操作ログに残る。
- 最後に `notifyHandout`（配布物の一覧を見られる人へ。events.go 381〜397行）と `notifyMessage`（取り消した知らせを見られる人へ）を呼ぶ。配布物の画面は `onLive('handout')` を受けて読み直す（StaffHandoutsScreen.tsx 31〜32行）。
- 画面：配布物管理画面（[StaffHandoutsScreen.tsx](../web/src/screens/chat/StaffHandoutsScreen.tsx)）は、一般の職員には閲覧だけを見せる。配布物一覧画面（[GuardianHandoutsScreen.tsx](../web/src/screens/chat/GuardianHandoutsScreen.tsx)）は月ごとにまとめて並べる。


## 気をつけているところ

- **誤送信を防ぐ。** 書きかけはチャンネルごとに持つ。届く保護者の人数を入力欄の上に出す。職員が保護者の参加するチャンネルへ送るときは、サーバが他児の名前を照合し、承諾がなければ送らない。
- **誤送信のあとを残す。** 取り消しは本文を消して事実だけを残し、もとの本文は操作ログに残す。管理者は既読の有無ととった対応を誤送信対応記録画面で記録する。記録の無い取り消しは、ダッシュボードにも件数で出る。
- **見てよい範囲をサーバでそろえる。** 一覧・未読・既読・知らせ・リアクションのどれも、`afterLeftClause`・`beforeJoinedClause`・`isMember`／`canRead`／`isParticipant` の同じ条件を通す。画面で投稿欄を隠すだけに頼らない（基本設計書「権限チェックの実装方針」(6-2)）。
- **保護者に見せない値。** 既読の人数・未対応／対応済み・メンバー一覧（ほかの家庭の氏名と続柄）は保護者に返さない。後から加わった保護者には、先の保護者と園のやりとりを見せない。
- **外れた人は閲覧のみ。** 職員は所属していた期間の過去ログだけを読め、書けない。保護者は外れたらチャンネルごと読めない。参加の行は消さず `left_at` で期間を残す。
- **参加は規則から決める。** 職員の参加は `syncStaffChatRooms` の1か所で決め、起動のたびに合わせ直す。目的別グループだけが手で編成でき、保護者は入れない。
- **ひとまとまりで書く。** 送信と未対応への戻し、配布物と掲載の知らせ、取り下げと知らせの取り消しは、それぞれ1つのトランザクションで書く。取り消し・編集は WHERE に `is_deleted = 0` を入れ、同時の操作で上書きしない。
- **規則は2か所。** サーバ（server/api_chat.go・chat_membership.go・api_handout.go）とモック（web/src/api/mock.ts の `chatApi`・`syncStaffChatRooms`・`handoutApi`）に同じ規則と文言がある。テストもサーバ（server/api_chat_*_test.go）とモック（web/tests/）の両方にある。
- **設計に無い値は【仮置き】。** リアクションの絵文字4種、職員だけのチャンネルの既読の数え方、外れたのと同じ秒の扱い、保護者の送ったものを誤送信の対象にしないこと、配布物のファイルの実体を持たないこと、などは web/仮置き値.md にある。
