# 01 全体の仕組み（かんたん版）

> [長い版](../01-全体の仕組み.md) を、関数1つにつき2〜3行に縮めたもの。行番号は書かない（コードが変わるとずれるため）。名前で検索して探す。

## サーバの起動と配線

#### `main`（server/main.go）
起動の引数を読み、DB を開いて `app` を作り、経路と画面のファイルを登録する。
`securityHeaders(checkOrigin(mux))` で包み、待ち時間の上限を付けた `http.Server` で待ち受ける。→ 詳しく：[01 の節 1](../01-全体の仕組み.md)

#### `openDB`（server/db.go）
SQLite（`modernc.org/sqlite`）を開き、接続を1本に絞って、`schema.sql` と `seed.sql` から DB を作る。
最後に `ensureXxx` を決まった順に呼び、足りない表や列を足す。→ 詳しく：[01 の節 2](../01-全体の仕組み.md)

#### `ensureEvents`（server/db.go）
行事カレンダーの予定の表 `t_event` を用意し、空なら `seedEvents` で今月と来月に4件入れる。
`ensureXxx` はこの形で、以前に作った DB へ表や列を足す関数の一族である（一覧は長い版の表）。→ 詳しく：[01 の節 2](../01-全体の仕組み.md)

#### `isStaleDemoDB`（server/db.go）
既にある DB が、いまと違う `seed.sql` で作ったデモの DB かを見る。
指紋（`fingerprintOf`）が `PRAGMA user_version` と違い、1番のアカウントが seed の管理者のときだけ古いと見る。→ 詳しく：[01 の節 3](../01-全体の仕組み.md)

#### `fingerprintOf`（server/db.go）
`seed.sql` から空行・コメントの行・前後の空白を除いてハッシュにし、seed の指紋を作る。
指紋は `PRAGMA user_version` に書き、次に開いたときの比べに使う。→ 詳しく：[01 の節 3](../01-全体の仕組み.md)

#### `moveAsideStaleDB`（server/db.go）
古いデモの DB を `<path>.stale-<UTC の日時>` へ名前を変えて退け、新しい DB を作り直す。
退けたものは新しい3つまで残す。公開先の DB は「無いときだけ作る」ため、この作り直しが要る。→ 詳しく：[01 の節 3](../01-全体の仕組み.md)

#### `routes`（server/routes.go）
経路を機能ごとの `routeXxx` に分け、まとめて呼ぶ。
`"POST /api/login"` のようにメソッドと道筋を1つの文字列で書く。権限は表に書かず、各ハンドラの入口で判定する。→ 詳しく：[01 の節 4](../01-全体の仕組み.md)

#### `routeAuth`（server/routes.go）
ログイン・合言葉つきのログイン・ログアウト・自分の情報など、認証の経路を登録する。
ほかに `routeChild`・`routeDiary`・`routeChat`・`routeNap`・`routeContact`・`routeGrowth`・`routeAdmin`・`routeGuardian` がある。→ 詳しく：[01 の節 4](../01-全体の仕組み.md)

#### `handleGetChild`（server/api_child.go）
園児を1人読む。ほぼすべてのハンドラがこの形である。
`requireStaff` → `canReadChild` → SQL → `writeJSON` の順に進む。モックの `getChild` が同じ規則を持つ。→ 詳しく：[01 の節 5](../01-全体の仕組み.md)

#### `writeJSON`（server/httpx.go）
先に JSON にしてから状態を書く。JSON にできない値で「200 の空の本文」を返さないためである。
権限が無いときは `writeForbidden` で 403 を返し、文言はそのまま画面に出る。→ 詳しく：[01 の節 5](../01-全体の仕組み.md)

## サーバの守り・状態・知らせ

#### `checkOrigin`（server/csrf.go）
状態を変える要求の `Origin`（無ければ `Referer`）が、要求先と同じホストかを確かめる。
GET・HEAD・OPTIONS と `/api/` 以外は素通りする。もう1段は Cookie の SameSite=Strict である。→ 詳しく：[01 の節 6](../01-全体の仕組み.md)

#### `sameOrigin`（server/csrf.go）
要求の送信元のホストが、要求先のホストと同じかを答える。
`checkOrigin` が呼ぶ。トークンを配る方式は採らない。→ 詳しく：[01 の節 6](../01-全体の仕組み.md)

#### `contentSecurityPolicy`（server/headers.go）
読み込めるものを自分のオリジンに限る、応答ヘッダの文字列の定数である。
`style-src` にだけ `'unsafe-inline'` がある。画面が style 属性を使うためである。→ 詳しく：[01 の節 7](../01-全体の仕組み.md)

#### `securityHeaders`（server/headers.go）
すべての応答にセキュリティのヘッダを付ける。`/api/` の応答には `Cache-Control: no-store` も付ける。
`-secure` のときだけ HSTS を付ける。値は【仮置き】である。→ 詳しく：[01 の節 7](../01-全体の仕組み.md)

#### `create`（server/session.go）
ログインに成功したあと、ランダムな ID でセッションを作り、HttpOnly・SameSite=Strict の Cookie を渡す。
期限は、ログインを保つ上限と、職員だけの自動ログアウトの2つである。方式は【仮置き】である。→ 詳しく：[01 の節 8](../01-全体の仕組み.md)

#### `requireLogin`（server/session.go）
セッションが無ければ 401 を返す。画面が思っている利用者とセッションの利用者が違っても断る。
`requireUser`・`requireStaff`・`requireAdmin` の土台である。→ 詳しく：[01 の節 9](../01-全体の仕組み.md)

#### `requireUser`（server/session.go）
一時パスワードのまま、または規約の再同意が要るあいだは、403 と理由を返して止める。
`requireLogin` の上に積んだ守りである。→ 詳しく：[01 の節 9](../01-全体の仕組み.md)

#### `requireStaff`（server/session.go）
ロールを見て、職員でなければ断る。`false` を返したときは応答を書き終えているので、ハンドラは `return` するだけである。
`requireAdmin` は同じ形で管理者だけを通す。断りの文言はモックと同じにしてある。→ 詳しく：[01 の節 9](../01-全体の仕組み.md)

#### `loadSessionUser`（server/session.go）
利用者の情報を、要求のたびに DB から読み直す。
停止や権限の変更がすぐ効く。→ 詳しく：[01 の節 9](../01-全体の仕組み.md)

#### `canSeeChild`（server/scope.go）
ロールで分け、管理者は全園児、一般は今年度の担任クラスの園児、保護者は紐づいた園児だけを見られる。
画面で隠すだけでは守りにならず、ここが権限の担保である。モックの `canSeeChild` と対になる。→ 詳しく：[01 の節 10](../01-全体の仕組み.md)

#### `canReadChild`（server/scope.go）
ハンドラが使う「この園児を読めるか」の判定である。`canSeeChild` を土台にしている。
一覧は `visibleChildren` が同じ範囲を SQL の条件にし、連絡帳は別の `contactAccess` で判定する。→ 詳しく：[01 の節 10](../01-全体の仕組み.md)

#### `log`（server/oplog.go）
操作ログを `t_operation_log` に追記する。更新・削除の手段は作らない。
何を記録するかはサーバが決める。失敗しても業務は止めず、サーバのログに残す。モックにも同じ `log` がある。→ 詳しく：[01 の節 11](../01-全体の仕組み.md)

#### `changedFields`（server/oplog.go）
変更前後の値を、変わった項目だけの `{"項目名": 値}` にまとめる。
モックにも同じ名前の関数があり、項目名と形を合わせてある。→ 詳しく：[01 の節 11](../01-全体の仕組み.md)

#### `notify`（server/events.go）
いまつないでいる画面のうち、`see` で見てよいと判定された人にだけ合図（`liveEvent`）を送る。
合図は種類と ID だけで、中身は入れない。行を読んでいる途中やトランザクションの中では呼ばない。→ 詳しく：[01 の節 12](../01-全体の仕組み.md)

#### `notifyContactChild`（server/events.go）
連絡帳を読める職員と保護者にだけ、`contact` の合図を送る。
誰に送るかは、読み直す API と同じ判定で決める。→ 詳しく：[01 の節 12](../01-全体の仕組み.md)

#### `notifyCalendar`（server/events.go）
行事の予定を見られる人に、`calendar` の合図を送る。`api_event.go` の書き込みのあとに呼ばれる。
予定の ID・日付・操作・クラスを受け取る。→ 詳しく：[01 の節 12](../01-全体の仕組み.md)

#### `handleEvents`（server/events.go）
`text/event-stream` で応答を開いたままにして、合図を流す SSE の受け口である。
つないでいる画面はサーバのメモリにだけ持つ（サーバ1台の前提）。画面側は `web/src/live.ts` が受ける。→ 詳しく：[01 の節 12](../01-全体の仕組み.md)

#### `serveWeb`（server/main.go）
React のビルド成果物を配る。`/api/` で合うハンドラが無ければ 404 の JSON を返す。
無い経路は `index.html` を返し、`/assets/` は1年キャッシュ、`/assets/` に無いファイルは 404 にする。→ 詳しく：[01 の節 13](../01-全体の仕組み.md)

## 画面

#### `main.tsx`（web/src/main.tsx）
`#root` に React を描く。外側から `StrictMode`・`BrowserRouter` などで包む。
描く前に書体と CSS（`styles/tokens.css`・`app.css` など機能ごとに分けたもの）を読み込む。→ 詳しく：[01 の節 14](../01-全体の仕組み.md)

#### `RequireStaff`（web/src/App.tsx）
職員の経路の外枠に置く守り。未ログインなら職員用トップへ、保護者なら保護者のホームへ戻す。
`RequireAdmin` は管理者だけを通し、一般には理由を持たせて戻す。出し分けであって、権限の担保ではない。→ 詳しく：[01 の節 15](../01-全体の仕組み.md)

#### `RequireAdmin`（web/src/App.tsx）
管理者だけを通す。一般を黙って戻さず、理由（`state.denied`）を持たせて戻す。
サーバ側の `requireAdmin` が本当の担保である。→ 詳しく：[01 の節 15](../01-全体の仕組み.md)

#### `RequireProcedure`（web/src/App.tsx）
一時パスワードからの変更と規約の同意の画面に、手続きの要る人だけを通す守りである。
経路の表は入れ子で、守りごとに画面が並ぶ。保護者は `RequireGuardian` が `GuardianLayout` を描く。→ 詳しく：[01 の節 15](../01-全体の仕組み.md)

#### `App`（web/src/App.tsx）
開き直したときに `api.bootstrap()`（`GET /api/me`）でサーバのセッションから利用者を取り戻す。
取り戻すまで `ready` を偽にして経路を待たせる。使えるあいだだけ SSE を1本つなぐ（`connectLive`）。→ 詳しく：[01 の節 16](../01-全体の仕組み.md)

#### `SessionProvider`（web/src/session.tsx）
ログイン中の利用者を React の Context で持ち、どの画面からも読めるようにする。
`setUser` は画面の利用者と要求に添える利用者を同時に更新する。`logout` はサーバのセッションの破棄を待ってから空にする。→ 詳しく：[01 の節 17](../01-全体の仕組み.md)

#### `api`（web/src/api/client.ts）
画面が必ず通る呼び口で、`VITE_API` が `mock` なら `mock.ts`、そうでなければ `http.ts` を選ぶ。
両者は同じ関数名・同じ戻り値の形（`shapes.ts`）を持つ。本番のビルドでは `keepMockOutOfBuild` がモックを外す。→ 詳しく：[01 の節 18](../01-全体の仕組み.md)

#### `keepMockOutOfBuild`（web/build/keepMockOutOfBuild.ts）
本番のビルドで `mock.ts` を `noMock.ts` へ差し替え、出力にモックが残っていないかを2か所で見張る。
入っていたらビルドを失敗させる。→ 詳しく：[01 の節 18](../01-全体の仕組み.md)

#### `request`（web/src/api/http.ts）
すべての API が通る共通の口で、Cookie を送り、15秒の時間切れを付けて `fetch` する。
画面が思っている利用者を `X-Sukusuku-Account` で添える。401 は参照表を捨てて入口へ戻す。→ 詳しく：[01 の節 19](../01-全体の仕組み.md)

#### `StaffLayout`（web/src/layouts/StaffLayout.tsx）
職員の全画面の共通の枠で、ヘッダ・左メニュー・本文（`ScreenErrorBoundary` で包む）を描く。
`useAsync` で件数などを読み、ログアウトの前に午睡チェックの実施中と保存していない入力を確かめる。→ 詳しく：[01 の節 20](../01-全体の仕組み.md)

## モック

#### `canSeeChild`（web/src/api/mock.ts）
サーバの `canSeeChild` と同じ分け方・同じ条件で、モックの側の参照範囲を判定する。
業務の規則が Go とモックの2か所にあることの例である。規則を変えるときは両方を直し、両方にテストを足す。→ 詳しく：[01 の節 21](../01-全体の仕組み.md)
