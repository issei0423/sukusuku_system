## 流れ

職員が園児の情報を開くときを例にする（`GET /api/children/C001`）。

1. 画面が `useAsync(() => api.getChild(user, id), …)` の形で、`api/client.ts` の `api` を呼ぶ
2. 本物のサーバにつなぐときは、`api/http.ts` の `request` が `fetch` で要求を送る。Cookie と、画面が思っている利用者（`X-Sukusuku-Account`）を添える
3. Go の `http.Server` が、`securityHeaders`（ヘッダを付ける）→ `checkOrigin`（送信元を確かめる。GET は素通り）→ `ServeMux`（経路を選ぶ）の順に通す
4. `routes.go` の表で、`GET /api/children/{childID}` が `handleGetChild` に渡る
5. ハンドラは `requireStaff`（ログイン・手続き・職員か）→ `canReadChild`（この園児を読めるか）→ SQL → `writeJSON` の順に進む
6. 書き込みの API なら、続けて `a.log`（操作ログ）と `a.notifyXxx`（開いている画面への知らせ）を呼ぶ
7. 知らせを受けたほかの画面は、`useAsync` の `live` で同じ API を読み直す

```
画面  useAsync → api(client.ts) → request(http.ts) ──fetch──┐
                                                            ▼
サーバ securityHeaders → checkOrigin → ServeMux(routes.go) → handleXxx(api_*.go)
         requireStaff など(session.go) → canSeeChild など(scope.go) → SQLite
         → writeJSON(httpx.go)、書き込みなら log(oplog.go)・notify(events.go)
                                                            │ SSE
画面  live.ts → useAsync が読み直す ◄─────────────────────────┘
```

**解説**
- `flag` で起動の引数を読む。`-addr`（待ち受け。既定 `:8080`）、`-files`（写真の実体の置き場）、`-db`（SQLite のファイル）、`-web`（React のビルド成果物）、`-ai-model`、`-secure`（HTTPS で公開するとき）
- `openDB` で DB を開き、`app` を作って `init` する。`app`（26〜52行）はサーバ全体の状態（DB・セッション・知らせの配り先など）を持つ構造体で、ハンドラはすべて `app` のメソッドである
- 1つ目の略（77〜87行）では、環境変数 `ANTHROPIC_API_KEY` があれば AI の呼び口を用意する。無ければ AI を使わず、ほかはすべて動く
- `init`（114〜138行）は起動のときの準備をする。知らせの配り先（`liveHub`）を用意し、最新版の利用規約の版を読み、`seed.sql` に入れた平文のパスワードの目印（`!pass1234`）を bcrypt のハッシュに置き換え（`seedPasswords`。方式は【仮置き】）、職員のチャットの参加を規則に合わせ直す（`syncChatMembership`。06 で扱う）
- `ServeMux` に経路（routes.go）と画面のファイルの配信（`serveWeb`）を登録し、`securityHeaders(checkOrigin(mux))` で包む。要求は外側から、ヘッダを付ける → 送信元を確かめる → 経路に振り分ける、の順に通る
- 待ち時間の上限は、ゆっくり送り続ける接続で待ち受けを使い切らせないため（Slowloris。GitHub Issue #236 の 5）。`WriteTimeout` は置かない。SSE の接続を長く開いたままにするためである。秒数は【仮置き】

### 2. DB を開く・作る（server/db.go 34〜139行）
```go
func openDB(path string) (*sql.DB, error) {
	_, statErr := os.Stat(path)
	fresh := os.IsNotExist(statErr)

	db, err := sql.Open("sqlite", path+"?_pragma=foreign_keys(1)&_pragma=busy_timeout(5000)")
	if err != nil {
		return nil, fmt.Errorf("データベースを開けません: %w", err)
	}
	// SQLite は書き込みを直列化する。接続を1本に絞って書き込みの競合を避ける
	db.SetMaxOpenConns(1)
	// …（略）…
	if fresh {
		log.Printf("データベースを新規作成します: %s", path)
		if _, err := db.Exec(schemaSQL); err != nil {
			return nil, fmt.Errorf("スキーマの作成に失敗しました: %w", err)
		}
		if _, err := db.Exec(seedSQL); err != nil {
			return nil, fmt.Errorf("デモデータの投入に失敗しました: %w", err)
		}
		// …（略）…
		// どの seed で作ったかの印。次の起動で seed が変わっていないかを見る（isStaleDemoDB）
		if _, err := db.Exec(fmt.Sprintf(`PRAGMA user_version = %d`, seedFingerprint())); err != nil {
			return nil, fmt.Errorf("seed の指紋を書けません: %w", err)
		}
		log.Printf("デモデータを投入しました")
	}
	// …（略）…
	return db, nil
}
```
**解説**
- `schemaSQL`・`seedSQL` は、`//go:embed` で `schema.sql` と `seed.sql` を実行ファイルに埋め込んだもの（18〜22行）。サーバのファイル1つで DB を作れる
- ドライバは `modernc.org/sqlite`（純 Go）。gcc の無い環境でもビルドできるため（server/README.md「選定の理由」）
- `SetMaxOpenConns(1)` で接続を1本に絞る。SQLite は書き込みを直列化するため。その代わり、行を読んでいる途中で別の問い合わせを投げると止まる（server/README.md「実装上の注意」）
- 1つ目の略（44〜65行）は、接続の確かめと、次の項で読む作り直しの判定である。ファイルが無ければ（`fresh`）、`schema.sql` → `seed.sql` の順に流す。2つ目の略（74〜86行）で、成長曲線の基準値を入れ、デモの日付を起動した日へずらす（seed_shift.go）
- 最後に seed の指紋を `PRAGMA user_version`（SQLite のファイルに1つだけ持てる整数）に書く。次の項で使う
- 3つ目の略（93〜137行）で `ensureXxx` を順に呼び、以前に作った DB に、あとから足した表と列を足す。どれも「足りないものだけを足す」ので、何度呼んでも同じ結果になる（db_contact.go の頭のコメント）

### 3. seed が変わったデモの DB を作り直す（server/db.go 49〜64行）

**解説**
- 既にある DB を開いたとき、`isStaleDemoDB`（170〜194行）で「いまと違う seed で作ったデモの DB か」を見る
- 指紋は `fingerprintOf`（147〜163行）が作る。`seed.sql` から空行・コメントの行・前後の空白を除いてハッシュにする。改行を LF にそろえるので、Windows と Linux で同じ値になる。コメントや字下げだけの直しでは作り直さない（PR #332）
- 指紋が `PRAGMA user_version` と同じなら何もしない。違っても、1番のアカウントが seed の管理者（`@hoiku.example.jp`）でなければ、本当の園の DB とみなして作り直さない。環境変数 `SUKUSUKU_DEMO_RESEED=off` でも止められる
- 作り直すときは、古い DB を `<path>.stale-<UTC の日時>` へ名前を変えて退け（`moveAsideStaleDB`。新しい3つまで残す）、`openDB` を呼び直して新しく作る
- なぜ要るか：公開先の DB は「無いときだけ作る」ため、`seed.sql` でデモアカウントを入れ替えても古いまま残り、ログインできなかった（2026-10-30。db.go 26〜30行）。この動きは設計に無い【仮置き】である

### 5. ハンドラの入口の型（server/api_child.go 123〜140行）
```go
func (a *app) handleGetChild(w http.ResponseWriter, r *http.Request) {
	u, ok := a.requireStaff(w, r)
	if !ok {
		return
	}
	childID := r.PathValue("childID")
	if !a.canReadChild(u, childID) {
		writeForbidden(w, "この園児を参照する権限がありません")
		return
	}
	row := a.db.QueryRow(`SELECT `+childColumns+` FROM m_child WHERE child_id = ?`, childID)
	c, err := scanChild(row)
	if err != nil {
		writeErr(w, http.StatusNotFound, "園児が見つかりません")
		return
	}
	writeJSON(w, http.StatusOK, c)
}
```
**解説**
- ほぼすべてのハンドラがこの形をしている。① 入口で利用者を確かめる（`requireStaff`）② 対象を読めるかを確かめる（`canReadChild`）③ SQL を投げる ④ `writeJSON` で返す
- `requireStaff` が `false` を返したときは、401・403 の応答をもう書き終えている。ハンドラは `return` するだけでよい
- 権限が無いときは `writeForbidden` で 403 を返す。`message` の文言はそのまま画面に出る（httpx.go の `apiError`）
- `writeJSON`（httpx.go 33〜48行）は、先に JSON にしてから状態を書く。JSON にできない値で「200 の空の本文」を返し、画面が真っ白になったことがあるため（GitHub Issue #160）
- 同じ規則はモックの `getChild`（web/src/api/mock.ts 949〜954行）にもある。保護者を断る・`canReadChild` で断る・無ければ「園児が見つかりません」の3つがそろっている

### 6. 送信元の確かめ（server/csrf.go 36〜63行）
```go
func checkOrigin(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if safeMethods[r.Method] || !strings.HasPrefix(r.URL.Path, "/api/") {
			next.ServeHTTP(w, r)
			return
		}

		if !sameOrigin(r) {
			writeForbidden(w, "要求の送信元を確認できませんでした")
			return
		}
		next.ServeHTTP(w, r)
	})
}

// sameOrigin は、要求の送信元が要求先と同じかを判定する
func sameOrigin(r *http.Request) bool {
	// Origin が付いていればそれを見る
	if o := r.Header.Get("Origin"); o != "" {
		return hostOf(o) == r.Host
	}
	// Origin が無いときは Referer で代替する
	if ref := r.Header.Get("Referer"); ref != "" {
		return hostOf(ref) == r.Host
	}
	// どちらも無い要求は、ブラウザからの通常の操作ではない
	return false
}
```
**解説**
- CSRF（ほかのサイトから、ログイン中の利用者の名で要求を送らせる攻撃）への守りである（要件定義書「セッションの保護」(8 No.9)、基本設計書「データ保護」(6-3)）
- GET・HEAD・OPTIONS の読むだけの要求（`safeMethods`、30〜34行）と、`/api/` 以外（画面のファイル）は確かめない
- 状態を変える要求は、`Origin` のホストが要求先と同じかを見る。`Origin` が無ければ `Referer` で代える。どちらも無ければ断る（「無ければ通す」は守りにならない。csrf.go 25〜26行）
- 守りは2段である。もう1段は、セッションの Cookie を SameSite=Strict にすること（session.go）。SameSite だけに頼らないのは、ブラウザによって扱いに差があるため
- トークンを配って照合する方式は採らない。画面側にも発行・保持・失効を作り込むことになり、得られる差に見合わないため（csrf.go 21〜23行）

### 7. セキュリティの応答ヘッダ（server/headers.go 27〜49行）
```go
const contentSecurityPolicy = "default-src 'self'; " +
	"img-src 'self' data: blob:; " +
	"style-src 'self' 'unsafe-inline'; " +
	"object-src 'none'; " +
	"base-uri 'self'; " +
	"form-action 'self'; " +
	"frame-ancestors 'none'"

func securityHeaders(next http.Handler, secure bool) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		h := w.Header()
		h.Set("Content-Security-Policy", contentSecurityPolicy)
		h.Set("X-Content-Type-Options", "nosniff")
		h.Set("Referrer-Policy", "same-origin")
		if strings.HasPrefix(r.URL.Path, "/api/") {
			h.Set("Cache-Control", "no-store")
		}
		if secure {
			h.Set("Strict-Transport-Security", "max-age=31536000")
		}
		next.ServeHTTP(w, r)
	})
}
```
**解説**
- すべての応答に3つのヘッダを付ける。Content-Security-Policy（読み込めるものを自分のオリジンに限り、ほかのサイトの枠に入れさせない）、X-Content-Type-Options（種類の取り違えをさせない）、Referrer-Policy（ほかのサイトへ移るときに URL を渡さない）
- `style-src` に `'unsafe-inline'` があるのは、画面が style 属性を使っているため（headers.go 14行）
- `/api/` の応答には `Cache-Control: no-store` を付ける。園児の情報（要配慮個人情報を含む）を、共有の端末のブラウザに残さないため（基本設計書「データ保護」(6-3)）
- `-secure` のときだけ HSTS（以後 https でしかつながせない指示）を付ける。localhost の http で付けると、ブラウザがその後 https でしかつながなくなるため
- 値は設計に定めが無い【仮置き】である（GitHub Issue #236 の 3・4）

### 8. ログインの状態を作る（server/session.go 99〜135行）
```go
func (s *sessionStore) create(w http.ResponseWriter, accountID int64, entrance string, idleLogout, remember bool, lifetime time.Duration) {
	id := randomToken(32)
	at := s.now()
	s.mu.Lock()
	// …（略）…
	s.data[id] = session{
		accountID: accountID, entrance: entrance,
		expiresAt: at.Add(lifetime), idleLogout: idleLogout, lastActiveAt: at,
	}

	maxAge := 0
	if remember {
		maxAge = int(lifetime / time.Second)
	}

		Name:     sessionCookie,
		Value:    id,
		Path:     "/",
		HttpOnly: true,
		SameSite: http.SameSiteStrictMode,
		MaxAge:   maxAge,
		// Secure は HTTPS 公開時に true にする（起動時の -secure）。本演習の動作検証環境は localhost のため既定は false

		Secure: s.secure,
	})
}
```

- この方式は【仮置き】である。認証情報の保持方式は要決定事項の優先度Aで、まだ決まっていない（session.go 14〜23行）

- 通信の失敗・時間切れは「サーバに届かない」とし、`setReachable(false)` で画面の上端の帯（ConnectionBanner）を出させる。502・503・504 も同じに扱う（124〜133行）。貯めて後から送ることはしない（詳細設計書「画面の受け取り」(6-4)）
- 401 は「セッションが無い・切られた」。参照表を捨て、App へ知らせて入口へ戻させる
- 略したところでは、裏の読み直しの要求に印を付け（101行。自動ログアウトを延ばさない）、手続きの途中の 403 を手続きの画面へ案内し（144〜147行）、ログインの失敗理由をモックと同じ形（JSON の文字列）で投げる（172〜174行）
- 園児名・クラス名・設定などの小さな参照は、ログイン直後に `GET /api/reference` でまとめて読み、参照表に持つ（238〜284行）。毎回問い合わせると往復が増えるため

## 業務の規則は Go とモックの2か所にある

[AGENTS.md](../AGENTS.md) の「いちばん大事な決まり」である。
参照範囲・権限・承認の可否・入力の検証・操作ログの規則は、Go サーバ（`server/`）とモック（`web/src/api/mock.ts`）の両方にある。
例として、10 で読んだ Go の `canSeeChild` と同じ規則を、モックの側で見る。

### 21. モックの canSeeChild（web/src/api/mock.ts 336〜348行）
```ts
/** 職員が参照できる園児か。一般（保育士）は自クラスに限る（要件定義書「対象権限列の読み方」(4-2 冒頭)） */
export function canSeeChild(user: SessionUser, childId: string): boolean {
  if (user.role === '1') return true;
  if (user.role === '2') {
    if (user.class_id == null) return false;
    return db.classChildren.some((cc) => cc.class_id === user.class_id && cc.child_id === childId);
  }
  // 保護者は有効な紐づけのある自児のみ
  if (!user.guardian_id) return false;
  return db.guardianChildren.some(
    (gc) => gc.guardian_id === user.guardian_id && gc.child_id === childId && gc.link_status === '1',
  );
}
```
**解説**
- 10 の Go の `canSeeChild`（server/scope.go 95〜117行）と、分け方も条件も同じである。違うのは、SQL で数えるか、`mockDb` の配列を `some` で探すかだけ

| 利用者 | Go（server/scope.go） | モック（web/src/api/mock.ts） |
| :-- | :-- | :-- |
| 管理者 | `case "1": return true` | `if (user.role === '1') return true;` |
| 一般 | `t_class_child` を `class_id` と `child_id` で数える | `db.classChildren.some(...)` |
| 保護者 | `t_guardian_child` を `link_status = '1'` で数える | `db.guardianChildren.some(... gc.link_status === '1')` |

- なぜ2か所にあるか：テスト（`web/tests/`）と `npm run dev:mock` は、Go サーバを立てずにモックを相手に動く。モックの規則が Go と違うと、テストが通っても本物のサーバでは違う動きになる
- 規則を変えるときは必ず両方を直し、両方にテストを足す（Go は `server/*_test.go`、モックは `web/tests/`）。同じ観点を両方から確かめる組として、`server/api_mock_rules_test.go` と `web/tests/mockServerRules.test.ts` がある。`web/tests/integration.test.ts` は、`http.ts` を本物のサーバへ向けて確かめる
- `http.ts` にも `canSeeChild`（http.ts 324〜326行）があるが、これは規則ではない。サーバが利用者の範囲で絞って返した参照表に、その園児が含まれるかを見るだけである。画面の出し分けのためで、担保ではない（http.ts 317〜323行）
- ほかにも、2か所にある規則は多い。操作ログの `changedFields`（11）、知らせの `notify` と `publish`（12）、手続きの途中を断る `requireUser` とモックの `guardProcedure`（mock.ts 5710行）などである。Go 側のコメントに「モックは web/src/api/mock.ts の〇〇」と、もう片方の場所が書いてあることが多い
- デモデータも `server/seed.sql` と `web/src/api/mockDb.ts` の2か所にある。片方を変えたら、もう片方も合わせる

## 気をつけているところ

- **権限の担保はサーバ。** `requireStaff`・`requireAdmin` と、`scope.go`・`contact_scope.go` の判定で守る。画面の `RequireAdmin` や「管理」のメニューを隠すのは操作性のため
- **業務の規則は2か所。** Go とモックの両方を直し、両方にテストを足す。デモデータも2か所
- **状態を変える要求は、送信元を確かめる。** `checkOrigin` と、HttpOnly・SameSite=Strict の Cookie の2段
- **API の応答はキャッシュさせない。** 共有の端末に園児の情報を残さない（`headers.go`）
- **DB の接続は1本。** 行を読んでいる途中で別の問い合わせや `notify` を呼ばない（server/README.md「実装上の注意」）
- **操作ログは追記だけ。** 記録する操作はサーバが決め、変更前後の値は変わった項目だけを並べた順に書く
- **知らせに中身を入れない。** 送るのは種類と ID だけ。誰に送るかは、読み直す API と同じ判定で決める
- **日付と時刻は JST に固定。** Go は `model.go` の `now()`・`today()`（118〜124行）、画面は `web/src/api/util.ts` の `now()`・`today()`
- **【仮置き】が多い土台である。** セッションの方式、応答ヘッダの値、待ち時間の秒数、デモの DB の作り直し、画面のファイルのキャッシュの値は、どれも設計に定めが無い。一覧は [web/仮置き値.md](../web/仮置き値.md)
