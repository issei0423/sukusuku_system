# 02 ログインとアカウント

> この説明は commit 74f09acf のコードで書いた。行番号はその版のもの。

## この機能でできること

- 職員と保護者が、ログインID（メールアドレス）とパスワードでログインする。入口は職員用トップ（`/staff-top`）と保護者用トップ（`/`）の2つだ。様式は同じで、入口だけが違う。
- まちがいが続くと、アカウントをロックする。送信元（IP アドレス）ごとの上限もある。
- 職員の画面だけ、操作が無いまま時間が過ぎると、自動でログアウトする。その職員が始めた午睡チェックの実施中は切らない。
- 一時パスワードでログインした人と、規約の改定のあとに初めてログインした人は、変更・同意を終えるまでほかの画面へ進めない。
- 保護者は、園から配られた招待コードで、自分のアカウントを作る。職員のアカウントは管理者が発行する（[08 園児と管理の画面](./08-園児と管理の画面.md)）。
- ログイン中の人は、メニューからパスワードを変えられる。

## 流れ

ログインの流れを書く。

1. 利用者が TopScreen でログインIDとパスワードを入れ、「ログイン」を押す。画面は `api.login(email, password, entrance)` を呼ぶ。
2. `web/src/api/http.ts` が `POST /api/login` を送る。`entrance` は開いた入口（`staff` か `guardian`）だ。
3. サーバのハンドラ（1つの URL の要求を受けて応答を返す関数）`handleLogin` が、上から順に確かめる。ログイン中か → 入口の値 → 送信元の上限 → アカウントの有無 → ロック中か → パスワード → 停止中か → 入口の系統 → 一時パスワードの期限。
4. どこかで止まったら、401 と理由の種類（`kind`）を返す。全部通ったら、失敗の回数を 0 に戻し、セッションを作る。セッションID は Cookie（ブラウザが次の要求に自動で添える小さな値）で渡す。
5. 画面は、返った利用者（`SessionUser`）を `session.tsx` に入れる。一時パスワードならパスワード変更へ、規約が未同意なら同意へ、どちらも済んでいればホームへ進む。
6. 以後の要求には Cookie が付く。サーバは要求のたびに `requireUser` で、手続きの途中でないかを確かめる。

```
TopScreen ──api.login──▶ http.ts ──POST /api/login──▶ handleLogin（server/api_auth.go）
                                                        ├ 失敗：401 と kind（credential・locked・suspended など）
                                                        └ 成功：Cookie（sukusuku_session）と SessionUser
TopScreen ◀──SessionUser── setUser ──▶ /password-change ・ /terms-agree ・ /staff ・ /guardian
```

## コードを読む

### 1. ログインの前の守り（server/api_auth.go 29〜57行）

```go
func (a *app) handleLogin(w http.ResponseWriter, r *http.Request) {
	/*
	 * ログイン中のセッションがある場合は認証を成立させず、既存のセッションを維持したまま、
	 * ログアウトを促して終了する。新しいセッションは作らない。上書きログインは設けない
	 * （基本設計書「ログイン」(4-3)、要件定義書「同時ログインの扱い」(4-1-1)）。
	 * 画面（TopScreen）もログイン中は入力欄を出さないが、ログインより前に開いておいた別のタブからは
	 * 送れてしまうため、サーバで止める（GitHub Issue #159）。案内にログイン中の氏名・ロールは出さない。
	 * 自動ログアウトで切れたセッションは、ログイン中とみなさない（GitHub Issue #210）
	 */
	if _, ok := a.sessionAccount(r); ok {
		writeAlreadyLoggedIn(w)
		return
	}
	var req loginRequest
	if !readJSON(w, r, &req) {
		return
	}
	// アカウントのロールが、使われた入口の系統と一致するかを判定する（基本設計書「ログイン」(4-3)）。
	// 入口が職員用・保護者用のどちらでもない要求は、判定ができないため受け付けない
	if req.Entrance != "staff" && req.Entrance != "guardian" {
		writeErr(w, http.StatusBadRequest, "入口の指定が正しくありません。職員用または保護者用のトップからログインしてください")
		return
	}
	// 送信元の失敗が上限を超えていたら、照合せずに断る（attempts.go。GitHub Issue #236 の 6）
	if a.guard().blocked(r) {
		writeTooManyAttempts(w)
		return
	}
	maxFailed := a.settingInt("auth.max_failed_login", 5)
```

**解説**
- まず、いまログイン中かを見る（38〜41行）。ログイン中なら新しいログインを成立させず、409 で「先にログアウトしてください」と返す。上書きのログインは設けない（基本設計書「ログイン」(4-3)、要件定義書「同時ログインの扱い」(4-1-1)）。
- 画面もログイン中は入力欄を出さない（TopScreen.tsx 34行）。ただし、ログインより前に開いておいた別のタブからは送れてしまう。そのためサーバでも止める（GitHub Issue #159）。
- この応答（`writeAlreadyLoggedIn`、670〜675行）には、ログイン中の人の氏名もロールも入れない。共有の端末で、前に使った人を第三者に見せないためだ。
- 入口の値が `staff`・`guardian` のどちらでもなければ、400 で断る（48〜51行）。入口とロールを比べる判定ができないためだ。
- 送信元の失敗が上限を超えていたら、アカウントを引く前に 429 で断る（53〜56行。下の 3）。
- ロックまでの回数は、設定 `auth.max_failed_login`（既定 5）から読む（57行）。

### 2. 存在しないログインIDでも、同じ文・同じ時間で返す（server/api_auth.go 69〜103行）

```go

		// 存在しないIDのときと同じだけ時間をかける（GitHub Issue #236 の 7）
		checkPassword(dummyPasswordHash(), req.Password)
		a.guard().failed(r)
		writeLocked(w)
		return
	}
```

**解説**
- メールアドレスで `m_account`（アカウントの表）を引く（69〜72行）。
- 見つからないとき（74〜91行）も、実在のアカウントと同じ文「ログインIDまたはパスワードが違います」を返す。
- パスワードの照合も1回行う（77行）。照合には bcrypt（わざと時間がかかるように作られたハッシュの方式）を使う。照合をせずにすぐ返すと、応答の速さで「このIDは無い」と分かってしまう（GitHub Issue #236 の 7）。照合の相手は、乱数から作ったダミーのハッシュだ（password.go 84〜96行の `dummyPasswordHash`）。どのパスワードとも一致しない。
- 画面には残りの回数を出す決まりがある（図/画面詳細図「職員用トップ／保護者用トップ」(2-1) 項目7）。存在しないIDだけ「残り 5 回」のまま減らないと、それで有無が分かる。そこで `unknownFailed` で回数を数え、実在のアカウントと同じ回数でロックを返す（81〜85行。GitHub Issue #159 の 5）。
- ロック中のアカウント（97〜103行）も、ダミーの照合で同じだけ時間をかけてから断る。
- ロックの応答（`writeLocked`、193〜199行）は、存在しないIDにも実在のIDにも同じものを返す。

### 3. 送信元ごとの上限と、存在しないIDの回数（server/attempts.go 115〜181行）

```go
// blocked は、送信元が失敗の上限を超えているかを返す
func (g *attemptGuard) blocked(r *http.Request) bool {
	g.mu.Lock()
	defer g.mu.Unlock()
	f, ok := g.ips[clientIP(r)]
	if !ok {
		return false
	}
	if time.Since(f.since) > ipFailureWindow {
		delete(g.ips, clientIP(r))
		return false
	}
	return f.count >= ipFailureLimit
}
// …（略）…
func (g *attemptGuard) unknownFailed(email string, maxFailed, lockMinutes int) (locked bool, remaining int) {
	g.mu.Lock()
	defer g.mu.Unlock()
	now := time.Now()
	// 1日以上失敗の無いものは掃除する
	for k, u := range g.unknown {
		if now.Sub(u.lastFailed) > 24*time.Hour && now.After(u.lockedUntil) {
			delete(g.unknown, k)
		}
	}
	key := strings.ToLower(email)
	u, ok := g.unknown[key]
	if !ok {
		u = &unknownLogin{}
		g.unknown[key] = u
	}
	u.lastFailed = now
	if now.Before(u.lockedUntil) {
		return true, 0
	}
	u.count++
	if u.count >= maxFailed {
		u.lockedUntil = now.Add(time.Duration(lockMinutes) * time.Minute)
		return true, 0
	}
	return false, maxFailed - u.count
}
```

**解説**
- ロックはアカウントの単位だ。それだけでは、ログインIDを替えながらの総当たりと、招待コードの総当たり（未ログインで呼べる）を止められない。そこで送信元の IP アドレスごとに失敗を数える（ファイルの冒頭 11〜25行の説明）。
- `blocked`（115〜128行）は、15分のうちの失敗が 20 回に達していれば真を返す。15分を過ぎたら数え直す。20 回・15分は【仮置き】で、設計に定めが無い（24〜30行、`web/仮置き値.md`）。
- 数えるのは失敗だけだ（`failed`、130〜148行）。園の端末が同じ IP から出るとき、朝に職員がそろってログインしても止めないためだ。
- `unknownFailed`（155〜181行）は、存在しないIDへの失敗を、メールアドレスを小文字にしたものごとに数える。上限に達したら、ロックの分数（`auth.lock_minutes`）のあいだロック中にする。ロックが明けても回数は戻さない。実在のアカウントも、成功するまで回数を戻さないからだ（153行）。
- 回数はメモリだけに持つ。アカウントの行が無いので、`m_account` には書けないからだ。サーバを起動し直すと消える（22行）。
- 送信元の IP は `clientIP`（83〜95行）が決める。公開先では、前段の Caddy（リバースプロキシ。外からの要求を受けて Go サーバへ渡すサーバ）を通る。そこで、相手がループバック（127.0.0.1 など）のときだけ、`X-Forwarded-For` のいちばん右の値を使う。
- モックには送信元が無いので、この上限を持たない（mock.ts 737行の注記）。存在しないIDの回数だけを持つ（下の 7）。

### 4. パスワードの照合と、失敗の記録（server/api_auth.go 105〜133行）

```go
	if !checkPassword(hash, req.Password) {
		a.guard().failed(r)
		failedCount++
		/*
		 * ログインの失敗と、失敗が続いたことによるロックを操作ログに残す（GitHub Issue #115）。
		 * 不正な試行に気づくための記録である。成功とログアウトは残さない。誰が記録したかは、
		 * 各操作の記録で追えるため（基本設計書「共通基盤：ログインとアカウント」(4-3)）。
		 * ログインできていないので、操作者は確かめられない。操作者の欄には、試された
		 * アカウントを入れる（本人とは限らない）。存在しないログインIDへの試行は、入れる先の
		 * アカウントが無いため残らない。
		 */
		attempt := "続けて " + strconv.Itoa(failedCount) + " 回目"
		if failedCount >= maxFailed {
			lockMinutes := a.settingInt("auth.lock_minutes", 30)
			a.db.Exec(`UPDATE m_account SET failed_login_count = ?, locked_until = ? WHERE account_id = ?`,
				failedCount, fromNowMinutes(lockMinutes), accountID)
			a.log(accountID, fnAccount, opUpdate, "m_account", i64(accountID), nil, nil,
				s("ログインに失敗（"+attempt+"）。失敗が続いたためロック"))
			writeLocked(w)
			return
		}
		a.db.Exec(`UPDATE m_account SET failed_login_count = ? WHERE account_id = ?`, failedCount, accountID)
		a.log(accountID, fnAccount, opUpdate, "m_account", i64(accountID), nil, nil, s("ログインに失敗（"+attempt+"）"))
		writeJSON(w, http.StatusUnauthorized, apiError{
			Kind: "credential", Remaining: maxFailed - failedCount,
			Message: "ログインIDまたはパスワードが違います",
		})
		return
	}
```

**解説**
- 照合に失敗したら、送信元の失敗を1回数え（106行）、アカウントの失敗の回数を1つ増やす（107行）。
- 回数が上限に達したら、`locked_until` に「いま＋ロックの分数」を書き、ロックの応答を返す（117〜125行）。
- 上限の前なら、残りの回数を `Remaining` に入れて返す（128〜131行）。画面はこれを「残り N 回」と出す。
- 失敗とロックは、操作ログ（だれが・いつ・何をしたかを、追記だけで残す表）に残す（GitHub Issue #115）。不正な試行に気づくためだ。成功とログアウトは残さない。
- ログインできていないので、操作者は確かめられない。操作者の欄には、試されたアカウントを入れる（本人とは限らない）。存在しないIDへの試行は、入れる先が無いので残らない（112〜114行）。
- 操作ログの書き方（`a.log`）は [01 全体の仕組み](./01-全体の仕組み.md) にある。

**解説**
- 停止中かの判定は、パスワードの照合のあとに置く（135〜139行の注記）。照合の前に置くと、パスワードを知らない人にも「停止中のアカウントがある」と分かってしまう。2 と同じ「あるかどうかを推測させない」考え方だ（GitHub Issue #159）。
- 入口の系統を確かめる（147〜162行）。職員のアカウントを保護者用の入口で使うと、ログインを成立させずに、正しい入口を案内する（図/画面詳細図「職員用トップ／保護者用トップ」(2-1)）。`Correct` に正しい入口を入れて返し、画面はそこへのリンクを出す（TopScreen.tsx 133〜143行）。
- 一時パスワードの期限を確かめる（169〜174行）。期限切れはロックとは別の状態だ。待っても解けず、管理者が再発行する（基本設計書「ログイン」(4-3)）。

### 9. ログイン中かの判定と、自動ログアウト（server/session.go 214〜258行）

```go
func (a *app) sessionAccount(r *http.Request) (int64, bool) {
	id := sessionID(r)
	sess, ok := a.sessions.lookup(id)
	if !ok {
		return 0, false
	}
	if !sess.idleLogout {
		return sess.accountID, true
	}
	at := a.sessions.now()
	// 最後の操作から時間内なら、午睡チェックの実施を確かめるまでもなく使える（要求のたびにデータベースを引かない）
	if !at.After(sess.lastActiveAt.Add(a.idleLimit())) {
		return sess.accountID, true
	}
	deadline, napActive := a.idleDeadline(sess, at)
	if napActive || !at.After(deadline) {
		return sess.accountID, true
	}
	a.sessions.drop(id)
	return 0, false
}
// …（略）…
func (a *app) idleDeadline(sess session, at time.Time) (deadline time.Time, napActive bool) {
	active, endedAt := a.napExemption(sess.accountID, sess.lastActiveAt, at)
	if active {
		return time.Time{}, true
	}
	from := sess.lastActiveAt
	if endedAt.After(from) {
		from = endedAt
	}
	return from.Add(a.idleLimit()), false
}
```

**解説**
- `sessionAccount` は、要求のセッションがいま使えるかを判定する。ログインの入口（上の 1）・ログアウト（上の 8）・新規登録（下の 14）・`requireLogin` が使う。
- まず `lookup` でセッションを引く（216〜219行）。無いものと、ログインを保つ上限（`expiresAt`）を過ぎたものは使えない（148〜158行）。
- 保護者のセッションは、無操作では切らない（220〜222行）。
- 職員は、最後の操作から `ui.auto_logout_minutes`（既定 30 分）の内なら、そのまま通す（224〜227行）。要求のたびにデータベースを引かないためだ。設定を変えると、ログイン中のセッションにもその場で効く（209〜210行）。
- 時間を過ぎていたら、その職員が始めた午睡チェックが実施中かを確かめる（228〜231行）。実施中なら切らない（基本設計書「午睡チェックの実施」(4-7)、要件定義書「午睡チェック中の例外」(4-1-4 (4))）。
- 実施が終わっていたら、終わった時刻から数え直す（`idleDeadline`、253〜256行）。実施中に操作が無くても、終わった直後に切れないようにするためだ（211〜213行）。終了を押し忘れた実施は、午睡の時間帯（`nap.time_range`）の終わりで解除したものとして数える（`napExemption`、260〜307行）。
- 切れていたら、セッションを消す（232行）。切れたあとに操作しても、つながり直さない。
- 最後の操作の時刻は、`requireLogin` が操作のたびに進める（480〜482行）。画面の5秒ごとの読み直し・知らせの受け取り・期限の問い合わせは、操作に数えない（194〜204行の `countsAsOperation`。基本設計書「ログイン」(4-3)）。
- 自動で切れたセッションは「ログイン中」とみなさない。そのため、切れたあとは入口から入り直せる（api_auth.go 36行の注記。GitHub Issue #210）。

### 10. 自動ログアウトの期限を返す（server/api_session.go 56〜76行）

```go
func (a *app) sessionStatusOf(r *http.Request) SessionStatus {
	sess, ok := a.sessions.lookup(sessionID(r))
	if !ok || !sess.idleLogout {
		return SessionStatus{}
	}
	at := a.sessions.now()
	deadline, napActive := a.idleDeadline(sess, at)
	if napActive {
		return SessionStatus{AutoLogout: true, NapExempt: true}
	}
	// ログインを保つ上限（「ログイン情報の記憶」の保存期間）が先に来るときは、そちらで切れる
	if deadline.After(sess.expiresAt) {
		deadline = sess.expiresAt
	}
	remaining := int64(deadline.Sub(at) / time.Second)
	if remaining < 0 {
		remaining = 0
	}
	expiresAt := deadline.In(jst).Format("2006-01-02T15:04:05")
	return SessionStatus{AutoLogout: true, ExpiresAt: &expiresAt, RemainingSeconds: &remaining}
}
```

**解説**
- 職員の画面は、最後の操作から設定 `ui.auto_logout_minutes`（既定 30 分）が過ぎたら切れる（基本設計書「ログイン」(4-3)）。切れるかどうかの判定は、上の 9 の `sessionAccount` だ。
- `sessionStatusOf` は、切れる時刻と残りの秒数を画面へ返す。判定と同じ `idleDeadline`（session.go 248〜258行）で求めるので、返す時刻と実際に切れる時刻がずれない（62行）。

- その職員が始めた午睡チェックが実施中なら、切らない。期限も返さない（63〜65行。基本設計書「午睡チェックの実施」(4-7)）。

- 画面の `SessionTimeoutWarning` は、この値を尋ねて、切れる2分前に「まもなくログアウトします」と「続ける」を出す（SessionTimeoutWarning.tsx 32〜33行・77〜89行）。2分は【仮置き】だ。
- 尋ねるだけでは、期限を延ばさない。`GET /api/session` は操作に数えない（session.go 194〜204行の `sessionStatusPath`・`countsAsOperation`）。「続ける」は `POST /api/session/extend` で、操作として延ばす（api_session.go 47〜53行）。
- モックも同じ規則を持つ（mock.ts 5619〜5708行の `idleSessionStatus` ほか）。ただし、モックはほかの API を期限で拒まない（5631行の注記）。

### 11. 手続きを終えるまで、ほかの機能を止める（server/session.go 486〜510行）

```go
// requireUser はログイン中の利用者を取り出す。未ログインなら 401 を返す。
// 一時パスワード中・規約の再同意が必要な間は、手続きを終えるまで 403 を返す。
// 状態は毎回データベースから読む。ログイン中に一時パスワードを発行し直されたときも、その時点から止めるため
func (a *app) requireUser(w http.ResponseWriter, r *http.Request) (*SessionUser, bool) {
	u, ok := a.requireLogin(w, r)
	if !ok {
		return nil, false
	}
	// 両方が要るときはパスワードの変更を先に求める。画面（TopScreen）が案内する順と同じ
	switch {
	case u.IsTempPassword:
		writeJSON(w, http.StatusForbidden, apiError{
			Kind:    kindPasswordChangeRequired,
			Message: "一時パスワードのままでは、ほかの機能は利用できません。パスワードを変更してください",
		})
		return nil, false
	case !u.TermsAgreed:
		writeJSON(w, http.StatusForbidden, apiError{
			Kind:    kindTermsAgreementRequired,
			Message: "利用規約に同意するまで、ほかの機能は利用できません。利用規約をご確認ください",
		})
		return nil, false
	}
	return u, true
}
```

**解説**
- `requireUser` は、多くの API の入口で使う確かめだ。職員だけ・管理者だけの確かめ（`requireStaff`・`requireAdmin`）も、これを通る。先に `requireLogin`（ログイン中か・停止中でないか）を通す。`requireLogin` の中身は [01 全体の仕組み](./01-全体の仕組み.md) を見る。
- 一時パスワードのままなら、403 と `password_change_required` を返す（496〜501行）。規約に同意していなければ、`terms_agreement_required` を返す（502〜507行）。
- 両方が要るときは、パスワードの変更を先に求める（494行）。画面の案内の順と同じだ。
- 状態は毎回データベースから読む（488行）。ログイン中に管理者が一時パスワードを発行し直したときも、その時点から止まる。
- 画面の出し分け（App.tsx の `RequireStaff`・`RequireGuardian`）だけでは、API を直接呼べば通ってしまう。そのためサーバで拒む（基本設計書「権限チェックの実装方針」(6-2)。GitHub Issue #153）。
- 手続きの画面が呼ぶ API だけは、`requireLogin` で通す。`GET /api/me`・`POST /api/password`・`POST /api/terms/agree` の3つだ（session.go 398〜403行）。
- 画面は 403 の `kind` を受けると、利用者を読み直して、手続きの画面へ案内する（http.ts 144〜147行 → App.tsx 184〜189行）。
- 強制の経路 `/password-change`・`/terms-agree` は、`RequireProcedure`（App.tsx 134〜149行）が受ける。手続きが残っている人だけに、強制の画面を出す。残っていない人は、メニューから開く任意の画面へ送る。
- 規約への同意（`handleAgreeTerms`、api_auth.go 304〜341行）は、アカウントの印と同意の履歴（`t_terms_agreement`）を、1つの取引（トランザクション。いくつかの書き込みを「全部するか、全部しないか」にまとめる仕組み）で書く。履歴が欠けたまま同意済みになると、いつ・どの版に同意したかを示せなくなるためだ（GitHub Issue #99）。履歴は追記だけで、前の版の行は消さない（基本設計書「同意履歴（t_terms_agreement）」(5-2)）。
- 同意の画面は、初めてログインした人にも出る。そのため「改定しました」とだけ書かない（TermsAgreeScreen.tsx 62〜66行。GitHub Issue #126）。「同意せずログアウトする」も置く（76〜82行）。

- 強制の画面には「変更せずログアウトする」も置く（72〜76行・101〜103行。GitHub Issue #178 の 4）。ヘッダもメニューも無い画面から抜けられるようにするためだ。
- モックの `changePassword`（mock.ts 803〜819行）も同じ検査をする。モックは端末を区別できないので、ほかの端末を切る扱いは無い（mock.ts 5612〜5613行の注記）。

### 13. 招待コードを照合する（server/api_auth.go 391〜421行）

```go
func (a *app) lookupUsableCode(code string) (usableCode, error) {
	var out usableCode
	normalized := normalizeInvitationCode(code)

	var status, expiresOn string
	err := a.db.QueryRow(`SELECT invitation_code_id, child_id, status, expires_on
	                        FROM t_invitation_code WHERE REPLACE(UPPER(code), '-', '') = ?`, normalized).
		Scan(&out.ID, &out.ChildID, &status, &expiresOn)
	if errors.Is(err, sql.ErrNoRows) {
		return out, errors.New(msgInvitationNotFound)
	}
	if err != nil {
		return out, errors.New("招待コードの確認に失敗しました")
	}
	// 取り消した（誤登録）・在籍していない園児のコードでは登録させない。発行のあとで園児を取り消しても、
	// 配ったコードで、その園児に紐づく保護者アカウントができてしまうため（GitHub Issue #166 の 4）。
	// 園児の状態は言わず、無いコードと同じ文言にする。取消は未使用のコードを失効（3）にするので
	// （GitHub Issue #279）、コードの状態より先に見る。後に見ると「失効しています」と出て、取り消したことが分かる
	if _, issuable := a.childIssuable(out.ChildID); !issuable {
		return out, errors.New(msgInvitationNotFound)
	}
	switch {
	case status == "2":
		return out, errors.New(msgInvitationUsed)
	case status == "3":
		return out, errors.New(msgInvitationRevoked)
	case expiresOn < today():
		return out, errors.New(msgInvitationExpired)
	}
	return out, nil
}
```

**解説**
- 入力は、先に照合用の形に直す（393行）。大文字・小文字を区別せず、ハイフンと空白を除く（`normalizeInvitationCode`、358〜367行。基本設計書「招待コード（t_invitation_code）」(5-2)）。画面側の `web/src/api/util.ts` 212〜214行も同じ規則だ。
- 使えない理由は、4つの文のどれかを返す。「見つからない」「使用済み」「失効」「期限切れ」だ（基本設計書「メッセージ一覧」(4-12)。決めたこと D-52）。文の中身は `server/messages.go` にある。
- 取り消した園児・在籍していない園児のコードは、「見つからない」と同じ文にする（409〜411行。GitHub Issue #166 の 4）。園児の状態を言わないためだ。
- この判定は、コードの状態より先に置く。園児を取り消すと、未使用のコードは失効になる（GitHub Issue #279）。後に置くと「失効しています」と出て、取り消したことが分かってしまう（407〜408行）。
- 新規登録のコードの確認（`handleVerifyInvitationCode`、427〜450行）・新規登録の送信・お子さまの追加は、どれもこの関数を通る。だから同じ文を返す。
- コードの確認は、未ログインで呼べる。そのため、送信元ごとの失敗の上限を当てる（435〜438行）。コードの総当たりを止めるためだ（GitHub Issue #236 の 6）。
- ログインしていない人には、園児名を返さない（449行）。誰の保護者かを名乗る前の段階だからだ（図/画面詳細図「新規登録画面（保護者）」(2-3)）。
- モックは `usableInvitationCode`（mock.ts 4048〜4060行）が、同じ順で判定する。

### 14. 新規登録の守り（server/api_auth.go 474〜584行）

```go
func (a *app) handleSignUpGuardian(w http.ResponseWriter, r *http.Request) {
	// ログイン中は新しいアカウントを作らせない。登録が成立するとセッションが新しい保護者に置き換わり、
	// 上書きログインと同じことになる（基本設計書「ログイン」(4-3)。GitHub Issue #159）
	if _, ok := a.sessionAccount(r); ok {
		writeAlreadyLoggedIn(w)
		return
	}
	// …（略）…
	code, err := a.lookupUsableCode(req.Code)
	if err != nil {
		a.guard().failed(r)
		writeErr(w, http.StatusBadRequest, err.Error())
		return
	}
	// …（略）…
	if !req.TermsAgreed {
		writeErr(w, http.StatusBadRequest, termsNotAgreedMessage)
		return
	}
	if req.TermsVersion != a.currentTermsVersion {
		writeErr(w, http.StatusBadRequest, termsOutdatedMessage)
		return
	}
	// …（略）…
	if a.emailTaken(req.Email) {
		writeErr(w, http.StatusBadRequest, "このメールアドレスはすでに登録されています")
		return
	}
	// …（略）…
	res, err := tx.Exec(`UPDATE t_invitation_code SET status = '2', used_at = ?
		WHERE invitation_code_id = ? AND status = '1' AND expires_on >= ?`, now(), code.ID, today())
	if err != nil {
		writeErr(w, http.StatusInternalServerError, "登録に失敗しました")
		return
	}
	if n, _ := res.RowsAffected(); n != 1 {
		// 同じコードを同時に送ったときの2つ目。文言は基本設計書「メッセージ一覧」(4-12)「招待コードが使用済み」による
		writeErr(w, http.StatusBadRequest, msgInvitationUsed)
		return
	}
```

**解説**
- ログイン中は、新しいアカウントを作らせない（475〜480行）。登録が成立するとセッションが新しい保護者に入れ替わり、上書きのログインと同じことになるためだ（GitHub Issue #159）。
- 招待コードの検査は、コードの確認と同じ `lookupUsableCode` を通す（492〜497行）。
- 規約への同意を、サーバでも受け取って確かめる（505〜508行）。画面のチェックだけで止めると、API を直接呼んだ登録にも同意の記録が付いてしまう（GitHub Issue #170）。
- 同意した版が、いま有効な版と違えば断る（509〜512行）。画面に出していた規約が、送るまでのあいだに改定されていたら、読んでいない版に同意したことになるためだ。画面（SignUpScreen.tsx 90〜98行）は、そのとき改定後の本文を出し直し、同意のチェックを外す。
- ログインIDは、ロールをまたいで園内で一意だ。大文字・小文字だけが違うメールアドレスも、同じとみなす（524〜527行。判定は api_admin.go の `emailTaken`）。
- 招待コードは、取引の中で「未使用なら使用済みにする」条件付きの更新で押さえる（574〜584行）。同じコードを同時に送っても、更新できた1つだけが登録へ進む（GitHub Issue #163）。1枚のコードは、1アカウントの登録にだけ使える（基本設計書「招待コード（t_invitation_code）」(5-2)）。
- そのあと同じ取引で、アカウント・同意の履歴・保護者・紐づけを書く。個人チャット・いまのクラスのクラスグループ・園全体のチャットへも入れる（586〜645行）。
- 登録が済むと、そのままログインした状態にする（657行）。保護者なので、自動ログアウトは課さない。
- 気をつけるところ：「このメールアドレスはすでに登録されています」（525行）は、登録済みかどうかを教える文だ。ただし、この検査は、使える招待コードの照合と規約の確認のあとにある。コードを持たない人は、ここまで届かない。
- 画面（SignUpScreen.tsx）は、コードを確認するまで (2)(3) を操作できなくする（138〜154行）。続柄の初期値は未選択だ（44行）。送る前に画面でも氏名・続柄・メール・パスワードを確かめるが、担保はサーバだ（66〜76行）。
- モックの `signUpGuardian`（mock.ts 4076〜4160行）も、同じ順に確かめる。コードを使用済みにするまで `await` を挟まずに進め、ほかの登録が割り込まないようにしている（4083〜4087行）。

## 気をつけているところ

- **あるかどうかを推測させない。**
  - 存在しないIDでも、同じ文・同じ残りの回数・同じロック・同じ時間（ダミーの照合）で返す（api_auth.go 74〜91行、attempts.go 155〜181行）。
  - ロック中のアカウントにも、同じだけ時間をかける（api_auth.go 97〜103行）。
  - 停止中かは、パスワードの照合のあとで判定する（api_auth.go 135〜145行）。
  - ログイン中の案内に、前の利用者の氏名・ロールを出さない（api_auth.go 667〜675行、TopScreen.tsx 108〜127行）。
  - 取り消した園児の招待コードは、「見つからない」と同じ文にする（api_auth.go 405〜411行）。未ログインのコードの確認には、園児名を返さない（449行）。
- **総当たりの止め方は3段ある。** アカウントのロック（`auth.max_failed_login` 回・`auth.lock_minutes` 分）、存在しないIDの回数、送信元ごとの上限（15分に 20 回。【仮置き】）だ。
- **権限の担保はサーバだ。** 手続きの途中の拒否（`requireUser`）も、ログイン中の新しいログインの拒否も、サーバで行う。画面の出し分けは操作性のためだ（基本設計書「権限チェックの実装方針」(6-2)）。
- **業務の規則はサーバとモックの2か所にある。** ログインの判定の順・存在しないIDの回数・招待コードの4つの文・新規登録の検査・手続きの拒否・自動ログアウトの期限は、どれも両方にある。モックに無いのは、送信元の上限、ログイン中の新しいログインの拒否、ほかの端末のセッションを切る扱いだ。どれもモックに送信元やセッションが無いためだ。
- **セッションを切る場面。** パスワードの変更（ほかの端末）、一時パスワードの再発行、アカウントの停止、紐づけの解除だ（session.go 317〜340行の `destroyAccount`）。画面は 401 を受けて入口へ戻る（http.ts 161〜164行 → App.tsx 191〜209行）。
- **パスワードは平文で持たない。** bcrypt でハッシュにする。72 バイトを超えるものは、SHA-256 の要約にしてから渡す（password.go 57〜82行）。ハッシュの方式そのものが【仮置き】だ。
- **【仮置き】の主なもの。** 送信元ごとの上限、よく使われるパスワードの一覧、記憶を付けないときのログインの上限（30日）、予告を出す時刻（2分前）、規約が送るまでに改定されたときの文。一覧は `web/仮置き値.md` にある。
