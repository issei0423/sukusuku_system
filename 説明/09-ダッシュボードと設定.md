# 09 ダッシュボードと設定

> この説明は commit 74f09acf のコードで書いた。行番号はその版のもの。

## この機能でできること

- 職員は、ログインした直後の職員ダッシュボードで、残っている仕事の件数を見る。「届けること」（家庭からの連絡・園からのひとこと・午睡中の園児）と「園内のこと」（日誌・チャット・発達チェック・異常時の記録）に分かれ、各行の「開く」で、その仕事の画面へ移る。
- 保護者は、ログインした直後の保護者ホームで、お子さまごとの「きょう」（連絡帳の要約と新しい件数）と、連絡帳・成長の記録・チャット・配布物への入口を見る。
- 管理者は、設定画面で、連絡帳・AI の下書き・そのほかの設定値を変える。変えた値はまとめて1回で保存し、操作ログに残る。
- 管理者は、設定画面の AI の区画で、文章の下書き（AI）を使うかと、1日の上限回数を決める。サーバに API キーが無ければ、AI のボタンはどの画面にも出ない。

要求を受ける仕組み（ログイン・権限の共通の関数・知らせ）は [01 全体の仕組み](./01-全体の仕組み.md) を見る。ダッシュボードが数える個々の仕事の中身は、各機能の説明（[03 連絡帳](./03-連絡帳.md)・[04 午睡チェック](./04-午睡チェック.md)・[05 日誌](./05-日誌.md)・[06 チャットと配布物](./06-チャットと配布物.md)・[07 成長の記録](./07-成長の記録.md)）を見る。

## 流れ

管理者が設定を変え、それが発達チェック一覧とダッシュボードの「予定日が近い」に効くまでを例にする。

1. 管理者が設定画面で「発達チェックの予定日が近いとする日数」を 7 から 14 に変え、「保存する」を押す。確認の窓で変更の前後を見てから、もう一度「保存する」を押す。
2. 画面は `api.saveSettings` を呼ぶ（本番は `POST /api/settings`）。送るのは変えたキーだけと、設定を読んだ時刻（`read_at`）である。
3. サーバの `handleSaveSettings` が、管理者か・変えてよいキーか・値が正しいかを確かめる。1つでも誤りがあれば何も書かない。
4. トランザクションの中で `m_setting` を書く。ほかの管理者が読んだあとに変えていれば 409 にする。変わったキーごとに操作ログを残す。
5. 設定を読む側（`settingInt` など）は、呼ばれるたびに `m_setting` を読む。そのため次に一覧やダッシュボードを開いたときから、新しい値が効く。

```
設定画面（管理者）                       Go サーバ
SettingsForm ─POST /api/settings─▶ handleSaveSettings
  （変えたキーと read_at）            ├ requireAdmin・editable か・settingSpecs の検査・下限 < 上限
                                      ├ m_setting を書く（読んだあとに変わっていたら 409）
                                      └ 操作ログ（キーごとに前と後）
                                               ↓ 次に読むとき
職員ダッシュボード ─GET /api/dashboard/staff─▶ handleStaffSummary
                                      └ settingInt("dev.notice_days_before") → devNear で数える
```

**解説**
- 承認待ちの日誌は、管理者だけに数える。そのうち自分が申請した数も返す。自分の申請は自分で承認できないので、画面は「ほかの管理者へ」と添える（図/画面詳細図「職員ダッシュボード」(2-6) 項目8。GitHub Issue #268）。
- 誤送信への対応を記録していない取り消しも、管理者だけに数える。記録するのが管理者だからである（図/画面詳細図「誤送信対応記録画面（管理者）」(4-4)。GitHub Issue #141）。この行は職員ダッシュボードの項目表に無いので【仮置き】である。
- 数え損ねたときは 0 件を返さず、500 にする。「0 件」は「漏れなし」と読まれるからである。未対応の個人チャットも同じ扱いである（`unhandledPersonalChats`、201〜240行）。
- 差し戻された日誌は、逆に一般の職員だけに数える（22〜31行）。開いた先の日誌一覧と同じ範囲（自分が書いて差し戻されたもの・参照範囲の中）を数える（GitHub Issue #174）。

### 2. 「届けること」を数える（server/api_dashboard.go 81〜116行）

```go
	// 家庭からの「未確認」「更新」と、おひるね中の園児（詳細設計書「ダッシュボード」(4-8 (2))）。今日のページだけを数える。
	// 一般は自クラス、管理者は全クラス（visibleChildren の範囲）
	homeUnconfirmed, homeRevised, napSleeping := 0, 0, 0
	// 園からのひとことを送っていない園児：在籍中で、今日の取り消していない園からが無い園児。
	// 今日の午睡で「きょうは対象外（欠席）」にした子は数えない（詳細設計書 (4-8 (2))、基本設計書「届いていない家庭の一覧」(4-5)）
	facilityUnsent := 0
	for _, c := range children {
		if c.EnrollmentStatus == "1" {
			var sent, absent int
			a.db.QueryRow(`SELECT COUNT(*) FROM t_contact_facility WHERE child_id = ? AND contact_date = ? AND is_deleted = 0`,
				c.ChildID, today()).Scan(&sent)
			a.db.QueryRow(`SELECT COUNT(*) FROM t_nap_exclusion x JOIN t_nap_session n ON n.nap_session_id = x.nap_session_id
				WHERE x.child_id = ? AND x.reason = '1' AND x.is_deleted = 0 AND n.session_date = ?`, c.ChildID, today()).Scan(&absent)
			if sent == 0 && absent == 0 {
				facilityUnsent++
			}
		}
		h, err := a.loadContactHome(c.ChildID, today())
		if err != nil {
			writeErr(w, http.StatusInternalServerError, "集計に失敗しました")
			return
		}
		switch homeState(h) {
		case "unconfirmed":
			homeUnconfirmed++
		case "revised":
			homeRevised++
		}
		var sleeping int
		a.db.QueryRow(`SELECT COUNT(*) FROM t_nap_sleep s JOIN t_nap_session n ON n.nap_session_id = s.nap_session_id
			WHERE s.child_id = ? AND s.woke_at IS NULL AND s.is_deleted = 0 AND n.ended_at IS NULL AND n.session_date = ?`,
			c.ChildID, today()).Scan(&sleeping)
		if sleeping > 0 {
			napSleeping++
		}
	}
```

**解説**
- 3つの数は、見える園児（`visibleChildren`）を1人ずつ見て数える。どれも今日のページだけである（詳細設計書「ダッシュボード」(4-8 (2))）。
- 園からのひとことを送っていない園児は、在籍中で、今日の取り消していない園からのひとことが無い園児である。今日の午睡で「きょうは対象外（欠席）」にした子は数えない（基本設計書「届いていない家庭の一覧」(4-5)）。
- 家庭からの「未確認」「更新」は、連絡帳と同じ `homeState`（[server/api_contact.go](../server/api_contact.go) 457行）で決める。連絡帳（クラス）画面の印と同じ数になる。
- 午睡中は、今日の終わっていない午睡で、まだ「おきた」が無い園児である。
- 発達チェックの未実施と予定日が近いは、このあと（118〜148行）で数える。判定は発達チェック一覧と同じ `devOverdue`・`devNear` を呼ぶ（[07 成長の記録](./07-成長の記録.md) の 2.）。「近い」の日数は設定 `dev.notice_days_before` を、開くたびに読む。
- モックの `staffSummary`（[web/src/api/mock.ts](../web/src/api/mock.ts) 4399〜4473行）が同じ数え方を持つ。

### 4. 保護者ホームは保護者だけ（server/api_dashboard.go 242〜260行）

```go

func (a *app) handleGuardianHome(w http.ResponseWriter, r *http.Request) {
	u, ok := a.requireUser(w, r)
	if !ok {

		API キーはサーバの環境変数 ANTHROPIC_API_KEY だけに置く（基本設計書「API キーの置き場所」(6-3)）。
		キーそのものはログ・画面・データベースに出さない。無ければ AI のボタンを出さず、ほかはすべて動く（8-8）
	*/
	if key := strings.TrimSpace(os.Getenv("ANTHROPIC_API_KEY")); key != "" {
		a.ai = newClaudeWriter(key, *aiModel)
		log.Printf("AI の下書き：API キーがあります（モデル %s）。使うかは設定画面の AI の区画で決めます", *aiModel)
	} else {
		log.Printf("AI の下書き：API キーが無いため使いません（環境変数 ANTHROPIC_API_KEY）")
	}
```

**解説**
- API キーは、サーバの環境変数 `ANTHROPIC_API_KEY` だけに置く（基本設計書「API キーの置き場所」(6-3)）。画面・DB・ログには出さない。
- キーがあれば本物の口（`newClaudeWriter`、[server/ai_claude.go](../server/ai_claude.go) 42〜48行）を作って `a.ai` に入れる。無ければ `a.ai` は `nil` のままで、AI だけが使えず、ほかはすべて動く（詳細設計書「キーが無い・無効・有効にしていないときの画面」(8-8)）。
- キーがあっても、すぐには使わない。使うかは設定 `ai.enabled`（既定 `0`）で管理者が決める。
- 口は `draftWriter` というインタフェース（[server/ai.go](../server/ai.go) 16〜19行）である。テストでは偽物の `fakeWriter`（`server/ai_test.go`）に差し替え、外部へは呼ばない。手元の CI（`agent-harness/api-agent/scripts/local-ci.sh`）と受け入れテストも、キーを渡さずに回す。
- モデルは既定で `claude-haiku-5-5` である（[server/ai_claude.go](../server/ai_claude.go) 31行）。起動の `-ai-model` か環境変数 `SUKUSUKU_AI_MODEL` で変えられる（[server/main.go](../server/main.go) 60〜61行。変える口は設計に無いので【仮置き】）。

設定画面の AI の区画（[AiSettings.tsx](../web/src/screens/admin/settings/AiSettings.tsx) 26〜27行）は、応答の `ai_key_present`（キーがあるか）と `ai_key_rejected`（キーが無効と分かったか）で注意を出し分ける。キーそのものは返さない（[server/api_settings.go](../server/api_settings.go) 42行）。

| サーバの状態 | 設定画面の AI の区画 | 連絡帳の AI のボタン |
| :-- | :-- | :-- |
| キーが無い | 「サーバに API キーがありません。AI の下書きは使えません。」。「使う」を選ぶと「API キーが無いあいだは、有効にしても使えません。」を添える | 出ない |
| キーがあり、`ai.enabled` が `0` | 注意は出ない | 出ない |
| キーがあり、`ai.enabled` が `1` | 注意は出ない | 宛先の子が条件を満たせば出る（10.） |
| 呼んだら 401・403 が返った | 「API キーが使えませんでした。サーバの設定を確かめて起動し直してください。」 | 出ない（起動し直すまで） |

### 10. AI を使える条件（サーバで確かめる）（server/api_ai.go 76〜100行）

```go
/*
aiAvailableFor は、その職員がその宛先に AI の下書きを使えるか（8-3）。/api/ai/status と /api/ai/drafts の両方が呼ぶ
（基本設計書「処理の流れ」(4-11) の「サーバでもう一度確かめる」）。

① m_setting の ai.enabled が 1 ② 呼び出し口があり、キーが無効と分かっていない ③ 職員で、宛先を Write できる
④ 宛先の園児が aiChildConsented。クラスあては在籍園児の全員が満たす。
上限に達したかはここに入れない（ボタンを出したまま、押したときに 429 で知らせる。決めたこと D-9）
*/
func (a *app) aiAvailableFor(u *SessionUser, t aiTarget) bool {
	if a.settingText("ai.enabled", "0") != "1" || !a.aiKeyUsable() || !u.isStaff() {
		return false
	}
	if t.isClass() {
		if !a.classContactAccess(u, t.ClassID).Write {
			return false
		}
		for _, id := range a.enrolledClassChildIDs(t.ClassID) {
			if !a.aiChildConsented(id) {
				return false
			}
		}
		return true
	}
	return a.contactAccess(u, t.ChildID).Write && a.aiChildConsented(t.ChildID)
}
```

**解説**
- 使えるのは、次の4つを全部満たすときだけである（詳細設計書「使える条件」(8-3)）。① 設定 `ai.enabled` が `1`。② 口があり、キーが無効と分かっていない（`aiKeyUsable`、72〜74行）。③ 職員で、宛先を書ける（園児あては `contactAccess`、クラスあては `classContactAccess` の Write）。④ 宛先の園児が `aiChildConsented` を満たす。クラスあては在籍園児の全員が満たす。
- `aiChildConsented`（42〜51行）は、有効な紐づけの保護者が1人以上いて、その全員が外部の AI を書いた版の規約に同意していて、誰も断っていない（`ai_opt_out`）ことである。保護者がまだ登録していない子には使わない。
- `GET /api/ai/status` と `POST /api/ai/drafts` の両方がこの関数を呼ぶ。ボタンを出すかの判定と、押したときの判定を同じにして、サーバでもう一度確かめる（基本設計書「処理の流れ」(4-11)）。
- `status` の応答は `available` の真偽だけで、理由は返さない。どの子の保護者が断ったかを見せないためである（22行のコメント）。
- 1日の上限に達したかは、ここに入れない。ボタンは出したまま、押したときに 429 で知らせる（決めたこと D-9）。上限は園全体で1つで、その日に成功した数と呼び出し中の数の合計で数える（`reserveAiCall`、384〜393行）。
- 呼んで 401・403 が返ったら `aiKeyRejected` を立て、起動し直すまで使えない扱いにする（`aiReadReply`、313〜318行。決めたこと D-11）。
- 送る前に、園児・保護者・職員の名前を置き換える（256〜264行の `anonymize`）。送った文・返った文・メモは、どのログにも出さない（288〜293行）。
- モックの `aiAvailableFor`（[web/src/api/mock.ts](../web/src/api/mock.ts) 6719〜6725行）が、関数の名前もそろえて同じ規則を持つ。モックは外部へつながず、`mockAi.keyPresent`（既定は真）がサーバの「キーがあって起動した」に当たる。

### 11. 画面は「使える」ときだけ部品を出す（web/src/components/AiDraftPanel.tsx 59〜70行）

```tsx
  // 使えるかを読む。読めないときは出さない（AI が無くても届けられる）
  const readStatus = () => api.aiStatus(user!, { child_id: childId })
    .then((r) => setAvailable(r.available)).catch(() => setAvailable(false));
  useEffect(() => {
    let alive = true;
    api.aiStatus(user!, { child_id: childId })
      .then((r) => { if (alive) setAvailable(r.available); })
      .catch(() => { if (alive) setAvailable(false); });
    return () => { alive = false; };
  }, [user, childId]);

  if (!available) return null;
```

**解説**
- 部品は、開いたときに `api.aiStatus` を読み、`available` が真のときだけ描く。偽か、読めなかったときは何も出さない。理由も出さない（6〜7行のコメント）。AI が無くても、職員は手で書いて送れる。
- 下書きを作るのに失敗したら、もう一度 `aiStatus` を読む（98〜99行）。キーが無効と分かったあとなら、ボタンが消える。
- 下書きは入力欄に入るだけで、送るのは職員が「送る」を押したときである。宛先の表示と他児の名前の照合は、ふだんの送信と同じに通る（1〜8行のコメント）。
- この部品は連絡帳の入力欄 `Composer`（[web/src/screens/contact/Composer.tsx](../web/src/screens/contact/Composer.tsx) 102〜103行）の下に出る。発達チェックの保護者へのひとことには出さない（[07 成長の記録](./07-成長の記録.md) の 8.）。

## 気をつけているところ

- **権限の担保はサーバにある。** ダッシュボードの管理者だけの数は、一般の職員には 0 を返す。保護者ホームは職員に 403。設定の読み書きは `requireAdmin`。AI の使える条件は、ボタンを出すときと押したときの両方でサーバが確かめる。画面の出し分けは使いやすさのためである（基本設計書「権限チェックの実装方針」(6-2)）。
- **「0 件」を嘘にしない。** 未対応の個人チャットと誤送信の数は、数え損ねたら 500 にする。0 件の行も消さずに出す。
- **件数を画面ごとに食い違わせない。** 発達チェックは一覧と同じ `devOverdue`・`devNear`、家庭からは連絡帳と同じ `homeState`、差し戻しは日誌一覧と同じ範囲で数える。
- **設定は全部か何もしないか。** 1つでも誤りがあれば書かない。ほかの管理者とぶつかったら 409 で読み直させる。値が変わったキーだけ操作ログに残す。
- **効かないキーを見分ける。** 保存できても、この版では読む処理が無いキーが7つある（`settingNoEffect`）。画面はその行に添え書きを出す。
- **API キーを外に出さない。** キーは環境変数だけ。応答はあるか・無効かの真偽だけ。テスト・手元の CI・受け入れテストはキーを渡さずに回す。
- **規則は2か所にある。** `handleStaffSummary`／`staffSummary`、`handleGuardianHome`／`guardianHome`、`settingSpecs`／`SETTING_SPECS`、`handleSaveSettings`／`saveSettings`、`aiAvailableFor`（同じ名前）。片方だけを直さない。
- **仮置きの値。** ダッシュボードの「対応の記録がない取り消し」の行・項目の並びと見出し、`settingNoEffect` の7つ、設定画面の区画の説明、AI のモデルを変える口などは、設計が決めていない。コードに【仮置き】と書き、[web/仮置き値.md](../web/仮置き値.md) に一覧がある。
