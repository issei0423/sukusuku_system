# 11 行事カレンダー

> この説明は commit 41fbc463（2026-11-26 の本線）のコードに合わせてある。引いたコードと行番号は、どちらもこの版のもの。

## この機能でできること

- 保育士（一般の職員）と園長（管理者）が、園の行事や予定を月のカレンダーに書く。画面は職員の「行事カレンダー」（`/staff/calendar`）。保護者はスマートフォンの「行事カレンダー」（`/guardian/calendar`）で見る。
- 予定は、日付・開始と終了の時刻（任意。両方空なら「終日」）・題名・内容・対象（園全体か、1つのクラス）を持つ。何日も続く行事と繰り返しは作らない（【仮置き】）。
- 見られる範囲は配布物と同じ（`handoutClassIDs`）。管理者は全部、一般の職員は園全体と自クラス、保護者は園全体と自分の子がいま在籍するクラス。
- 書けるのは、園全体の予定は管理者だけ、クラスの予定は管理者かそのクラスの一般の職員。担当クラスの無い一般の職員（フリー）と保護者は見るだけ。
- 直すときは、いまの対象と移し先の対象の両方に権限が要る。消すときは論理削除（行は残して一覧に出さない）にする。
- 足す・直す・消すのたびに操作ログを残し、その予定を見られる人の開いている画面へ「読み直して」と知らせる。
- 基本設計書・要件定義書に行事カレンダーの定めは無い（行事は配布物と園チャットで伝える設計）。2026-11-26 の持ち主の依頼「行事やイベントのカレンダー機能を作りたい。保護者はそれを確認出来て保育士はカレンダーに記入する」を受けて、形のよく似た配布物（`t_handout`）を手本に置いた【仮置き】。設計へ取り込むかどうかは Issue で持ち主が決める（web/仮置き値.md「行事カレンダーの動き」）。

## 予定の列と、だれが何をできるか

予定は `t_event` に入れる。定義は [server/schema.sql](../server/schema.sql) 348〜366行。

| 列 | 中身 |
| :-- | :-- |
| `event_id` | 主キー（自動で振る） |
| `event_date` | 日付 'YYYY-MM-DD'（必須） |
| `start_time`・`end_time` | 開始・終了 'HH:MM'。開始が空なら終日 |
| `title`・`note` | 題名（必須）・内容（既定は空の文字列） |
| `class_id` | 対象のクラス。空なら園全体 |
| `created_staff_id`・`created_at`・`updated_staff_id`・`updated_at` | 足した職員と日時・最後に直した職員と日時（足したときは同じ） |
| `is_deleted`・`deleted_at`・`deleted_staff_id` | 論理削除。消した日時と職員 |

日付で引くための索引 `ix_event_date` がある。だれが何をできるか（サーバの判定は `handoutClassIDs` と `canWriteEventClass`）は次のとおり。

| 利用者 | 見られる予定 | 園全体の予定を足す・直す・消す | クラスの予定を足す・直す・消す |
| :-- | :-- | :-- | :-- |
| 管理者 | すべて | できる | どのクラスもできる |
| 一般の職員（担当クラスあり） | 園全体と自クラス | できない | 自クラスだけできる |
| 一般の職員（担当クラスなし。フリー） | 園全体だけ | できない | できない |
| 保護者 | 園全体と、自分の子がいま在籍するクラス | できない（職員だけの経路で 403） | できない（同じ） |

道（URL）は 4 つ。`GET /api/events` は開いている画面への知らせの受け口（SSE）なので、取り違えないように接頭辞を `/api/calendar/events` にしている。

| 操作 | 要求 | ハンドラ | 返すもの |
| :-- | :-- | :-- | :-- |
| 月の予定を読む | `GET /api/calendar/events?month=YYYY-MM` | `handleCalendarEvents` | `month`・`events`・`can_write_all`・`writable_class_ids` |
| 足す | `POST /api/calendar/events` | `handleAddCalendarEvent` | `{ "event": … }` |
| 直す | `POST /api/calendar/events/{id}` | `handleUpdateCalendarEvent` | `{ "event": … }` |
| 消す | `POST /api/calendar/events/{id}/delete` | `handleDeleteCalendarEvent` | `{ "ok": true }` |

## 流れ

1. 職員は左メニューの「行事カレンダー」から `/staff/calendar` を、保護者はメニューから `/guardian/calendar` を開く。
2. 画面は今月を選び、`GET /api/calendar/events?month=YYYY-MM`（`handleCalendarEvents`）で月の予定を読む。サーバは見られるものだけに絞り、予定ごとの `can_edit` と、書ける範囲（`can_write_all`・`writable_class_ids`）を添える。
3. 月の格子（`MonthCalendar`）の日を押すと、その日の予定が一覧に出る（職員は右、保護者は下）。「前の月」「次の月」「今月へ戻る」で月を替えると、その月を読み直す。
4. 書ける職員は「予定を足す」で窓を開き、`POST /api/calendar/events`（`handleAddCalendarEvent`）へ送る。サーバは、職員か → 入力 → 対象の権限 → クラスの有無、の順に確かめて `t_event` に書き、操作ログを残し、`notifyCalendar` で知らせる。
5. 「直す」は `POST /api/calendar/events/{id}`、「消す」は確認を挟んで `POST /api/calendar/events/{id}/delete`。消すのは論理削除。
6. 知らせを受けた画面は、`onLive('calendar')` で月の予定を読み直す。足した人・直した人の画面は、保存のあとにも自分で読み直す。

```
StaffCalendarScreen ──月の予定を読む──▶ GET /api/calendar/events?month= ──▶ handleCalendarEvents ──▶ t_event
   │                                                        └─ handoutClassIDs で見られる予定だけ ＋ can_edit
   │ 予定を足す・直す・消す
   ▼
POST /api/calendar/events ｜ …/{id} ｜ …/{id}/delete ──▶ handleAdd… ｜ handleUpdate… ｜ handleDelete…CalendarEvent ──▶ t_event
                                                            └──▶ 操作ログ（t_operation_log）・notifyCalendar
GuardianCalendarScreen ◀── GET /api/calendar/events?month=（園全体と自児のクラスだけ。見るだけ）
```

## コードを読む

### 1. 予定の表を、古い DB にも用意する（server/db.go 422〜437行）

```go
func ensureEvents(db *sql.DB) error {
	if _, err := db.Exec(eventDDL); err != nil {
		return fmt.Errorf("行事の表を作れません: %w", err)
	}
	if _, err := db.Exec(`CREATE INDEX IF NOT EXISTS ix_event_date ON t_event (event_date)`); err != nil {
		return fmt.Errorf("行事の index を作れません: %w", err)
	}
	var n int
	if err := db.QueryRow(`SELECT COUNT(*) FROM t_event`).Scan(&n); err != nil {
		return fmt.Errorf("行事を確かめられません: %w", err)
	}
	if n > 0 {
		return nil
	}
	return seedEvents(db)
}
```

**解説**

- `ensureEvents` は、DB を開くたびに呼ばれる（`openDB`、db.go 108行。配布物の `ensureHandouts` の次）。新しく作る DB では、[server/schema.sql](../server/schema.sql) 348〜366行が `t_event` と索引 `ix_event_date` を作る。以前に作った DB には、同じ定義を文字列にした `eventDDL`（db.go 439〜454行）を `CREATE TABLE IF NOT EXISTS` で流して足す。なぜ：ファイルを消さずに使い続けられるようにするため（コメント）。
- `SELECT COUNT(*) FROM t_event` が 0 のときだけ、`seedEvents`（464〜512行）でデモの予定を入れる。数えるのは消した予定（論理削除）も含めた全行なので、1件でも行があれば入れ直さない。
- `seedEvents` が入れるのは 4 件で、作成者・更新者は管理者の S001。今月 10 日 09:30〜12:00「運動会」（園全体）、今月 20 日 10:00〜10:45「誕生会」（園全体）、今月 15 日 終日「身体測定」（今年度のクラスのうち `class_id` が最も小さいクラス。クラスが 1 つ以上あるとき）、来月 5 日 09:00〜14:00「遠足」（2 番目に小さいクラス。クラスが 2 つ以上あるとき）。
- 日付は起動した日（JST。`nowTime()`）の月から決める。`server/seed.sql` に予定は無く、デモの日付をずらす `shiftSeedDates`（seed_shift.go）の対象にもならない。新しく作る DB では、ずらす処理（db.go 78行）のあとに `ensureEvents`（108行）が呼ばれ、そのときの今日から日付を決めるため。
- モックの `buildEvents`（[web/src/api/mockDb.ts](../web/src/api/mockDb.ts) 1131〜1151行）も同じ 4 件を入れる。デモデータは 2 か所にある（AGENTS.md「いちばん大事な決まり：業務の規則は 2 か所にある」）。

**解説**

- `eventTitleMax`（50）と `eventNoteMax`（500）は、題名と内容の文字数の上限。設計に定めが無い【仮置き】（web/仮置き値.md）。画面（calendarText.ts の `EVENT_TITLE_MAX`・`EVENT_NOTE_MAX`）とモック（mock.ts の `CALENDAR_TITLE_MAX`・`CALENDAR_NOTE_MAX`）にも、同じ値がある。
- `timePattern` は時刻の形で、`00:00`〜`23:59` の「09:30」の形だけを通す。「9:00」「24:00」「10:60」は通らない。
- `CalendarEvent` は、画面へ返す JSON の形。開始・終了の時刻とクラスは、空のとき JSON の `null` にするためにポインタにしてある。`ClassName` と `CanEdit` は「画面が使う導出値」で、`t_event` には無い。園全体のとき `class_name` は `null`。
- `eventColumns` は予定を読む列の並びで、`scanEvent`（48〜65行）の `Scan` の並びと合わせてある。`scanEvent` は、空を許す列を `sql.NullString`・`sql.NullInt64` で受け、値があるときだけポインタに入れる（`nullInt` は model.go 238行）。引数は `Scan(...any) error` を持つものなら何でもよいので、`QueryRow` の結果（`loadEvent`）にも、`Query` の行（`handleCalendarEvents`）にも使える。

### 3. だれが書けるか・直せるか（server/api_event.go 67〜86行）

```go
// canWriteEventClass は、その利用者が、その対象（nil は園全体）の予定を書けるかを返す。
// 園全体は管理者だけ。クラスは canUseClass（一般は自クラスだけ）
func (a *app) canWriteEventClass(u *SessionUser, classID *int64) bool {
	if !u.isStaff() {
		return false
	}
	if classID == nil {
		return u.isAdmin()
	}
	return a.canUseClass(u, *classID)
}

// fillEvent は、名前と「直せるか」を入れる。カーソルを閉じたあとに呼ぶ（接続を1本に絞っているため。db.go）
func (a *app) fillEvent(u *SessionUser, e *CalendarEvent) {
	if e.ClassID != nil {
		name := a.className(*e.ClassID)
		e.ClassName = &name
	}
	e.CanEdit = a.canWriteEventClass(u, e.ClassID)
}
```

**解説**

- `canWriteEventClass` が、書ける範囲のただ 1 つの判定。職員でなければ（保護者は）偽。対象が園全体（`classID` が `nil`）なら管理者だけ。クラスなら `canUseClass`（[server/scope.go](../server/scope.go) 251〜256行）で、管理者は全部、一般の職員は自分のクラス（`u.ClassID`）と同じときだけ真になる。担当クラスの無い一般の職員（フリー）は `u.ClassID` が空なので、どのクラスも偽。
- 足す・直す・消すのどれも、この関数で判定する（ブロック 6・7）。直すときは、いまの対象と移し先の対象の両方を通す。
- `fillEvent` は、予定に `class_name`（`className` は scope.go 279行）と `can_edit`（見ている人がその予定を直せるか）を入れる。「カーソルを閉じたあとに呼ぶ」のは、DB の接続を 1 本に絞っていて、行を読んでいる最中に別の問い合わせをすると進まなくなるため（db.go）。
- `writableEventClassIDs`（88〜109行）は、見ている人が予定を書けるクラスの ID の並び。管理者は今年度（`fiscalYear`）のクラスすべて（ID の小さい順）、一般の職員は自分のクラス 1 つ、保護者とフリーは空。空のときも `[]int64{}` を返すので、JSON は `null` でなく `[]` になる。なぜ：画面が「予定を足す」の対象の選択肢を、書ける範囲だけにするため（ブロック 10）。
- 画面の出し分けは見た目で、担保はこの判定（基本設計書「権限チェックの実装方針」(6-2)）。`loadEvent`（112〜115行）は、消されていない（`is_deleted = 0`）予定を 1 件読む。消した予定は「見つからない」になる。

### 4. 月の予定を読む（server/api_event.go 128〜141・154〜164行）


**解説**

- 前半（118〜127行）：`requireUser` で、ログインしていれば職員も保護者も通す（していなければ 401）。`month` は `monthPattern`（api_handout.go 42行。`YYYY-MM`、月は 01〜12）で確かめ、違えば 400「月を指定してください」。
- 日付の範囲は `event_date >= 月-01 AND event_date <= 月-31`。日付は 'YYYY-MM-DD' の文字列なので、月の末日が 30 日や 28 日でも、「-31」を上限にすれば、その月の分が入る。
- 見られる範囲は `handoutClassIDs(u)`（api_handout.go 52〜81行）に任せる。管理者は `all` が真で、絞らない。ほかは `class_id IS NULL`（園全体）に、`class_id IN (…)`（見られるクラス。数だけ `?` を並べる）を `OR` でつなぐ。見られるクラスが無い人（フリー）は、`class_id IS NULL` だけになる。なぜ：配布物と同じ関数にして、配布物と予定で食い違わないようにするため（ファイルの頭のコメント）。
- `ORDER BY event_date, start_time IS NOT NULL, start_time, event_id`：日付順に、その日の中では終日（開始が空）を先に置き、あとは開始の時刻、同じなら ID の順。
- 行は `scanEvent` で全部読み、`rows.Close()` のあとに `fillEvent` をかける（接続を 1 本に絞っているため）。0 件でも `events` は `[]` になる。引けなかったときは 500「予定を取得できませんでした」。
- 返すのは `month`・`events`・`can_write_all`（管理者か）・`writable_class_ids`（ブロック 3）の 4 つ。保護者にも同じ形で返す。違いは値だけで、保護者は `can_edit` がどれも偽、`can_write_all` が偽、`writable_class_ids` が空になる。`class_id`・`class_name` は保護者にも返す。

### 5. 入力を確かめる（server/api_event.go 176〜205行）

```go
// validateEvent は体を確かめ、整えた値を返す。誤りがあれば、利用者に見せる文言を返す
func validateEvent(req *eventRequest) (start, end *string, message string) {
	req.Title = strings.TrimSpace(req.Title)
	if _, err := time.Parse("2006-01-02", req.EventDate); err != nil {
		return nil, nil, "日付を正しく入力してください"
	}
	// 空の文字列は「指定なし」（終日）として読む
	clean := func(v *string) *string {
		if v == nil || *v == "" {
			return nil
		}
		return v
	}
	start, end = clean(req.StartTime), clean(req.EndTime)
	switch {
	case start != nil && !timePattern.MatchString(*start), end != nil && !timePattern.MatchString(*end):
```

### 8. 見られる人にだけ知らせる（server/events.go 407〜430行）

```go
func (a *app) notifyCalendar(eventID int64, eventDate, op string, classIDs ...*int64) {
	a.notify(liveEvent{Type: evCalendar, EventID: eventID, EventDate: eventDate, Op: op}, func(u *SessionUser) bool {
		ids, all := a.handoutClassIDs(u)
		if all {
			return true
		}
		for _, c := range classIDs {
			if c == nil {
				return true
			}
			for _, id := range ids {
				if id == *c {
					return true
				}
			}
		}
		return false
	})
}
```

### 9. 月の格子を作る（web/src/components/MonthCalendar.tsx 13〜34行）

```tsx
const WEEKDAYS = ['日', '月', '火', '水', '木', '金', '土'];

/** 「2026-10」の前の月・次の月 */
const shiftMonth = (month: string, delta: number): string => {
  const [y, m] = month.split('-').map(Number);
  const d = new Date(Date.UTC(y, m - 1 + delta, 1));
  return `${d.getUTCFullYear()}-${String(d.getUTCMonth() + 1).padStart(2, '0')}`;
};
const monthLabel = (month: string): string => `${month.slice(0, 4)}年${Number(month.slice(5))}月`;

/** 月の格子。週ごとの7日（月の外の日は null） */
function weeksOf(month: string): (string | null)[][] {
  const [y, m] = month.split('-').map(Number);
  const lead = new Date(Date.UTC(y, m - 1, 1)).getUTCDay();
  const days = lastDayOfMonth(y, m);
  const cells: (string | null)[] = Array.from({ length: lead }, () => null);
  for (let d = 1; d <= days; d++) cells.push(`${month}-${String(d).padStart(2, '0')}`);
  while (cells.length % 7 !== 0) cells.push(null);
  const weeks: (string | null)[][] = [];
  for (let i = 0; i < cells.length; i += 7) weeks.push(cells.slice(i, i + 7));
  return weeks;
}
```

- `defaultTarget` は、足す窓の対象の初めの値。管理者は園全体（空の文字列）、一般の職員は自クラス（`targetClasses` の先頭）。`openAdd`（64〜67行）は窓を開き、日付は選んだ日（無ければその月の 1 日）、時刻・題名・内容は空にする。`openEdit`（68〜74行）は予定の値をそのまま窓へ写し、時刻が `null` なら空の文字列、`class_id` が `null` なら対象は空の文字列にする。

### 12. モックにも同じ規則がある（web/src/api/mock.ts 4752〜4764行）


**解説**

- サーバの `handleAddCalendarEvent`（ブロック 6）と同じ順で確かめる。職員か（保護者は `STAFF_ONLY_MESSAGE`「職員のみが行えます」）→ 入力（`checkCalendarInput`）→ 対象の権限（`canWriteCalendar`）→ 対象のクラスの有無（`calendarClassExists`）。文言も同じ。

## 気をつけているところ

- **権限の担保はサーバ。** 書ける範囲は `canWriteEventClass`、見られる範囲は `handoutClassIDs` の 1 か所ずつで決める。画面の「予定を足す」「直す」「消す」のボタン（`can_edit`・`canWrite`）は見た目のためで、押されてもサーバが断る（基本設計書「権限チェックの実装方針」(6-2)）。
- **配布物と同じ範囲。** 読む（`handleCalendarEvents`）と知らせる（`notifyCalendar`）のどちらも `handoutClassIDs` を通し、見られる人と知らせる人がずれないようにする。保護者は、園全体と自児がいま在籍する今年度のクラスの予定だけを読める。
- **直すときは両側に権限。** いまの対象と移し先の対象の両方を `canWriteEventClass` に通す。消すときは、いまの対象だけ。
- **消しても行は残す。** 論理削除（`is_deleted = 1`）にして、消した職員と日時を残す。一覧と 1 件の読み出し（`loadEvent`）は消したものを返さない。二度消す・消したものを直すのは 404。
- **接続を 1 本に絞っている。** 行を読んでいる最中に別の問い合わせをしないよう、`handleCalendarEvents` は `rows.Close()` のあとに `fillEvent` をかける。
- **規則は 2 か所。** サーバ（server/api_event.go・events.go・db.go）とモック（web/src/api/mock.ts の `canWriteCalendar`・`checkCalendarInput`・`calendarApi`、mockDb.ts の `buildEvents`）に、同じ規則・文言・デモの予定がある。テストもサーバ（server/api_event_test.go。書ける人・見られる範囲・並び・移し替え・論理削除・入力の検査・月の形・デモの予定・操作ログ・知らせの相手）とモック（web/tests/calendar.test.ts）の両方にある。
- **設計に無い値は【仮置き】。** 題名 50 文字・内容 500 文字の上限、何日も続く行事・繰り返しを作らないこと、操作ログの機能種別にチャットを流用すること、知らせでチャットへ流さないこと、メニューの位置（職員は「連絡帳」の次、保護者はメニューの先頭）、カレンダーの色と印、デモの予定 4 件などは、web/仮置き値.md「行事カレンダーの動き」にある。
- **道を取り違えない。** `GET /api/events` は開いている画面への知らせの受け口（SSE）。行事カレンダーの道は `/api/calendar/events`（routes.go 149〜153行）。
