# 05 日誌

> この説明は commit 74f09acf のコードで書いた。行番号はその版のもの。

## この機能でできること

- 保育士（一般の職員）と園長（管理者）が、園児やクラスの記録を書く。画面は職員のタブレット・PC の「日誌」。
- 日誌は**園内の記録**である。どの状態でも、保護者には届かない（基本設計書「日誌システム（園内の記録）」(4-6)）。
- 例外は1つだけある。保育士が申請するときに「保護者へ共有する」を選び、管理者が承認した**個人日誌**は、その子の保護者が「園からの日誌」で読める（2026-10-29 に持ち主が決めた）。
- 書いた日誌は、下書き → 申請 → 管理者の承認、の順に進む。差し戻し・申請の取り下げ・承認の取り消しもある。
- 同じ日誌を2人が同時に直さないよう、編集ロック（いま直している人を1人に決める仕組み）をかける。
- 本文には、雛形・定型文・きょうのようす（連絡帳の午睡と食事）を入れられる。園児タイムラインで、その子の記録を日付の順に見られる。

## 記録の種類と状態

コード値は [web/src/api/codes.ts](../web/src/api/codes.ts) 22〜27行にある。DB の列の制約は [server/db_diary.go](../server/db_diary.go) 108・113行（`t_diary` の定義）にある。記録の種類でテーブルを分けず、1つの `t_diary` に入れる。

| 列 | 値 |
| :-- | :-- |
| `record_type`（記録種別） | 1 個人日誌・2 クラス日誌・3 週案・月案・4 ヒヤリハット |
| `status`（状態） | 1 下書き・2 申請中・3 承認済・4 差し戻し |

個人日誌とヒヤリハットは園児（`child_id`）を対象にする。クラス日誌と週案・月案は `child_id` を空にし、クラス（`class_id`）を対象にする。

状態の移り変わりは次のとおり。

| 操作 | だれが | 状態 | サーバの関数 |
| :-- | :-- | :-- | :-- |
| 下書き保存 | 職員 | （新規）→ 1、1 → 1、4 → 4 | `handleSaveDiary`・`updateDiary` |
| 申請 | 職員 | （新規）→ 2、1 → 2、4 → 2 | `handleSaveDiary`・`updateDiary` |
| 承認 | 管理者（自分が申請したものは不可） | 2 → 3 | `handleApproveDiary` |
| 差し戻し（理由は必須） | 管理者 | 2 → 4 | `handleReturnDiary` |
| 申請の取り下げ | 申請した本人 | 2 → 1 | `handleWithdrawDiary` |
| 承認の取り消し（理由は必須） | 管理者 | 3 → 4 | `handleRevokeDiaryApproval` |

## 流れ

1. 職員が日誌作成・編集画面を開く。既存の日誌なら、まず編集ロックを取る（`POST /api/diaries/{id}/lock`）。
2. 書いて「下書き保存」を押すか、「確認へ進む」で日誌確認画面へ移り「申請」を押す。どちらも `POST /api/diaries`（`handleSaveDiary`）へ送る。
3. サーバは、参照範囲・入力・ロックを確かめてから `t_diary` と写真（`t_diary_attachment`）を1つのトランザクション（全部書くか、何も書かないかのまとまり）で書く。そのあと操作ログを残し、`notifyDiary` で、その日誌を読める職員の開いている画面へ知らせる。
4. 管理者が承認待ち一覧（`GET /api/diaries/pending`）から日誌承認画面を開き、承認（`.../approve`）か差し戻し（`.../return`）を押す。
5. 申請した本人は取り下げ（`.../withdraw`）、管理者は承認の取り消し（`.../revoke-approval`）ができる。
6. 共有を選んだ個人日誌が承認されると、保護者は `GET /api/guardian/diaries` で読める。保護者は `/api/diaries/...` の経路を使えない。

```
DiaryEditScreen ──ロックの取得・操作の知らせ──▶ /api/diaries/{id}/lock
   │ 下書き保存 ／ 確認へ進む
   ▼
DiaryConfirmScreen ──申請──▶ POST /api/diaries ──▶ handleSaveDiary ──▶ t_diary・t_diary_attachment
                                                        └──▶ 操作ログ・notifyDiary（職員だけ）
DiaryApproveScreen ──承認・差し戻し──▶ POST /api/diaries/{id}/approve ｜ return
GuardianDiaryScreen ◀── GET /api/guardian/diaries（共有を選んで承認された個人日誌だけ）
```

## コードを読む

### 1. だれが日誌を読めるか（server/api_diary.go 117〜154行）

```go
// visibleDiaryCondition は参照範囲の条件を組み立てる。
//
// 個人日誌・ヒヤリハットは対象園児で、クラス日誌・週案は対象クラスで判定する。
// 承認済みであっても参照範囲は広がらない。保護者はこの経路では読めない
// （基本設計書「日誌システム（園内の記録）」(4-6)、詳細設計書「日誌」(4-13 (10))）。
// 共有された個人日誌を保護者が読むのは、別の経路（api_diary_share.go）で、保護者に見せる項目だけを返す
func (a *app) visibleDiaryCondition(u *SessionUser) (string, []any) {
	switch u.Role {
	case "1":
		return "1 = 1", nil
	case "2":
		if u.ClassID == nil {
			return "1 = 0", nil
		}
		return `((child_id IS NOT NULL AND child_id IN (SELECT child_id FROM t_class_child WHERE class_id = ?))
		         OR (child_id IS NULL AND class_id = ?))`, []any{*u.ClassID, *u.ClassID}
	default:
		return "1 = 0", nil
	}
}

// msgDiaryForbidden は、その日誌を読めないときの文言（既存）。保護者が日誌の経路を呼んだときも同じ文言にする
// （詳細設計書「日誌」(4-13)「保護者が呼んだら 403」）。モック（web/src/api/mock.ts）と同じ
const msgDiaryForbidden = "この日誌を参照する権限がありません"

// requireDiaryStaff は、日誌の経路を職員だけに通す。保護者には 403 を返す（詳細設計書「日誌」(4-13)）。
// 共有日誌閲覧画面を外したため、保護者が日誌を読む経路は無い
func (a *app) requireDiaryStaff(w http.ResponseWriter, r *http.Request) (*SessionUser, bool) {
	u, ok := a.requireUser(w, r)
	if !ok {
		return nil, false
	}
	if !u.isStaff() {
		writeForbidden(w, msgDiaryForbidden)
		return nil, false
	}
	return u, true
}
```

**解説**

- `visibleDiaryCondition` は、SQL の WHERE に足す条件と引数を返す。管理者（ロール 1）はすべて、一般（ロール 2）は自分の担当クラスの分だけになる。
- 個人日誌・ヒヤリハット（`child_id` がある）は、その園児が担当クラスに在籍しているかで決める。クラス日誌・週案（`child_id` が空）は、日誌の `class_id` で決める。
- 保護者（ロール 3）は `1 = 0` で、何も出ない。そのうえ `requireDiaryStaff` が、日誌の経路の入口で保護者を 403（権限が無いときの応答）にする。
- なぜ：承認済みでも参照範囲は広がらず、保護者へは返さない（基本設計書「日誌システム（園内の記録）」(4-6)、詳細設計書「日誌」(4-13)）。
- すぐ下の `canSeeDiary`（158〜165行）は、同じ条件で1件だけを判定する。保存・取り下げ・ロック・添付が使う。無い日誌も「読めない」と同じ 403 にして、あるかどうかを推測させない。
- 気をつけるところ：同じ規則がモックの `canSeeDiary`（[web/src/api/mock.ts](../web/src/api/mock.ts) 430〜438行）にある。片方だけ直すと食い違う。ログインした人の情報（`SessionUser`）の作り方と `requireUser` の仕組みは [01 全体の仕組み](./01-全体の仕組み.md) を見る。

**解説**

- 個人日誌（1）とヒヤリハット（4）は、対象の園児が要る。`canSeeChild` で、その園児を扱えるかを見る（server/scope.go。仕組みは [01](./01-全体の仕組み.md) を見る）。
- クラス日誌・週案では、送られた `child_id` を捨てて空にする。
- 対象のクラスは、記録種別によらず必須にする。`canUseClass` で、自分が扱えるクラスかを見る。他クラスを対象に作れると、作った本人には見えず、そのクラスの担任には見える日誌ができていた（GitHub Issue #153）。
- 【仮置き】個人日誌・ヒヤリハットの対象のクラスは、その園児が在籍するクラスに限る（`childInClass`、400〜406行。web/仮置き値.md）。
- この前の 107〜145行で、本文は1〜2,000文字、保存する状態は "1"（下書き）か "2"（申請）、記録日は当日まで、を確かめる。週案・月案だけは365日先まで認める（基本設計書「日付の扱い」(4-6)）。
- この後の 189〜199行で、ヒヤリハットは本文の代わりに欄（発生日時・場所・状況・とった対応・今後の対策・保護者へ伝えたこと）を受け取る。`checkDiaryIncident` で欄を確かめ、`incidentBody` が「【状況】」「【とった対応】」「【今後の対策】」の見出しでつないだ本文をサーバで作る（[server/api_diary_incident.go](../server/api_diary_incident.go) 111〜157・181〜187行。詳細設計書「日誌」(4-13 (1)) の D-33）。本文に入れるのは、一覧のキーワード検索で探せるようにするため。
- 気をつけるところ：同じ検査がモックの `saveDiary`（mock.ts 1325行〜）にある。画面の `goConfirm`（DiaryEditScreen.tsx 422〜438行）も記録日を先に確かめるが、これは使いやすさのためで、担保はサーバである。

### 3. 既存の日誌を書き換える（server/api_diary_write.go 266〜285・295〜298・316〜319行）

```go
func (a *app) updateDiary(w http.ResponseWriter, u *SessionUser, in diaryInput) {
	var (
		status, version string
		shared          bool
	)
	if err := a.db.QueryRow(`SELECT status, updated_at, share_to_guardian FROM t_diary WHERE diary_id = ? AND is_deleted = 0`,
		*in.DiaryID).Scan(&status, &version, &shared); err != nil {

	}
	// 書き換える日誌そのものも、参照範囲の内にあるものに限る。入力の園児・クラスを確かめるだけでは、
	// 他クラスの日誌を日誌IDで指定して自クラスへ書き換えられてしまう（GitHub Issue #153）

		return

		writeErr(w, http.StatusBadRequest, "申請中または承認済みの日誌は編集できません")
		return
	}
	// …（略）…
	if !a.holdsDiaryLock(u, *in.DiaryID, in.LockToken) {
		writeErr(w, http.StatusConflict, msgDiaryLockReleased)
		return
	}
	// …（略）…
	next := in.Status
	if next == "1" && status == "4" {
		next = "4"
	}
```

**解説**

- まず、いまの状態・版（`updated_at`。書き換えるたびに進む値で、読んだあとに変わったかを見分ける）・共有の印を読む。
- 書き換える日誌そのものも `canSeeDiary` で確かめる。入力の園児・クラスだけを見ると、他クラスの日誌を日誌 ID で指定して自クラスへ書き換えられた（GitHub Issue #153）。
- 申請中（2）・承認済み（3）は書き換えられない。
- `holdsDiaryLock`（970〜980行）で、送られたロックの識別子が今のロックと同じで、ロックを持つのが本人かを見る。違えば 409（いまの状態とぶつかったときの応答）「編集ロックが解除されました。内容を再読み込みしてください。」を返す（基本設計書「同時編集の検出」(4-2)・「編集ロックの解除」(4-5)）。ロックの行が無いときも通さない。管理者が強制解除したあとに古い識別子で保存が通ると、ほかの人の直しを黙って上書きするため（GitHub Issue #166）。
- 差し戻し（4）の日誌を下書き保存しても、状態は差し戻しのまま残す（`next`）。作成者の一覧とダッシュボードの「差し戻された日誌」から消さないため（GitHub Issue #305）。
- 省いた 320〜368行：トランザクションの中で日誌と写真を書く。申請ならロックの行を消し、下書き保存ならロックの最終操作時刻を進める。最後に操作ログを残して `notifyDiary` を呼ぶ。
- 差し戻す理由（`returned_reason`）は、申請し直しても消さない。承認者が前回の指摘を見ながら確かめられるようにするため（300〜301行のコメント）。

### 4. 承認する（server/api_diary_write.go 566〜574・580〜606行）

- 承認できるのは管理者だけ。関数の頭（545〜549行）の `requireAdminFor` で、ほかのロールは 403「承認は管理者のみが行えます」になる。
- 申請中でなければ 409。下書きに戻っていれば「この日誌は取り下げられました。」を返す（`notAppliedMessage`、516〜521行）。
- 自分が申請した日誌は承認できない。判定は申請者の列 `applied_staff_id` で行い、作成者では見ない。作成者が管理者でも、ほかの職員が申請したものは承認できる（詳細設計書「日誌の状態」(3-6)。GitHub Issue #106・#174）。
- 読んだ版（画面が送る `updated_at`）が今の版と違えば 409（`kind: version_conflict`）。承認画面を開いている間に、保育士が取り下げて本文や「保護者へ共有する」を変えて申請し直すと、状態は申請中に戻り、状態だけでは見分けられない。版を見ないと、管理者が読んでいない本文が保護者へ届く（532〜544行の説明）。
- UPDATE の WHERE に `status = '2' AND updated_at = ?` を入れる。ほぼ同時に取り下げ・差し戻しが押されたときは、後に届いたほうを断る。
- `nextDiaryVersion` は、書くたびに版を必ず前より進める。同じ秒に2回書いても別の版になる（詳細設計書「足す表」(5-2) の D-40）。
- 画面側：日誌承認画面の `approve`（[DiaryApproveScreen.tsx](../web/src/screens/diary/DiaryApproveScreen.tsx) 69〜80行）が読んだ版を送る。`version_conflict` で断られたら、日誌と写真を両方読み直し、読み直したことを伝える文を出す。共有が選ばれていれば、ボタンの名前を「承認して保護者へ共有する」に変える（176行）。

### 9. きょうのようすから本文へ入れる（web/src/screens/diary/DiaryEditScreen.tsx 275〜314行）

```tsx
   * 書いてある本文の後ろは、行を改めてから足す（【仮置き】web/仮置き値.md「日誌作成・編集画面の動き」）。
   * 選んだ値は呼び出しの前に受け取る。欄を空へ戻したあとに読むと空になり、改行しか入らなかった（GitHub Issue #175 の 1）
   */
  const addPhrase = (phrase: string) => {
    setBody((b) => (b === '' || b.endsWith('\n') ? `${b}${phrase}` : `${b}\n${phrase}`));
    setDirty(true);
  };
```

**解説**

- 雛形（`m_diary_template`）は `GET /api/diaries/templates`（`handleDiaryTemplates`、api_diary.go 346〜365行）で読む。いまの記録種別の雛形だけを並べる。選んでも記録種別は変えない（GitHub Issue #178）。
- 本文が空なら雛形を入れ、書いてあれば末尾に足す。書きかけを消さない。
- 定型文は `GET /api/diaries/phrases` で読み、本文の末尾へ行を改めて足す。
- サーバの定型文は `fixedPhrases`（api_diary.go 367〜385行）の定数である。【仮置き】定型文を置くテーブルが設計に無い。保護者に向けた文は置かない（日誌は園内の記録で、保護者へは連絡帳で届けるため）。モックの `fixedPhrases`（web/src/api/mockDb.ts）と同じ並びにそろえる。
- ヒヤリハットでは雛形と定型文を出さず、欄（[IncidentFields.tsx](../web/src/screens/diary/IncidentFields.tsx)）に替える（DiaryEditScreen.tsx 546〜553行）。

### 12. モックにも同じ承認の規則がある（web/src/api/mock.ts 1477〜1497行）

```ts
  async approveDiary(user: SessionUser, diaryId: number, updatedAt: string): Promise<Diary> {
    if (user.role !== '1') return fail(DIARY_MSG.approveAdminOnly);
    const d = db.diaries.find((x) => x.diary_id === diaryId && !x.is_deleted);
    if (!d) return fail('日誌が見つかりません');
    // 下書きなら、申請が取り下げられたあとに届いた承認である（詳細設計書「日誌の状態」(3-6)）
    if (d.status !== '2') return fail(d.status === '1' ? DIARY_MSG.withdrawn : DIARY_MSG.approveNotApplied);
    // 自分が申請した日誌は承認できない。申請者の列（applied_staff_id）で判定し、作成者が管理者でも、ほかの職員が
    // 申請したものは承認できる（詳細設計書「日誌の状態」(3-6)。GitHub Issue #106・#174）
    if (d.applied_staff_id === user.staff_id) return fail(DIARY_MSG.ownApplication);
    // 版の食い違いは kind を添える（server/api_diary_write.go の kindVersionConflict と同じ。画面は読み直したことを伝える文に替える）
    if (d.updated_at !== updatedAt) return failKind(DIARY_MSG.versionConflict, 'version_conflict');

    d.status = '3';
    d.approved_staff_id = user.staff_id;
    d.approved_at = now();
    d.returned_reason = null;
    d.updated_at = nextDiaryVersion(d.updated_at);
    log(user.account_id, '1', '3', 't_diary', d.diary_id, d.child_id, '申請中',
      d.share_to_guardian ? DIARY_LOG_APPROVE_SHARED : '承認済み');
    publishDiary(d);
    return ok(withDiaryNames(d));
```

**解説**

- サーバの `handleApproveDiary`（ブロック 4）と同じ順で確かめる。管理者か → 申請中か（下書きなら「取り下げられました」）→ 自分の申請でないか → 読んだ版か。
- 文言は `DIARY_MSG` にまとめ、サーバの `msgDiary...` の定数（api_diary_write.go 470〜489行）と同じ文にしている。
- 版の食い違いは `failKind(..., 'version_conflict')` で `kind` を添える。サーバの `kindVersionConflict` と同じで、画面は同じ扱いができる。
- 操作ログの文言（「承認済み」「承認済み（保護者へ共有）」）もサーバと同じ。`publishDiary` は、サーバの `notifyDiary` に当たるモックの知らせ。
- なぜ：画面のテスト（web/tests/）はモックを相手に回る。規則がずれると、テストは通るのに本物のサーバでは断られる、ということが起きる（AGENTS.md「いちばん大事な決まり：業務の規則は 2 か所にある」）。

## 気をつけているところ

- **保護者には届かない。** 日誌の経路は入口（`requireDiaryStaff`）で保護者を 403 にする。開いている画面への知らせも職員だけに送る（events.go の `notifyDiary` は `u.isStaff()` を条件にする）。保護者が読めるのは、`/api/guardian/diaries` で返す「共有を選んで承認された個人日誌」の6項目だけ。
- **参照範囲はサーバで担保する。** 一覧・1件・添付・ロック・保存・取り下げのどれも、`visibleDiaryCondition`／`canSeeDiary` を通す。画面でボタンを隠すだけに頼らない（基本設計書「権限チェックの実装方針」(6-2)）。添付は件数とファイル名だけでも担当外の園児の写真があると分かるので、権限を通してから返す（api_diary.go 402〜423行。GitHub Issue #153）。
- **同時に直させない。** 編集ロックの識別子を保存のたびに照合し、合わなければ断る。ロックは編集画面から確認画面へ引き継ぎ、申請でサーバが外す。
- **読んだ版で確かめる。** 承認・取り下げ・承認の取り消しは、画面が読んだ `updated_at` を送り、今の版と違えば 409 にする。書き換えの WHERE にも状態と版を入れる。
- **自分の申請は自分で承認しない。** 申請者の列で判定する。画面もボタンを押せなくするが、担保はサーバ。
- **規則は2か所。** サーバ（server/api_diary*.go）とモック（web/src/api/mock.ts の `canSeeDiary`・`saveDiary`・`approveDiary`・`withdrawDiary`・`revokeDiaryApproval`・`guardianDiaries`）に同じ規則と文言がある。テストもサーバ（server/api_diary_*_test.go）とモック（web/tests/）の両方にある。
- **設計に無い値は【仮置き】。** 個人日誌の対象クラスを在籍クラスに限ること、ロックの操作の知らせの間隔（30秒）、無操作を過ぎたロックの扱い、定型文の置き場、共有された日誌の上限 100 件、などは web/仮置き値.md にある。
- **古い DB は起動のときに移す。** `ensureInternalDiary`（db_diary.go 22〜73行）が、保護者への共有の古い列を外し、申請者の列とヒヤリハットの欄を足す。あわせて、保護者のチャットに残っていた古い「日誌の共有の知らせ」（`source_type` 2・3）を取り消し済みにする。何度呼んでも同じ結果になる。
