# 05 日誌

> この説明は commit 41fbc463（2026-11-26 の本線）のコードに合わせてある。引いたコードと行番号は、どちらもこの版のもの。

## この機能でできること

- 保育士（一般の職員）と園長（管理者）が、園児やクラスの記録を書く。画面は職員のタブレット・PC の「日誌」。
- 担当クラスの無い一般の職員（フリー）は、全クラスの日誌を読むだけで、書けない（基本設計書「権限と利用可能機能」(6-1) ※1）。
- 日誌は**園内の記録**である。どの状態でも、保護者には届かない（基本設計書「日誌システム（園内の記録）」(4-6)）。
- 例外は1つだけある。保育士が申請するときに「保護者へ共有する」を選び、管理者が承認した**個人日誌**は、その子の保護者が「園からの日誌」で読める（2026-10-29 に持ち主が決めた）。
- 書いた日誌は、下書き → 申請 → 管理者の承認、の順に進む。差し戻し・申請の取り下げ・承認の取り消しもある。
- 同じ日誌を2人が同時に直さないよう、編集ロック（いま直している人を1人に決める仕組み）をかける。
- 本文には、雛形・定型文・きょうのようす（連絡帳の午睡と食事）を入れられる。園児タイムラインで、その子の記録を日付の順に見られる。
- 本文の横の「AI で下書き」で、本文の見出しごとの下書きを入れられる（個人日誌・クラス日誌・週案・月案。ヒヤリハットには使えない）。下書きは本文の欄に入るだけで、保存と申請は職員が押す（節 13〜24）。

## 記録の種類と状態

コード値は [web/src/api/codes.ts](../web/src/api/codes.ts) 22〜27行にある。DB の列の制約は [server/db_diary.go](../server/db_diary.go) 108・113行（`t_diary` の定義）にある。記録の種類でテーブルを分けず、1つの `t_diary` に入れる。

| 列 | 値 |
| :-- | :-- |
| `record_type`（記録種別） | 1 個人日誌・2 クラス日誌・3 週案・月案・4 ヒヤリハット |
| `status`（状態） | 1 下書き・2 申請中・3 承認済・4 差し戻し |

個人日誌とヒヤリハットは園児（`child_id`）を対象にする。クラス日誌と週案・月案は `child_id` を空にし、クラス（`class_id`）を対象にする。

状態の移り変わりは次のとおり。

| 操作 | だれが | 状態 | サーバの関数 |
| :-- | :-- | :-- | :-- |
| 下書き保存 | 職員 | （新規）→ 1、1 → 1、4 → 4 | `handleSaveDiary`・`updateDiary` |
| 申請 | 職員 | （新規）→ 2、1 → 2、4 → 2 | `handleSaveDiary`・`updateDiary` |
| 承認 | 管理者（自分が申請したものは不可） | 2 → 3 | `handleApproveDiary` |
| 差し戻し（理由は必須） | 管理者 | 2 → 4 | `handleReturnDiary` |
| 申請の取り下げ | 申請した本人 | 2 → 1 | `handleWithdrawDiary` |
| 承認の取り消し（理由は必須） | 管理者 | 3 → 4 | `handleRevokeDiaryApproval` |

## 流れ

1. 職員が日誌作成・編集画面を開く。既存の日誌なら、まず編集ロックを取る（`POST /api/diaries/{id}/lock`）。
2. 書いて「下書き保存」を押すか、「確認へ進む」で日誌確認画面へ移り「申請」を押す。どちらも `POST /api/diaries`（`handleSaveDiary`）へ送る。
3. サーバは、書ける範囲・入力・ロックを確かめてから `t_diary` と写真（`t_diary_attachment`）を1つのトランザクション（全部書くか、何も書かないかのまとまり）で書く。そのあと操作ログを残し、`notifyDiary` で、その日誌を読める職員の開いている画面へ知らせる。
4. 管理者が承認待ち一覧（`GET /api/diaries/pending`）から日誌承認画面を開き、承認（`.../approve`）か差し戻し（`.../return`）を押す。
5. 申請した本人は取り下げ（`.../withdraw`）、管理者は承認の取り消し（`.../revoke-approval`）ができる。
6. 共有を選んだ個人日誌が承認されると、保護者は `GET /api/guardian/diaries` で読める。保護者は `/api/diaries/...` の経路を使えない。
7. 日誌作成・編集画面で「AI で下書き」を押すと、本文の見出しの行・記録日・メモ（と、個人日誌なら園児）を `POST /api/ai/drafts`（`purpose: diary`）へ送る。サーバは `handleAiDiary` で、使える条件・名前の置き換え・1日の上限を確かめてから外部の AI を呼び、見出しごとの下書きを1つの文にして返す。画面はそれを本文の欄に入れる（保存はしない）。

```
DiaryEditScreen ──ロックの取得・操作の知らせ──▶ /api/diaries/{id}/lock
   │ 下書き保存 ／ 確認へ進む
   ▼
DiaryConfirmScreen ──申請──▶ POST /api/diaries ──▶ handleSaveDiary ──▶ t_diary・t_diary_attachment
                                                        └──▶ 操作ログ・notifyDiary（職員だけ）
DiaryApproveScreen ──承認・差し戻し──▶ POST /api/diaries/{id}/approve ｜ return
GuardianDiaryScreen ◀── GET /api/guardian/diaries（共有を選んで承認された個人日誌だけ）
DiaryEditScreen（AiDraftPanel）──「AI で下書き」──▶ POST /api/ai/drafts（purpose: diary）──▶ handleAiDiary ──▶ 外部の AI
   ▲                                                                            └──▶ 操作ログ（文は残さない）
   └── 下書き（本文の欄に入れるだけ。保存・申請は職員が押す）
```

### 1. だれが日誌を読めるか・書けるか（server/api_diary.go 117〜151・175〜196行）

```go
//
```

**解説**

- 範囲の条件は2つある。`visibleDiaryCondition` は**読める範囲**、`writableDiaryCondition` は**書ける範囲**の、SQL の WHERE に足す条件と引数を返す。前は1つの条件で読む経路も書く経路も守っていたが、PR #375 で2つに分けた。
- 書ける範囲：管理者（ロール 1）はすべて、一般（ロール 2）は自分の担当クラスの分だけ。個人日誌・ヒヤリハット（`child_id` がある）は、その園児が担当クラスに在籍しているかで決める。クラス日誌・週案（`child_id` が空）は、日誌の `class_id` で決める。担当クラスの無い一般（フリー）と保護者（ロール 3）は `1 = 0` で、何も書けない。
- 読める範囲は、フリーのときだけ書ける範囲より広い（128〜131行）。在籍中（`enrollment_status = '1'`）で取り消していない園児の個人日誌・ヒヤリハットと、今年度のクラスのクラス日誌・週案を読める。`canReadChild`・`canReadClass`（server/scope.go）と同じ範囲で、退園・卒園した園児の日誌と、過年度のクラスのクラス日誌は読めない。フリー以外は、書ける範囲と同じ（132行）。
- なぜ：フリーは全クラスを閲覧のみで見られ、記録の作成・編集・確認はできない（基本設計書「権限と利用可能機能」(6-1) ※1）。前の1つの条件はフリーを `1 = 0` にしていて、フリーには日誌が1件も出なかった（受け入れテスト 06-045）。読める範囲だけを広げると書く経路も開くので、書ける範囲を別に持った（PR #375）。
- 保護者は、どちらの条件でも `1 = 0` で何も出ない。そのうえ `requireDiaryStaff`（163〜173行）が、日誌の経路の入口で保護者を 403（権限が無いときの応答）にする。承認済みでも参照範囲は広がらず、保護者へは返さない（基本設計書「日誌システム（園内の記録）」(4-6)、詳細設計書「日誌」(4-13)）。
- `canSeeDiary` と `canWriteDiary` は、それぞれの条件で1件だけを判定する（中身は同じ `diaryMatches`）。一覧（`handleListDiaries` 227行〜。足すのは232行）と1件（`handleGetDiary` 291行〜。足すのは301行）は `visibleDiaryCondition` をそのまま WHERE に足す。添付（`handleDiaryAttachments` 442行〜。判定は452行）・ロックの状態（`handleLockOf`、[server/api_diary_write.go](../server/api_diary_write.go) 1005行）・開いている画面への知らせ（`notifyDiary`、[server/events.go](../server/events.go) 380行）は `canSeeDiary`、書く経路（書き換え・申請の取り下げ・ロックの取得）は `canWriteDiary` を使う（3・5・6）。無い日誌も「読めない」と同じ 403 にして、あるかどうかを推測させない。

### 6. 編集ロックを取る（server/api_diary_write.go 852〜892行）

**解説**

- ロックは `t_diary_lock` に、1つの日誌につき1行で持つ。列は識別子（`lock_token`）・持っている職員・取った時刻・最終操作時刻。

- ロックの状態を返す `handleLockOf`（995〜1024行）は、識別子を返さない。渡すと、その識別子で編集中の日誌を上書きできてしまう（GitHub Issue #166）。
- 【仮置き】無操作の時間を過ぎても、ほかの職員が取り直すまでは元の識別子を有効とみなす（969〜975行。web/仮置き値.md「日誌の編集ロックの動き」）。

- `pagehide`（タブを閉じる・読み込み直す）でも解除を送る。

- 取得と解除は、[diaryLock.ts](../web/src/screens/diary/diaryLock.ts) の `inOrder`（37〜41行）で、送った順にサーバへ届ける。開発時の StrictMode（画面を2回描く React の確かめ）で取得と解除が続けて出ても、前後しないようにするため。
- 入力が変わると、30秒（`LOCK_TOUCH_MS`、【仮置き】）に1回まで `touchLock` を送る（229〜235行）。

- `aiDraftInput` のうち `RecordType`（記録種別。1 個人日誌・2 クラス日誌・3 週案・月案・4 ヒヤリハット）・`Headings`（本文の見出しの名前）・`ShareToGuardian`（保護者へ共有する個人日誌か）は、日誌の下書きだけが読む。`ChildID`・`ClassID`・`Date`・`Memo` は連絡帳と同じ項目を使う。`ClassID` はポインタで、送られなければ nil になる。
- 【仮置き】`record_type` と `share_to_guardian` は、設計の要求の形（詳細設計書「保育日誌の下書き」(8-12)）に足した（web/仮置き値.md「保育日誌の AI の下書き」）。なぜ：ヒヤリハットを断り、週案・月案だけ記録日を365日先まで認めるには、サーバが記録種別を知る必要がある。共有を選んだ個人日誌の指示の文を替えるには、共有を選んだかを知る必要があるが、日誌はまだ保存されておらず、サーバは知らない。
- AI を使える条件の共通の部分（`ai.enabled`・キー・保護者の同意）、1日の上限、外部の AI を呼ぶ口（`draftWriter`）、設定画面の AI の区画は、[09 ダッシュボードと設定](./09-ダッシュボードと設定.md) が持つ。この文書は、日誌に固有の材料・指示の文・見出し・画面を書く。連絡帳の「園からのひとこと」の下書きは [03 連絡帳](./03-連絡帳.md) と 09 を見る。

### 14. 日誌に AI の下書きを使える条件（server/api_ai_diary.go 64〜89行）

```go
/*
aiDiaryWritable は、その職員がその日誌（の下書き）を書ける範囲か。日誌の作成と同じ判定（api_diary_write.go の handleSaveDiary）。
個人日誌は、園児を参照でき、そのクラスを使え、園児がそのクラスに在籍している。クラス日誌・週案月案は、そのクラスを使える
（担当クラスの無い一般（フリー）は書けない）
*/
func (a *app) aiDiaryWritable(u *SessionUser, recordType, childID string, classID int64) bool {
	if !u.isStaff() || !a.canUseClass(u, classID) {
		return false
	}
	if recordType == "1" {
		return a.canSeeChild(u, childID) && a.childInClass(childID, classID)
	}
	return true
}

// aiAvailableForDiary は、その職員がその日誌に AI の下書きを使えるか（8-12「使える条件」）。
// 使える条件（8-3）に、日誌を書ける判定を重ねる。個人日誌はその園児、クラス日誌・週案月案はクラスの全園児が宛先
func (a *app) aiAvailableForDiary(u *SessionUser, recordType, childID string, classID int64) bool {
	if !a.aiDiaryWritable(u, recordType, childID, classID) {
		return false
	}
	if recordType == "1" {
		return a.aiAvailableFor(u, aiTarget{ChildID: childID})
	}
	return a.aiAvailableFor(u, aiTarget{ClassID: classID})
}
```

**解説**

- `aiDiaryWritable` は、その職員がその日誌（の下書き）を書ける範囲かを返す。日誌を保存するときの判定（節 2 の `handleSaveDiary`）と同じにしてある。職員でない、または `canUseClass` が偽（管理者以外は自分の担当クラスだけ。担当クラスの無い一般＝フリーは偽）なら、使えない。個人日誌（記録種別 "1"）は、さらに園児を扱え（`canSeeChild`）、その園児がそのクラスに在籍している（`childInClass`）ことが要る。クラス日誌・週案月案は、クラスを使えればよい。
- `aiAvailableForDiary` は、`aiDiaryWritable` が偽なら偽。真なら、連絡帳と共通の `aiAvailableFor`（[server/api_ai.go](../server/api_ai.go) 76〜100行。条件の中身は [09](./09-ダッシュボードと設定.md) の「AI を使える条件」を見る）を重ねる。宛先は、個人日誌ならその園児（`aiTarget{ChildID}`）、クラス日誌・週案月案ならクラス（`aiTarget{ClassID}`）。クラスあては在籍園児の全員が、保護者の同意と「AI の下書きを使わない」の条件を満たしているときだけ使える。クラスのようすの文に、クラスの園児の名前が入りうるため。
- ヒヤリハット（"4"）は、この関数に来る前に `handleAiDiary` が断る（節 16）。
- ボタンを出すかを聞く `GET /api/ai/status`（`handleAiStatus`、[server/api_ai.go](../server/api_ai.go) 113〜124行）が見るのは、共通の `aiAvailableFor` だけで、日誌を書ける判定は含まない。日誌を書ける判定は、下書きを頼まれたとき（`POST /api/ai/drafts`）に、ここで足される。画面は、書けない人（フリー・申請中・承認済み）には部品そのものを出さない（節 21）。
- なぜ：日誌は保護者に届かない園内の記録だが、外部へ送る守り（園の有効化・保護者の同意と拒否・送る項目の最小化・名前の置き換え・送った文を残さない）は、保護者へ届ける文と同じにする（api_ai_diary.go の頭のコメント）。そのうえで、書けない人に下書きを作らせないよう、日誌を書ける判定を足した。

### 15. 見出しを整える（server/api_ai_diary.go 28〜62行）

```go
// 見出しと本文の上限（詳細設計書「保育日誌の下書き」(8-12)）
const (
	aiDiaryHeadingsMax   = 20
	aiDiaryHeadingMax    = 50
	aiDiaryBodyMax       = 2000
	aiDiaryDefaultHeader = "記録"
)

// normalizeAiHeadings は、送られた見出しを整える。両端の空白と「【」「】」を外し、空なら誤り。
// 同じ見出しは最初の1つだけ残す（同じ見出しが2度出ない形を返してもらうため）。空の配列は「【記録】」1つとして扱う（8-12）。
// 数と長さの上限（0〜20個・1つ50文字）を超えたら誤り
func normalizeAiHeadings(raw []string) ([]string, bool) {
	if len(raw) > aiDiaryHeadingsMax {
		return nil, false
	}
	out := []string{}
	seen := map[string]bool{}
	for _, h := range raw {
		h = strings.TrimSpace(h)
		if strings.HasPrefix(h, "【") && strings.HasSuffix(h, "】") {
			h = strings.TrimSpace(strings.TrimSuffix(strings.TrimPrefix(h, "【"), "】"))
		}
		if h == "" || tooLong(h, aiDiaryHeadingMax) {
			return nil, false
		}
		if !seen[h] {
			seen[h] = true
			out = append(out, h)
		}
	}
	if len(out) == 0 {
		out = []string{aiDiaryDefaultHeader}
	}
	return out, true
}
```

**解説**

- 定数は4つ。見出しの数の上限 `aiDiaryHeadingsMax`（20）、見出し1つの文字数の上限 `aiDiaryHeadingMax`（50）、返す下書きの文字数の上限 `aiDiaryBodyMax`（2000。日誌の本文の上限と同じ）、見出しが無いときの名前 `aiDiaryDefaultHeader`（「記録」）。
- `normalizeAiHeadings(raw)` は、送られた見出しの名前を整え、整えた一覧と、誤りでないかの真偽を返す。
  1. 数が20を超えたら誤り（整える前の個数で数える）。
  2. 見出しごとに、前後の空白を除く。両端が「【」「】」なら、その2つを外して、また前後の空白を除く（画面は【】の中だけを送るが、付いていても受ける）。
  3. 空、または50文字を超える（`tooLong`）なら誤り。
  4. 同じ見出しは最初の1つだけ残す（`seen`）。同じ見出しが2度出ない形を返してもらうため。
  5. 結果が空（見出しが無い・空の配列）なら、「記録」1つとして扱う。
- 誤りのとき `handleAiDiary` は 400（`msgBadRequest`）を返す。画面は20個・50文字までしか送らないので（節 20）、誤りになるのは画面の不具合のときだけである。
- モックの `normalizeAiHeadings`（[web/src/api/mock.ts](../web/src/api/mock.ts) 7011〜7021行）が同じ規則を持つ（節 23）。

### 16. 頼まれたとき：検査して、送る文を作り、外部の AI を呼ぶ（server/api_ai_diary.go 91〜190行）

```go
func (a *app) handleAiDiary(w http.ResponseWriter, r *http.Request, u *SessionUser, in aiDraftInput) {
	childID := strings.TrimSpace(in.ChildID)
	memo := strings.TrimSpace(in.Memo)
	var classID int64
	if in.ClassID != nil {
		classID = *in.ClassID
	}
	headings, okHeadings := normalizeAiHeadings(in.Headings)
	// 画面の不具合でしか起きない誤り（記録種別・宛先・日付・見出し）。ヒヤリハットだけは園児を持つので宛先の形は問わない
	okType := in.RecordType == "1" || in.RecordType == "2" || in.RecordType == "3" || in.RecordType == "4"
	okChild := in.RecordType == "4" || (in.RecordType == "1") == (childID != "")
	limit := today()
	if in.RecordType == "3" {
		limit = addDays(today(), diaryPlanMaxDays)
	}
	if !okType || classID <= 0 || !okChild || !isISODate(in.Date) || in.Date > limit || !okHeadings {
		writeErr(w, http.StatusBadRequest, msgBadRequest)
		return
	}
	if tooLong(memo, aiMemoMax) {
		writeErr(w, http.StatusBadRequest, msgAiMemoTooLong)
		return
	}
	// ヒヤリハットには使えない（基本設計書「使いどころと使わないところ」(4-11)）
	if in.RecordType == "4" || !a.aiAvailableForDiary(u, in.RecordType, childID, classID) {
		writeForbidden(w, msgAiUnavailableForTarget)
		return
	}

	personal := in.RecordType == "1"
	all, err := a.enrolledNameChildren()
	if err != nil {
		writeErr(w, http.StatusInternalServerError, msgContactLoadFailed)
		return
	}
	adults := a.aiAdultNames()
	recipients := []nameChild{}
	if personal {
		recipients = append(recipients, a.nameChildOf(childID))
	}
	// ⑤ メモに AI を使えない園児の名前があれば呼ばない（8-5 ⑤。決めたこと D-12）
	if names, _ := findOtherNames(memo, "memo", recipients, a.aiExcludedChildren(all)); len(names) > 0 {
		writeJSON(w, http.StatusBadRequest, apiError{Message: msgAiExcludedName, Kind: kindAiExcludedName})
		return
	}
	if !a.reserveAiCall(a.settingInt("ai.daily_limit", 300)) {
		writeJSON(w, http.StatusTooManyRequests, apiError{Message: msgAiLimit, Kind: kindAiLimit})
		return
	}
	defer a.releaseAiCall()

	// 送る文を作る（8-12「送る項目」「置き換え」）。メモと見出しは職員が書いた文、クラスのようすは記録の文
	replaced := false
	anonWritten := func(s string) string {
		out, hit := anonymize(s, recipients, all, adults...)
		replaced = replaced || hit
		return out
	}
	anonRecord := func(s string) string {
		out, _ := anonymize(s, recipients, all, adults...)
		return out
	}
	share := personal && in.ShareToGuardian
	notes, err := a.diaryClassNotes(classID, in.Date, share, anonRecord)
	if err != nil {
		writeErr(w, http.StatusInternalServerError, msgContactLoadFailed)
		return
	}
	sentHeadings := []string{}
	seen := map[string]bool{}
	for _, h := range headings {
		if ah := strings.TrimSpace(anonWritten(h)); !seen[ah] {
			seen[ah] = true
			sentHeadings = append(sentHeadings, ah)
		}
	}
	facts := aiDiaryFacts{Headings: sentHeadings, ClassNotes: notes, Memo: anonWritten(memo)}
	req := draftRequest{System: aiDiarySystemFor(share), User: aiJSON(facts), Schema: aiDiarySchema()}

	start := time.Now()
	ctx, cancel := context.WithTimeout(r.Context(), a.aiTimeoutOf())
	reply, err := a.ai.Write(ctx, req)
	cancel()
	draft, why := a.aiReadDiaryReply(ctx, reply, err, sentHeadings, recipients, all)
	childPtr := (*string)(nil)
	if personal {
		childPtr = s(childID)
	}
	if draft == "" {
		// 送った文・返った文・メモは、どのログにも出さない（8-7 (2)）
		log.Printf("AI の下書きを作れませんでした（用途 %s・%s・%dms）", in.Purpose, why, time.Since(start).Milliseconds())
		a.log(u.AccountID, fnDiary, opAiDraft, "t_diary", nil, childPtr, nil,
			s(fieldsJSON([]field{{"用途", aiPurposeLabel(in.Purpose)}, {"結果", "失敗"}})))
		writeJSON(w, http.StatusServiceUnavailable, apiError{Message: msgAiFailed, Kind: kindAiUnavailable})
		return
	}
	a.log(u.AccountID, fnDiary, opAiDraft, "t_diary", nil, childPtr, nil,
		s(fieldsJSON([]field{{"用途", aiPurposeLabel(in.Purpose)}, {"結果", "成功"}})))
	writeJSON(w, http.StatusOK, aiDraftResult{Drafts: []string{draft}, ReplacedOtherNames: replaced})
}
```

**解説**

- はじめに要求の値を整える。`childID`・`memo` は前後の空白を除く。`classID` は、送られなければ 0。`headings` は `normalizeAiHeadings`（節 15）を通し、誤りでないかを `okHeadings` に持つ。
- 画面の不具合でしか起きない誤りは、400（`msgBadRequest`）で断る。`okType` は記録種別が1〜4のどれか。`okChild` は、ヒヤリハット（4）は園児の有無を問わず、個人日誌（1）は園児が要り、クラス日誌・週案月案は園児を持たないこと。`limit` は記録日の上限で、当日（`today()`）まで。週案・月案（3）だけ365日先（`diaryPlanMaxDays`、[server/api_diary_write.go](../server/api_diary_write.go) 493行）まで。ほかに `classID <= 0`・記録日が日付の形でない（`isISODate`）ときも 400。
- メモは500文字まで（`aiMemoMax`、[server/api_ai.go](../server/api_ai.go) 178行）。超えたら 400「メモは500文字以内で入力してください。」（`msgAiMemoTooLong`）。
- ヒヤリハット（4）か、`aiAvailableForDiary`（節 14）が偽なら、403「AI の下書きは使えません。そのまま書いて送れます。」（`msgAiUnavailableForTarget`）。ヒヤリハットには使わない（基本設計書「使いどころと使わないところ」(4-11)）。断る理由は返さない。断った子かどうかを見せないため。
- 名前の置き換えの用意。`all` は在籍園児の名前の一覧（`enrolledNameChildren`）。`adults` は園の保護者と職員の氏名（`aiAdultNames`、[server/api_ai.go](../server/api_ai.go) 423〜443行。保護者は「保護者の方」、職員は「先生」に伏せる）。`recipients` は、個人日誌ならその園児1人（`nameChildOf`）、ほかは空。空のときは宛先の園児がいないので、クラスの園児は全員が「おともだち」になる。置き換えの規則そのもの（`anonymize`・`findOtherNames`・`restoreName`、[server/namecheck.go](../server/namecheck.go)）は、連絡帳の他児の名前の照合と同じ関数を使う（[03 連絡帳](./03-連絡帳.md) を見る）。
- メモに、AI を使えない園児（保護者が断った・まだ同意していない）の名前があれば、AI を呼ばずに 400（`msgAiExcludedName`、`kind: ai_excluded_name`）を返す（詳細設計書「置き換えの手順」(8-5) の⑤、決めたこと D-12）。見るのはメモだけで、クラスのようすには当てない。
- 1日の上限。`reserveAiCall`（api_ai.go 405〜414行）が、その日に成功した数と呼び出し中の数の合計を、`ai.daily_limit`（既定300）と比べて、足りていれば呼び出し中の数を1つ増やす。達していれば 429「きょうの AI の下書きの回数を使い切りました。そのまま書いて送れます。」（`kind: ai_limit`）。`defer a.releaseAiCall()` で、終わったら呼び出し中の数を戻す。上限は園全体で1つで、連絡帳の下書きと日誌の下書きの数を分けない。
- 送る文を作る。`anonWritten` は職員が書いた文（メモ・見出し）の置き換えで、置き換えたら `replaced` を立てる。`anonRecord` は記録の文（クラスのようす）の置き換えで、`replaced` は立てない。`replaced` が立つと、応答の `replaced_other_names` が真になり、画面が「ほかのお子さんの名前は『おともだち』に置き換えて送りました。」を添える。職員が書いたものを置き換えたときだけ知らせるため。
- `share` は `personal && in.ShareToGuardian`。共有は個人日誌だけで、クラス日誌・週案月案に付けても使わない。`notes` は `diaryClassNotes`（節 17）。`sentHeadings` は、見出しも `anonWritten` を通し、置き換えた結果が同じになったものは1つにする（見出しに園児の名前が入っていたとき）。
- `facts` は `aiDiaryFacts{見出し・クラスのようす・先生のメモ}`（節 17）。`req` は `draftRequest` で、`System` に `aiDiarySystemFor(share)`（節 18）、`User` に `aiJSON(facts)`（JSON の文字列）、`Schema` に `aiDiarySchema()` を入れる。
- 呼び出し。`context.WithTimeout` で全体の時間の上限（`aiTimeoutOf`。既定は `aiTimeout` の10秒、[server/ai.go](../server/ai.go) 53行）を付け、`a.ai.Write` を呼ぶ。`a.ai` が外部の AI を呼ぶ口（`draftWriter`。本物は [server/ai_claude.go](../server/ai_claude.go)、テストは偽物。[09](./09-ダッシュボードと設定.md) を見る）。返りは `aiReadDiaryReply`（節 19）が、下書き（`draft`）と失敗の理由（`why`）にする。
- 失敗のとき（`draft == ""`）：サーバのログには「用途・理由・かかった時間（ミリ秒）」だけを出し、送った文・返った文・メモはどのログにも出さない（詳細設計書「呼び出し・上限・失敗のとき」(8-7 (2))）。操作ログには、機能＝日誌（`fnDiary`）・操作＝AI の下書き（`opAiDraft`）・表 `t_diary`・個人日誌なら対象の園児・変更後 `{"用途":"保育日誌","結果":"失敗"}` を残す。応答は 503「いまは下書きを作れません。そのまま書いて送れます。」（`msgAiFailed`、`kind: ai_unavailable`）。
- 成功のとき：同じ操作ログを「成功」で残し、`{ drafts: [下書き1つ], replaced_other_names }` を 200 で返す。下書きは1つだけで、日誌（`t_diary`）には何も書かない。保存・申請は職員が画面で押す。
- 呼ぶ前に止めたもの（400・403・429）は、操作ログに残さない（[server/api_ai.go](../server/api_ai.go) 254行のコメント。テストが確かめる）。

### 17. AI へ送る材料は、見出し・クラスのようす・メモの3つだけ（server/ai_facts.go 165〜198行）

```go
// aiDiaryFacts は、保育日誌の下書きに渡す中身（詳細設計書「保育日誌の下書き」(8-12 (1))）。見出し・クラスのようす・先生のメモだけ
type aiDiaryFacts struct {
	Headings   []string `json:"見出し"`
	ClassNotes []string `json:"クラスのようす"`
	Memo       string   `json:"先生のメモ,omitempty"`
}

/*
diaryClassNotes は、保育日誌の下書きの材料の「クラスのようす」（詳細設計書「保育日誌の下書き」(8-12)「送る項目」①）。
その日（date）のそのクラスの t_contact_class の、取り消していない body だけを読み、時刻の順に並べて anon（置き換え）を通す。
個人日誌でも、その子の食事・午睡・ひとことは読まない（日誌には「きょうのようすから入れる」で入る）。
共有を選んだ個人日誌（onlyShown）は、保護者に出さない設定（contact.show_items）でクラスのようすを外していれば送らない
（【仮置き】保護者に出していない事実を、保護者へ届く文に書かせないため。決めたこと D-26 と同じ考え方。web/仮置き値.md）
*/
func (a *app) diaryClassNotes(classID int64, date string, onlyShown bool, anon func(string) string) ([]string, error) {
	notes := []string{}
	if onlyShown && !a.guardianSeesItem("class") {
		return notes, nil
	}
	rs, err := a.db.Query(`SELECT body FROM t_contact_class
```

### 19. 返ってきた下書きを日誌の本文にする（server/api_ai_diary.go 192〜251行）

```go
// aiDiarySection は、返った JSON の見出し1つ分
type aiDiarySection struct {
	Heading string `json:"heading"`
	Text    string `json:"text"`
}

/*
aiReadDiaryReply は、呼んだ結果を日誌の下書きにする（8-12「出力の形」「返す形」）。使えないときは空の文字列と、ログに出す理由を返す。
失敗の振り分けは保護者へ送る文と同じ（aiCallFailure）。
返った見出しは、送った見出しのどれかと一致し、同じ見出しが2度出ず、送った順に並んでいること。
見出しの無い欄は空の文として扱う。「【見出し】」と文をつないで、置き換えを戻す。全体が2,000文字を超えたら使わない
*/
func (a *app) aiReadDiaryReply(ctx context.Context, reply draftReply, err error, sent []string, recipients, all []nameChild) (string, string) {
	if why := a.aiCallFailure(ctx, reply, err); why != "" {
		return "", why
	}
	dec := json.NewDecoder(strings.NewReader(reply.JSON))
	dec.DisallowUnknownFields()
	var v struct {
		Sections *[]aiDiarySection `json:"sections"`
	}
	if dec.Decode(&v) != nil || v.Sections == nil {
		return "", "形が合わない"
	}
	index := map[string]int{}
	for i, h := range sent {
		index[h] = i
	}
	texts := make([]string, len(sent))
	last := -1
	for _, sec := range *v.Sections {
		i, ok := index[sec.Heading]
		if !ok || i <= last {
			return "", "形が合わない"
		}
		last = i
		texts[i] = strings.TrimSpace(sec.Text)
	}
	parts := make([]string, 0, len(sent))
	for i, h := range sent {
		part := "【" + h + "】"
		if texts[i] != "" {
			part += "\n" + texts[i]
		}
		parts = append(parts, part)
	}
	draft := strings.Join(parts, "\n\n")
	if len(recipients) > 0 {
		draft = restoreName(draft, recipients[0])
	}
	draft = strings.TrimSpace(draft)
	if draft == "" || tooLong(draft, aiDiaryBodyMax) {
		return "", "形が合わない"
	}
	// 宛先以外の園児の名前が入っていたら（名前を渡していないので起きないはずだが）使わない（8-6 (3)）
	if names, _ := findOtherNames(draft, "draft", recipients, all); len(names) > 0 {
		return "", "ほかの園児の名前"
	}
	return draft, ""
}
```

**解説**

- `aiDiarySection` は、返った JSON の見出し1つ分（`heading`・`text`）。
- `aiReadDiaryReply(ctx, reply, err, sent, recipients, all)` は、`(下書き, 失敗の理由)` を返す。使えないときは、下書きが空の文字列になる。
  1. `aiCallFailure`（[server/api_ai.go](../server/api_ai.go) 310〜335行）が、時間切れ・提供者の状態コード・接続の失敗・拒否を振り分ける。理由が返れば、そのまま返す。キーが無効（401・403）と分かったら、起動し直すまで AI を使えない扱いにする（決めたこと D-11）。連絡帳の下書きと同じ。
  2. 返った JSON を、余計な項目を認めずに（`DisallowUnknownFields`）`{ "sections": [...] }` として読む。読めない・`sections` が無いときは「形が合わない」。
  3. 返った見出しは、送った見出し（`sent`）のどれかと一致し、送った順に並んでいなければならない。`index` が送った見出しの位置で、`i <= last` を断るので、同じ見出しが2度出ても、順が前後しても「形が合わない」になる。返ってこなかった見出しは、空の文として扱う（`texts`）。
  4. 送った順に、「【見出し】」の行を作り、文があればその次の行に文を置く。見出しどうしは空行（`\n\n`）でつなぐ。雛形と同じ形で、そのまま本文に入る。
  5. 個人日誌（`recipients` が1人）は、`restoreName` で「〇〇ちゃん」と「〇〇」を、宛先の園児の呼び名（`callName`。呼び名があればそれ、無ければ名に「ちゃん」）に戻す。「おともだち」は戻さない。クラス日誌・週案月案は宛先の園児がいないので、何も戻さない。
  6. 前後の空白を除いた結果が空、または2,000文字（`aiDiaryBodyMax`）を超えるなら「形が合わない」。見出しの行も含めた全体の字数で数える。
  7. 宛先以外の園児の名前が入っていたら（名前を渡していないので起きないはずだが）「ほかの園児の名前」で使わない（詳細設計書「指示の文と出力の形」(8-6 (3))）。
- 失敗の理由は、サーバのログにだけ出す。応答に載るのは、どの理由でも 503 の同じ文（節 16）。
- なぜ：返った文を、本文にそのまま入れられる形に直すところで、サーバが形・字数・名前を確かめる。モデルが指示に従わなかったときに、本文の上限を超えた文や他の園児の名前が日誌の入力欄に入らないようにするため。

### 20. 画面：本文の見出しの行を取り出す（web/src/screens/diary/diaryHeadings.ts 10〜38行）

```ts
/** 見出しの数と長さの上限（server/api_ai_diary.go の aiDiaryHeadingsMax・aiDiaryHeadingMax） */
const HEADINGS_MAX = 20;
const HEADING_MAX = 50;

/** 本文の行が見出しの行なら、その名前（【】の中）を返す。見出しの行でなければ null */
function headingOf(line: string): string | null {
  const t = line.trim();
  if (!t.startsWith('【') || !t.endsWith('】')) return null;
  return t.slice(1, -1).trim();
}

/** 本文の中の見出しの名前を、現れた順に返す */
export function diaryHeadings(body: string): string[] {
  const out: string[] = [];
  for (const line of body.split('\n')) {
    const h = headingOf(line);
    if (h && [...h].length <= HEADING_MAX && out.length < HEADINGS_MAX) out.push(h);
  }
  return out;
}

/**
 * 本文に、見出しの行でも空の行でもない行（文）があるか。
 * 【仮置き】雛形を呼び出しただけ（見出しの行だけ）の本文は「文が無い」と読み、AI の下書きをそのまま入れる。文があれば置き換えずに候補で示す
 * （詳細設計書 (2-13 (7)) は「本文が空なら入れ、文があれば候補」。web/仮置き値.md）
 */
export function hasDiarySentence(body: string): boolean {
  return body.split('\n').some((line) => line.trim() !== '' && headingOf(line) === null);
}
```

**解説**

- `HEADINGS_MAX`（20）・`HEADING_MAX`（50）は、サーバの `aiDiaryHeadingsMax`・`aiDiaryHeadingMax`（節 15）と同じ値。
- `headingOf(line)` は、行の前後の空白を除き、「【」で始まり「】」で終わる行なら、その中身（【】の中の、前後の空白を除いたもの）を返す。見出しの行でなければ `null`。
- `diaryHeadings(body)` は、本文を行ごとに見て、見出しの名前を現れた順に返す。空の見出し（「【】」）と、50文字を超える見出しの行は送らない。21個目からも送らない。同じ見出しの重なりは、サーバが1つにする（節 15）。
- `hasDiarySentence(body)` は、本文に、空の行でも見出しの行でもない行（文）が1行でもあれば真。【仮置き】雛形を呼び出しただけ（見出しの行だけ）の本文は「文が無い」と読み、AI の下書きをそのまま入れる。文があれば置き換えずに候補で示す（詳細設計書「日誌の画面（作り直し）」(2-13 (7)) は「本文が空なら入れ、文があれば候補」。web/仮置き値.md）。
- なぜ：サーバは21個以上・51文字以上の見出しを 400 で断る。長い日誌でも、画面の側で上限に収めて、この誤りを起こさない。

- 作っている間は「下書きを作っています（10秒ほどかかることがあります）」を出し、ボタンを押せなくして二度押しを止める（`making`）。

## 気をつけているところ

- **保護者には届かない。** 日誌の経路は入口（`requireDiaryStaff`）で保護者を 403 にする。開いている画面への知らせも職員だけに送る（events.go の `notifyDiary` は `u.isStaff()` を条件にする）。保護者が読めるのは、`/api/guardian/diaries` で返す「共有を選んで承認された個人日誌」の6項目だけ。
- **参照範囲はサーバで担保する。** 一覧・1件・添付・ロックの状態は読める範囲（`visibleDiaryCondition`／`canSeeDiary`）、書き換え・取り下げ・ロックの取得は書ける範囲（`writableDiaryCondition`／`canWriteDiary`）を通す。読めても書けない人（フリーの職員）がいるので、書く経路に読める範囲を使わない。画面でボタンを隠すだけに頼らない（基本設計書「権限チェックの実装方針」(6-2)）。添付は件数とファイル名だけでも担当外の園児の写真があると分かるので、権限を通してから返す（api_diary.go 434〜455行。GitHub Issue #153）。
- **同時に直させない。** 編集ロックの識別子を保存のたびに照合し、合わなければ断る。ロックは編集画面から確認画面へ引き継ぎ、申請でサーバが外す。
- **読んだ版で確かめる。** 承認・取り下げ・承認の取り消しは、画面が読んだ `updated_at` を送り、今の版と違えば 409 にする。書き換えの WHERE にも状態と版を入れる。
- **自分の申請は自分で承認しない。** 申請者の列で判定する。画面もボタンを押せなくするが、担保はサーバ。
- **規則は2か所。** サーバ（server/api_diary*.go）とモック（web/src/api/mock.ts の `canSeeDiary`・`canWriteDiary`・`saveDiary`・`approveDiary`・`withdrawDiary`・`revokeDiaryApproval`・`guardianDiaries`）に同じ規則と文言がある。テストもサーバ（server/api_diary_*_test.go）とモック（web/tests/）の両方にある。日誌の AI の下書きも同じで、サーバ（server/api_ai_diary.go・ai_facts.go・ai_prompt.go）とモック（mock.ts の `aiDiaryDrafts`・`normalizeAiHeadings`・`aiAvailableForDiary`・`diaryClassNotes`・`AI_DIARY_SYSTEM`・`AI_DIARY_SHARED_RULE`）に同じ規則があり、指示の文は同じ文を両方に置く。
- **設計に無い値は【仮置き】。** 個人日誌の対象クラスを在籍クラスに限ること、ロックの操作の知らせの間隔（30秒）、無操作を過ぎたロックの扱い、定型文の置き場、共有された日誌の上限 100 件、日誌の AI の下書きの要求に足した `record_type`・`share_to_guardian`・共有を選んだ個人日誌の指示の文・見出しの渡し方・「本文が空」の読み方、モックの AI が返す日誌の文、などは web/仮置き値.md にある。
- **日誌の AI の下書きは、外へ送る守りを連絡帳の下書きと同じにする。** 日誌は保護者に届かない園内の記録だが、AI へ送るのは見出し・クラスのようす・メモの3つだけで（その子の食事・午睡・ひとことは送らない）、園児・保護者・職員の名前は置き換えてから送り、送った文・返った文・メモはどのログにも出さない。ヒヤリハットには使えない。使えるのは日誌を書ける職員だけで、担当クラスの無い一般（フリー）は使えない。下書きは本文の欄に入るだけで、保存・申請は職員が押す（節 13〜24）。
- **古い DB は起動のときに移す。** `ensureInternalDiary`（db_diary.go 22〜73行）が、保護者への共有の古い列を外し、申請者の列とヒヤリハットの欄を足す。あわせて、保護者のチャットに残っていた古い「日誌の共有の知らせ」（`source_type` 2・3）を取り消し済みにする。何度呼んでも同じ結果になる。
