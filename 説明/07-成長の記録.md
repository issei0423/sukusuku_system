# 07 成長の記録

> この説明は commit 74f09acf のコードで書いた。行番号はその版のもの。

## この機能でできること

- 職員は、発達チェック一覧画面で、クラスの園児ごとに前回の実施日・次回の予定日・状態（未実施・予定日が近い・予定どおり）を見る。
- 職員は、発達チェック入力画面で、項目ごとに「確認できた」「一部」「未確認」を選び、下書き保存か確定をする。所見（園内だけ）と保護者へのひとことも書ける。
- 管理者は、スケジュール設定画面で、園児ごとの次回の予定日を手で上書きする。予定の無い園児には、推奨の予定日を一括で当てる。共有範囲の設定画面で、項目ごとに保護者へ出すかを決める。
- 職員は、身体記録画面で、クラスの園児の身長・体重を続けて入れる。成長曲線（基準値の帯）と過去の記録を並べて見る。
- 保護者は、スマートフォンの成長の記録画面で、身長・体重のグラフと、確定した発達チェックの「できたこと」を見る。

システムは発達・発育の判定や診断をしない。記録と見える化に徹する（[server/api_dev.go](../server/api_dev.go) 13行・[server/api_physical.go](../server/api_physical.go) 16行のコメント）。この決まりが、画面の文言・保護者へ返す項目・グラフの描き方のすべてに効いている。
要求を受ける仕組み（ログイン・権限の共通の関数・知らせ）は [01 全体の仕組み](./01-全体の仕組み.md) を見る。連絡帳の「成長の記録に残す」は [03 連絡帳](./03-連絡帳.md) で扱う。

## 流れ

職員が発達チェックを確定し、保護者の成長の記録に届くまでを例にする。

1. 職員が発達チェック入力画面で結果を選び、「確定する」を押す。画面は `api.saveCheck` を呼ぶ（本番は `POST /api/development/checks`）。
2. サーバの `handleSaveDevelopmentCheck` が受ける。その園児を書ける職員か（`contactAccess` の Write）、実施日・所見・ひとことの長さを確かめる。ひとことがあれば、他児の名前の照合も通す。
3. トランザクションの中で、`t_development_check`（1回の記録）と `t_development_result`（項目ごとの結果）を書く。未入力の項目は行を作らない。操作ログを残す。
4. 確定なら `advanceDevelopmentSchedule` が次回の予定日を `t_development_schedule` に足す。
5. `notifyDevelopment` が、その園児を読める職員と、確定のときだけ保護者へ知らせを送る。
6. 保護者の成長の記録画面は知らせを受け、`GET /api/children/{childID}/growth` を読み直す。
7. サーバの `growthRecord` は、成長の記録の表を持たない。開いた時点の元の記録と設定から、届けてよい事実だけを組み立てて返す。

```
職員の画面                               Go サーバ                                     保護者の画面
DevInputScreen ─POST /api/development/checks─▶ handleSaveDevelopmentCheck
                                               ├ contactAccess（書けるか）・検査・他児の名前
                                               ├ t_development_check / t_development_result・操作ログ
                                               ├ advanceDevelopmentSchedule（次回の予定日）
                                               └ notifyDevelopment ─知らせ（確定のとき）─▶ GuardianGrowthScreen
                                                                                              │ 読み直す
              handleGrowthRecord ◀─GET /api/children/{id}/growth──────────────────────────────┘
              └ growthRecord（共有する「確認できた」とひとことだけ。所見・一部・未確認は返さない）
```

## コードを読む

**推奨スケジュールと予定日**

### 1. 推奨スケジュールの次の予定日を作る（server/dev_schedule.go 67〜93行）

```go
/*
next は、基準日（baseDate）から予定日を作る。推奨頻度がマスタに無い月齢では作らない（ok = false）。

【仮置き】節目の「あいだ」は、基準日の翌日から、推奨頻度で数えた日の前日まで（web/仮置き値.md「健診の節目の『あいだ』」）。
基準日ちょうどが節目のときは、節目を予定日にしない。その日を予定日にすると、翌日から「過ぎた」になるため。
節目が2つ入るときは、早いほうを取る。
*/
func (r scheduleRule) next(birthDate, baseDate string) (string, bool) {
	age := ageInMonths(birthDate, baseDate)
	interval, found := 0, false
	for _, f := range r.frequencies {
		if age >= f.from && age <= f.to {
			interval, found = f.days, true
			break
		}
	}
	if !found {
		return "", false
	}
	next := addDays(baseDate, interval)
	for _, m := range r.milestones {
		if d := monthAnniversary(birthDate, m); d != "" && d > baseDate && d < next {
			return d, true
		}
	}
	return next, true
}
```

**解説**
- 次の予定日は「基準日の月齢の推奨頻度の日数を足した日」である。推奨頻度は `m_development_frequency`（月齢の範囲ごとの間隔の日数）から読む。
- 基準日とその日のあいだに乳幼児健診の節目（既定は 18・36・60 か月）の応当日があれば、節目の日を予定日にする。節目の月齢は設定 `dev.milestone_months` から読む（34〜49行の `loadScheduleRule`）。
- 典拠は基本設計書「推奨スケジュールの作り方」(4-9) である。「あいだ」の端の扱い（基準日ちょうどの節目は使わない）は設計が決めていないので【仮置き】である（70〜72行、[web/仮置き値.md](../web/仮置き値.md)「健診の節目の『あいだ』」）。
- 推奨頻度がマスタに無い月齢では、予定日を作らない（`ok = false`）。
- この関数は3か所から呼ばれる。確定したとき（`advanceDevelopmentSchedule`）、予定の無い園児へ一括で当てるとき（`handleApplyRecommendedSchedules`）、スケジュール設定画面の「システムの提案」を作るとき（[server/api_dev.go](../server/api_dev.go) 420〜437行）である。
- 応当日（生まれた日と同じ日にちの日）は `monthAnniversary`（98〜109行）が作る。1月31日生まれの2月のように日が無い月は、その月の末日にする。月齢の計算 `ageInMonths`（[server/model.go](../server/model.go) 172行）と同じ考え方である（要件定義書「月齢の算出規則」(7-1 No.6)）。
- モックの同じ計算は [web/src/api/devSchedule.ts](../web/src/api/devSchedule.ts) の `recommendedScheduleDate`（54〜69行）にある。

### 2. 「未実施」と「予定日が近い」の判定（サーバ）（server/api_dev.go 321〜349行）

```go
/*
devOverdue は、発達チェックが「未実施」かを返す。

園児の最新の予定日（scheduledOn）を過ぎていて、その予定日以降に確定した実施（lastCheckedOn）が無ければ未実施とする。
予定日の当日は、まだ未実施にしない（基本設計書「発達チェックの実施」(4-8)「実施予定日を過ぎて」）。
発達チェック一覧（handleDevelopmentList）と職員ダッシュボード（handleStaffSummary）が同じ判定を使い、
件数を食い違わせない（GitHub Issue #164）。画面側のモック（web/src/api/mock.ts の isDevOverdue）と同じ規則
*/
func devOverdue(scheduledOn, lastCheckedOn *string) bool {
	if scheduledOn == nil || *scheduledOn >= today() {
		return false
	}
	return lastCheckedOn == nil || *lastCheckedOn < *scheduledOn
}

/*
devNear は、発達チェックの予定日が「近い」かを返す。

予定日まで、設定の日数（dev.notice_days_before。既定 7 日）以内で、その予定日以降に確定した実施が無ければ近い。
予定日の当日も近いに入れる（まだ「過ぎた」ではない）。予定日を過ぎたものは devOverdue が数えるので、重ならない。
典拠：基本設計書「推奨スケジュールの作り方」(4-9)「近づいた　予定日まで、設定の日数（「設定マスタ」(5-9)。既定 7 日）以内」、
画面詳細図「発達チェック一覧画面」(6-1) 項目13。画面側のモック（web/src/api/mock.ts の isDevNear）と同じ規則
*/
func devNear(scheduledOn, lastCheckedOn *string, noticeDays int) bool {
	if scheduledOn == nil || *scheduledOn < today() || *scheduledOn > addDays(today(), noticeDays) {
		return false
	}
	return lastCheckedOn == nil || *lastCheckedOn < *scheduledOn
}
```

**解説**
- 「未実施」は、最新の予定日を過ぎていて、その予定日以降に確定した実施が無い状態である。予定日の当日はまだ未実施にしない（基本設計書「発達チェックの実施」(4-8)「実施予定日を過ぎて」。GitHub Issue #164）。
- 「近い」は、予定日まで設定 `dev.notice_days_before`（既定 7 日）以内で、まだ実施していない状態である。当日は「近い」に入る。過ぎたものは「未実施」が数えるので、2つは重ならない（基本設計書「推奨スケジュールの作り方」(4-9)）。
- 日付は `'YYYY-MM-DD'` の文字列のまま大小を比べている。同じ形の文字列なら、辞書の順と日付の順が一致するからである。
- この2つの関数は、発達チェック一覧（`handleDevelopmentList`）と職員ダッシュボード（`handleStaffSummary`）の両方が使う。件数が画面ごとに食い違わないよう、判定を1か所にまとめた（Issue #164）。ダッシュボードの側は [09 ダッシュボードと設定](./09-ダッシュボードと設定.md) を見る。
- 下書きは「実施」に数えない。呼ぶ側が、確定（`status = '2'`）の記録だけから最後の実施日を引いて渡す（272〜276行）。

### 3. モックの同じ判定（web/src/api/mock.ts 2972〜2991行）

```ts
/**
 * 発達チェックが「未実施」か。園児の最新の予定日を過ぎていて、その予定日以降に確定した実施が無ければ未実施とする。
 * 予定日の当日は、まだ未実施にしない（基本設計書「発達チェックの実施」(4-8)「実施予定日を過ぎて」。GitHub Issue #164）。

 * サーバ側は server/api_dev.go の devOverdue

function isDevOverdue(scheduledOn: string | null, lastCheckedOn: string | null): boolean {
  if (!scheduledOn || scheduledOn >= today()) return false;
  return !lastCheckedOn || lastCheckedOn < scheduledOn;
}

/**
 * 発達チェックの予定日が「近い」か。予定日まで設定の日数（dev.notice_days_before。既定 7 日）以内で、
 * その予定日以降に確定した実施が無ければ近い。予定日の当日も近いに入れる。予定日を過ぎたものは isDevOverdue が
 * 数えるので重ならない（基本設計書「推奨スケジュールの作り方」(4-9)）。サーバ側は server/api_dev.go の devNear
 */
function isDevNear(scheduledOn: string | null, lastCheckedOn: string | null, noticeDays: number): boolean {
  if (!scheduledOn || scheduledOn < today() || scheduledOn > addDays(today(), noticeDays)) return false;
  return !lastCheckedOn || lastCheckedOn < scheduledOn;
}
```

- 2. のサーバの `devOverdue`・`devNear` と、名前だけ違う同じ規則である。業務の規則は Go サーバとモックの2か所にある（AGENTS.md「いちばん大事な決まり」）。

### 4. 一覧の「未入力 n 件」を数える（server/api_dev.go 278〜303行）


**解説**
- 「未入力」は、いちばん新しい記録（下書きを含む）について、その実施日の月齢の区分の項目のうち、結果の行が無いものの数である。
- 「未入力」と「未確認」は別の状態である。未入力は行が無いこと、未確認は `result = '3'` の行があることで表す（[server/api_dev_write.go](../server/api_dev_write.go) 15〜17行、基本設計書「発達チェック・身体測定」(5-7)）。チェック漏れとして強調するのは未入力だけである。
- 以前は確定した記録だけで数えていた。そのため下書きを保存しても一覧の件数が変わらず、入力画面と食い違っていた（GitHub Issue #143）。典拠は要件定義書「チェック漏れの強調」(4-5-2)「下書き保存された記録は、保存されていない項目を未入力として扱う」である。
- 区分は、その記録の実施日の月齢で決める（`categoryFor`、60〜71行）。区分と項目はマスタ（`m_development_category`・`m_development_item`）から読む。指針が改定されたら、マスタを直せば追従できる（基本設計書「発達チェック・身体測定」(5-7)）。
- 一覧の月齢の列は、予定日の時点の月齢である（305〜310行。基本設計書「月齢の算出」(4-8)）。画面の見出しにも「（予定日の時点）」と書いてある（[DevListScreen.tsx](../web/src/screens/growth/DevListScreen.tsx) 97〜98行）。

### 11. 保護者に「届くもの」がある確定だけを読む（server/api_growth.go 163〜166・188〜198行）

- 結果のうち `result = '1'`（確認できた）だけを出す。「一部」「未確認」・所見・前回との比較・記録した職員の名前は返さない（9〜17行のコメント）。項目の名前は、行を読み終えてから別の問い合わせで引く（223〜245行）。DB の接続が1本だからである。
- 1回の確定を「できたこと」の1件にまとめる（決めたこと D-31）。日時は `finalized_at`（初めて確定した日時）である。
- 保護者ホームの「新しい記録があります」（`growthNew`、173〜186行）も、同じ `growthDeliverable` の条件を使う。きょう初めて確定し、届くものがある記録があれば真になる。

### 12. 成長の記録を組み立てて、12件ずつ返す（server/api_growth.go 106〜112・134〜160行）

```go
	day := today()

	// 身長・体重：身体測定を共有するときだけ、未削除の行を全件・測った日の新しい順。before に左右されない
	out.SharePhysical = a.sharePhysical()
	if out.SharePhysical {
		rows, err := a.db.Query(`SELECT physical_record_id, measured_on, height_cm, weight_kg, updated_at FROM t_physical_record
			WHERE child_id = ? AND is_deleted = 0 ORDER BY measured_on DESC, physical_record_id DESC`, childID)
	// …（略）…
	limit := a.settingInt("paging.physical_history_count", 12)
	dev, err := a.growthDevelopmentEntries(childID, before, limit+1, day)
	if err != nil {
		return nil, err
	}
	contact, err := a.growthContactEntries(childID, before, limit+1)
	if err != nil {
		return nil, err
	}
	entries := append(dev, contact...)
	sort.SliceStable(entries, func(i, j int) bool {
		if entries[i].At != entries[j].At {
			return entries[i].At > entries[j].At
		}
		if entries[i].Kind != entries[j].Kind {
			return entries[i].Kind > entries[j].Kind // 【仮置き】同じ日時なら発達チェックを先に（web/仮置き値.md）
		}
		return entries[i].id > entries[j].id
	})
	// 13件目まで読んで、あれば next_before に12件目の日時を入れる
	if len(entries) > limit {
		entries = entries[:limit]
		next := entries[limit-1].At
		out.NextBefore = &next
	}
	out.Achievements = append(out.Achievements, entries...)
	return out, nil
```

**解説**
- 成長の記録は表を持たない。開いた時点の元の記録と設定を読んで組み立てる（基本設計書「発達チェック・身体測定」(5-8)）。
- 身長・体重は、設定 `growth.share_physical` が `"1"` のときだけ返す（`sharePhysical`、[server/events.go](../server/events.go) 491〜493行）。未削除の行を全件返し、ページ送りに左右されない。
- 「できたこと」は、発達チェック（11.）と、連絡帳で「成長の記録に残す」を付けたひとこと・写真（`growthContactEntries`、254〜284行）を混ぜて、新しい順に並べる。連絡帳の分は、その種類がいまの `contact.show_items` にあるものだけである（決めたこと D-30）。
- 1ページの件数は設定 `paging.physical_history_count`（既定 12）である。13件目まで読み、あれば12件目の日時を `next_before` に入れる。画面は「さらに読み込む」でこれを `before` に渡す（[GuardianGrowthScreen.tsx](../web/src/screens/growth/GuardianGrowthScreen.tsx) 59〜70行）。同じ日時のときの並び（発達チェックを先に）は【仮置き】である。
- 読める人は `contactAccess` の Read で決める（`handleGrowthRecord`、75行）。保護者は紐づけが有効か猶予中の自児である。権限の外も、園児が無いのも、同じ 403 と同じ文言にして、在るかどうかを漏らさない。
- 保護者は職員の経路 `GET /api/children/{childID}/physical` を使えない（[server/api_physical.go](../server/api_physical.go) 121〜127行で 403）。保護者が読むのは、この成長の記録の経路だけである。
- モックの `growthApi.growthRecord`（[web/src/api/mock.ts](../web/src/api/mock.ts) 5523行から）が同じ形を返す。

## 気をつけているところ

- **判定しない。** 画面・応答・グラフに、発達や発育の良し悪しの言葉を出さない。免責の文を、入力画面は保存のボタンの直上、身体記録画面はグラフの直下、保護者の画面は下端に置く。保護者の画面のテスト（`web/tests/growthScreens.test.tsx`）は、判定の言葉が出ないことも確かめる。
- **権限の担保はサーバにある。** 発達チェックの保存は `contactAccess` の Write、身体測定の登録は `canSeeChild`、予定日の上書き・一括で当てる・共有範囲の設定・測定値の削除・PDF 出力の記録は `requireAdmin` で止める。画面の出し分け（`RequireAdmin`・`messageLocked`）は使いやすさのためである（基本設計書「権限チェックの実装方針」(6-2)）。
- **保護者に見せない値。** 所見、「一部」「未確認」の結果、共有しない項目、前回との比較、記録した職員の名前、下書き。身体測定は `growth.share_physical` が `"1"` のときだけ出す。知らせも同じ規則で絞る（`notifyDevelopment` は確定のときだけ、`notifyPhysical` は共有するときだけ保護者へ送る）。
- **`growth.share_physical` を変える画面は、この版には無い。** 設定画面では読むだけの行で、理由は「共有範囲の設定の画面で変えます。」と出る（[settingsLabels.ts](../web/src/screens/admin/settings/settingsLabels.ts) 57行）。しかし共有範囲の設定画面は項目ごとの切り替えだけを持ち、このキーを書く所は `web/src` にも `server` の経路にも見つからなかった（検索で確かめた）。
- **未入力と未確認を混ぜない。** 未入力は行が無いこと、未確認は `result = '3'`。チェック漏れの強調は未入力だけ。
- **月齢は1つの関数で。** サーバは `ageInMonths`、画面は [web/src/api/util.ts](../web/src/api/util.ts) の `ageInMonths`。基準日は画面ごとに違う（一覧は予定日、入力は実施日、身体測定は測定日、園児一覧は今日）。表の見出しに何の時点かを書いてある（GitHub Issue #124）。
- **規則は2か所にある。** `devOverdue`／`isDevOverdue`、`scheduleRule.next`／`recommendedScheduleDate`、`handleSaveDevelopmentCheck`／`saveCheck`、`handleSavePhysical`／`physicalApi.save`、`growthRecord`／`growthApi.growthRecord`。片方だけを直さない。基準値も Go と TypeScript の2つのファイルにある。
- **仮置きの値。** 健診の節目の「あいだ」、予定の無い園児へ当てるときの基準日と範囲、次回の予定日を計算し直すきっかけ、同じ月の2件目、確定を取り消さないこと、登録完了の文言、同じ日時の「できたこと」の並びなどは、設計が決めていない。コードに【仮置き】と書き、[web/仮置き値.md](../web/仮置き値.md) に一覧がある。
