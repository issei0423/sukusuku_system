## 0 この文書について

**このペルソナは架空の人物であり、実在の保育士への聞き取りにもとづかない。** たたき台である。

- **デモを操作したのは Claude である。** 人が触った結果ではない。「感想」は、この人物の立場に立って画面を見たときの**推定**であり、利用者の声として引用しない
- **「見つけた問題点」は、実際に画面で起きたことだけを書いた。** 確かめきれなかったものは「確かめられなかったこと」(5) に分けた
- 問題の指摘と論点の提示に留め、**どう直すかの結論は書かない**
- 氏名はモックアップのデモデータのものである。実在の人物ではない

**1巡目との違い**

1巡目は「慣れた担任が、いつもの1日を過ごす」筋書きだった。2巡目は**「不慣れな人が、いつもと違うことに出会う」**筋書きにした。1巡目の「確かめられなかったこと」に挙げた、初回ログイン・差し戻しを受けたあとの修正・異常時の記録・ヒヤリハットの起票・写真の添付を通る。

| | 内容 |

## 3 感想（この人の立場で見たときの推定）

**助かると感じそうなところ**

- **間違えたとき、何が違うのかを言ってくれる。** パスワードが短い、確認と合わない、とそのつど出る。「壊した」と思わずに済む
- **差し戻しの理由が、開いたその画面の一番上にある。** 何を直せばよいかを人に聞きに行かなくてよい
- **異常時の記録から、ヒヤリハットの下書きが自動でできる。** 同じことを二度打たなくてよい。文字入力が遅い身には大きい
- **ダッシュボードに、自分がやるべきことが出ている。** 差し戻しがあることを、誰かに言われる前に知ることができる
- **アレルギー一覧に、なぜ全クラスが見えるのかが書いてある。** 見てよいものかどうかを迷わない

**不安になりそうなところ**

- **一時パスワードをそのまま使い続けられてしまう。** 「変更してください」と言われて同じものを入れたら通った。変えたつもりで、園長が口頭で伝えたパスワードがそのまま残る
- **異変に気づいた直後に、文章を2つ打つ。** 園児を選び、状況と対応を文章で書く。その間、子どもから目が離れる。緊急のときにまず何をすべきか（人を呼ぶ、119番など）は、画面のどこにも書かれていない
- **クラスのグループに書いたものが、保護者にも見える。** 同僚に聞くつもりで書いた一言が、そのまま保護者に届く。書く前に、誰に届くのかを知らせてくれない
- **写真を付けたつもりで、何も付いていない。** 「＋ 追加」を押すと「1」と出るが、どの写真なのかが分からない
- **管理者の画面を開こうとすると、黙ってダッシュボードに戻される。** 何が起きたのか分からない。自分の操作が悪かったのかと思う
- **「残り 4 回」と出ると焦る。** あと何回で、どうなるのかが分からない。ロックされたら誰に言えばよいのかも書いていない

**全体として**

間違いを指摘してくれる作りは、この人にとって心強い。特に、異常時の記録からヒヤリハットへ内容が引き継がれるのは、二度書きを減らすというこのシステムの狙いがよく表れている。一方、**「いつもと違うこと」が起きたときに、次に何をすればよいかを画面が言わない場面**が目立った。慣れた人は困らないが、この人は手が止まる。

## 4 見つけた問題点

実際に画面で起きたことだけを挙げる。**どう直すかは書かない。** 1巡目で挙げたものは繰り返さない。

### 4-1 記録の正しさ・安全にかかわるもの

| 画面 | 起きたこと | 論点 |
| :-- | :-- | :-- |
| パスワード変更画面 | **新しいパスワードに一時パスワードと同じ値を入れても通る** | 一時パスワードは管理者が口頭や手渡しで伝える値である（基本設計書「一時パスワードの再発行」(4-3)）。同じ値のまま使い続けられると、変更を強制する意味がなくなる。**基本設計書「パスワードの要件」(6-3) には、これを禁じる定めが見当たらない**（設計の抜け） |
| 午睡チェック画面 | 午睡チェックが、時間帯（13:00〜15:00）を過ぎた23時台でも「実施中」のままだった | 基本設計書「午睡チェックの実施」(4-7) は、終了操作を忘れた場合に**午睡の時間帯の終了時刻で自動的に解除する**と定めている。モックアップでは解除されていない |
| チャット画面（職員） | クラスグループへ投稿するとき、**その投稿が保護者にも届くことを知らせる表示が無い**。メンバー一覧には保護者の名前が並んでいるが、入力欄の近くには何も出ない | デモデータにも、職員同士の相談がクラスグループに書かれた例がある。誤送信は起きてから対応する定めはある（基本設計書「誤送信への対応」(4-6)）が、起きる前に気づかせる手立てをどうするか |
| 異常時記録画面 | 異変の記録に、園児の選択と2つの文章の入力が要る。緊急時にまず行うことの案内は無い | この画面は事実を残すためのものである（画面にもそう書かれている）。**対応を終えてから書くものなのか、対応しながら書くものなのか**が画面から読み取れない。前者なら、その旨を示す必要がある |

### 4-2 使い勝手にかかわるもの

| 画面 | 起きたこと | 論点 |
| :-- | :-- | :-- |
| 日誌作成画面 | 「＋ 追加」を押しても写真を選ぶ画面が開かず、番号だけの項目が増える | 写真の添付が未実装である。モックアップの制約として明示するか、実装するか |
| 職員用トップ | ログインに失敗すると「残り 4 回」と出るが、**使い切るとどうなるのか、そのとき誰に頼めばよいのかは出ない** | 残り回数を示すこと自体の是非（第三者に手がかりを与える面もある）と、ロックされたときの案内 |
| 全般 | 一般の権限で管理者の画面を開こうとすると、**何も表示されずにダッシュボードへ戻る** | 権限が無いことを伝えるかどうか |
| 日誌作成画面（ヒヤリハットの起票） | 転記された発生日時が「2026-10-05 23:36:00」の形で入る | ほかの画面の日付の書き方（「2026/10/05（月）」）と揃っていない |
| パスワード変更画面 | 「（制約値は未確定です）」という開発中の注記が出ている | 1巡目の保護者側と同じ。職員側にも出る |

### 4-3 よくできていた点（残したいもの）

問題点ではないが、作り直しの際に失わないよう記録する。

| 画面 | 内容 |
| :-- | :-- |
| 異常時記録画面 → 日誌作成画面 | 「起票する」で、異常時の記録の内容がヒヤリハットの下書きへ転記される |
| 日誌作成画面 | 差し戻しの理由が、開いた画面の上部に出る |
| パスワード変更画面 | 一時パスワードのあいだは、ほかの画面へ進めない |
| 午睡記録検索画面 | チェック時刻と保存時刻を別に出し、「離れている行は、後からまとめて入力された記録です」と説明している |
| アレルギー一覧 | 全クラスを出す理由と、印刷物の取り扱いの注意が書かれている |

## 5 確かめられなかったこと

- **人が触ったときの速さ。** 文字入力が遅い人が、異常時の記録にどれだけ時間を取られるかは、人が打たないと分からない
- **片手で縦に持ったときの届きやすさ。** 画面の幅と向きは再現したが、親指が届くかどうかは分からない
- **ログインに5回失敗したあとの画面。** ロックの表示と、解除までの流れは確かめていない
- **よく使われるパスワードの拒否。** 基本設計書「パスワードの要件」(6-3) は `password` などを拒否すると定めている。試していない
- **写真を付けた日誌が、承認・共有を経て保護者にどう見えるか。** 添付が未実装のため確かめられない
- **異常時の記録を修正する場面、午睡の記録を修正する場面**
- **もう1人の担任と同じ日誌を同時に開いた場合**（編集ロック）
